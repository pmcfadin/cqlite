## TWO DEFECTS FOUND IN MY OWN TEST, both fixed in `388ec3cfd`

1. **Cross-realm prototype identity.** `Object.getPrototypeOf(row) === Object.prototype` is FALSE
   even for a healthy row: jest's sandboxed VM context has a different `Object` intrinsic from the
   one the addon reaches via `env.get_global()`. It failed on rows 2 and 3 — rows with no colliding
   cell at all — reporting "Expected: {} Received: serializes to the same string". Replaced with a
   realm-independent assertion: prototype is not null AND is the same object as a
   known-unmutated row's. `row instanceof Object` had the same flaw; now
   `Object.prototype.toString.call(row)`.
2. **A VACUOUS PASS — the important one.** The "every column is an own data property" case
   originally iterated `Object.keys(row)` and PASSED against unfixed code, because the lost
   `__proto__` column is exactly the one absent from `Object.keys`. **A test whose subject set is
   the output it is checking cannot see an omission from that output.** It now derives its subject
   from the authoritative `result.columns` and is RED. This is precisely the vacuity class the lead
   warned about, found by RED-running rather than by review.
