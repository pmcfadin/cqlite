# Design — Flight/Trino user-docs page

## Context

`cqlite-flight` (Arrow Flight server) and `cqlite-trino` (Trino connector) are documented only in repo
crate READMEs. The published site's `user-docs/` section (autogenerated sidebar from
`website/src/content/docs/user-docs/`) has no entry for them. This change adds one Starlight page and a
discovery link. The authoritative facts already exist in `cqlite-flight/README.md`,
`trino-connector/README.md`, and `docs/flight-trino/PLAN.md`; the page distills and links to them.

## Decision: one combined page, distill-and-link (not duplicate)

**Chosen:** a single page `user-docs/flight-trino.md` covering both the server and the connector, written
as an adoption on-ramp that **links back** to the crate READMEs for exhaustive detail (every flag,
every catalog property, the full ticket schema).

**Why:** the server and connector are one story — the connector is "the query layer on top of the Flight
data plane," and a reader adopting Trino-over-SSTables needs both in sequence. Splitting them forces
cross-page hops for a single workflow. Distill-and-link keeps the site page stable and low-maintenance:
deep, fast-moving detail (exact flag tables) stays single-sourced in the READMEs, so the page does not
silently rot when a flag default changes.

**Alternatives considered:**
- *Two separate pages (flight.md + trino.md).* More nav entries, more duplication of the shared
  compaction-on-read model, and a worse reading order for the primary adoption path. Rejected.
- *Duplicate the full README content onto the site.* Two sources of truth for the flag/property tables
  that drift independently — exactly the rot this project's committed-derived-artifact discipline warns
  against. Rejected in favor of distill + deep-link.
- *Only add the page to the existing `use-cases/` group.* Use-cases pages are scenario narratives, not
  reference on-ramps; Flight/Trino deserves a top-level user-docs entry alongside Write Support and
  Observability. We keep the `use-cases/sidecar-lakehouse.md` cross-link but the home is `user-docs/`.

## Decision: correctness gate is the website build + link validator

There is no Rust surface here, so `scripts/agent-gate.sh` does not exercise this change. The real gate is
`cd website && npm run build`, which runs `starlightLinksValidator` (configured in
`website/astro.config.mjs`) and **fails the build on any broken internal link or anchor** — including the
new cross-link and every intra-page anchor. External links (to GitHub blob URLs / GHCR) are not fetched
by the validator; we keep those to stable, existing paths and reference the repo-relative READMEs by
their site-external GitHub URL form used elsewhere on the site.

## Decision: sidebar placement

Place the page in the `user-docs` group with a `sidebar.order` that groups it with the other
capability/reference pages (after Observability, near the operational surfaces). Exact order value is an
implementation detail chosen to avoid collisions; the autogenerated sidebar reads it from frontmatter.

## Content outline (maps to spec requirements)

1. **What it is** — Flight server exposes a node's SSTables as Arrow streams; connector is the Trino
   query layer. Co-located, compaction-on-read, flushed-SSTables-only, snapshot-aware, `SELECT`-parity.
2. **Run the container** — `ghcr.io/pmcfadin/cqlite-flight`, unauthenticated `docker pull`, `docker run`
   with a **read-only** data mount + `--data-dir`/`--listen`.
3. **Client / ticket API** — the JSON ticket (keyspace/table/ddl + optional snapshot/token-range/
   columns/predicates), the read-only RPC surface (GetFlightInfo/GetSchema/DoGet), and a runnable PyArrow
   example.
4. **Trino connector** — Sidecar node/token-range discovery, one-split-per-replica (read each row once),
   plugin install (`./gradlew installPlugin` / assemble-from-Maven), catalog config incl.
   `cqlite.read-mode` snapshot-vs-live and the per-query snapshot lifecycle.
5. **Reachability** — a cross-link from an existing page so the page is discoverable.

## Risks / mitigations

- **README drift.** Mitigated by distill-and-link: the page carries the model + a working example, and
  points to the README for the authoritative flag/property tables.
- **Broken links.** Mitigated by the `starlightLinksValidator` build gate (internal) + using the same
  stable GitHub-URL convention other pages use (external).
- **Overreach into a runbook.** Non-goal; the page is an on-ramp, deep tuning stays in the READMEs.
