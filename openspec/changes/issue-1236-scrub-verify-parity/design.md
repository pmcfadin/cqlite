## Context

The verify *surface* is shipped and wired (`cqlite verify` → `verify_sstable` → `VerifyReport` with a
12-variant `VerifyErrorClass`), tested by `issue_1000_verifier.rs` against a CQLite-built corruption
corpus. The remaining work is purely the **parity layer**. The design decisions below are about *how* to
make a credible, fail-closed Cassandra parity claim on top of that existing surface — not about
re-designing the verifier.

## Decisions

### D1 — Oracle: capture real `nodetool verify` verdicts from Cassandra 5.0.2 (not hand-encoded, not 6.0)

**Chosen:** Generate the clean source SSTable and capture the corruption verdict by running **Apache
Cassandra 5.0.2 in Docker** (`nodetool verify --extended-verify`, or `StandaloneVerifier` on the
offline files), recording for each fixture the actual verdict (clean / `CorruptSSTableException` + the
check that tripped) plus `cassandra_version: 5.0.2` and the corresponding `cassandra_git_sha`
(`f278f677…`, matching the existing manifest pins).

**Beat:**
- *Hand-encode expected verdicts from reading `VerifyTest.java`/`SortedTableVerifier.java`.* Cheaper, but
  it is an assertion *about* Cassandra, not *from* it — exactly the "trust me" gap this change exists to
  close. Rejected.
- *Use the only local Cassandra checkout (`~/projects/cassandra`, trunk `cassandra-6.0-alpha1`).* The 6.0
  Verifier naming matches, but a 6.0-trunk source **cannot** back a `cassandra_version: 5.0.2` evidence
  claim — the manifest pins 5.0.2 and the lint requires a coherent version/SHA. Rejected; commission off
  5.0.2 like every other 5.0 fixture in the repo.

### D2 — Fixtures: Cassandra-written clean source + reproducible single-mutation injection, binaries gitignored

**Chosen:** One fixture per in-scope corruption class. Each is a **Cassandra-5.0.2-written** clean
SSTable with exactly one deterministic mutation applied (bit-flip / truncation / header damage / removed
TOC entry), described by a committed manifest tuple `{fixture, target_component, mutation, offset,
expected_error_class, cassandra_verdict}`. The corrupted/clean `*.db` binaries are **gitignored** and
**regenerated byte-for-byte** from the committed clean-source recipe + mutation tuples; only the manifest,
`*-sha256.txt`, text components (`TOC.txt`, `Digest.crc32`), the captured Cassandra verdicts, and a README
are committed.

**Beat:** *Force-commit the tiny corrupted binaries (`git add -f`, as the issue text suggests).* The repo
already standardized on regenerate-don't-commit for the existing corruption corpus
(`generate-corruption-corpus.sh`); committing binaries diverges from that convention, bloats the tree, and
makes provenance opaque. Rejected — extend the existing convention/script instead of inventing a second one.

**In-scope corruption classes** (mirroring CQLite's existing `VerifyErrorClass` coverage and the current
10-fixture corpus): `DigestMismatch`, `ChunkDecompressionError`/`ChunkOffsetOutOfBounds` (Data.db
bit-flip / truncation), `CompressionInfoCorrupt`, `IndexEntryCorrupt` (BIG), `BtiRootPointerCorrupt` /
`BtiTrieCorrupt`, `StatisticsHeaderCorrupt`, `SummaryCorrupt`, `MissingComponent`. **Out of scope** (no
CQLite class today): out-of-order key/row, negative local-deletion-time → follow-up issue.

### D3 — Parity assertion: per-fixture verdict equivalence, fail-closed

**Chosen:** The test runs the **public** surface — `verify_sstable(dir, VerifyMode::Full, …)` (the same
call path as `cqlite verify --mode full`, satisfying wiring-evidence) — on each Cassandra-written
corrupted fixture and asserts:
1. **Class match:** the `VerifyReport.findings` contain the `expected_error_class` for the corrupted
   component (and the clean baseline yields zero findings).
2. **Verdict match:** CQLite's overall verdict (findings present ⇒ corrupt) agrees with Cassandra's
   captured verdict (`CorruptSSTableException` ⇒ corrupt; clean ⇒ clean) for that fixture.

Fixture-gating follows repo doctrine: skip-clean when `CQLITE_DATASETS_ROOT` binaries are absent; **fail**
when present-but-wrong; `CQLITE_REQUIRE_FIXTURES=1` turns skip into hard-fail in CI. Zero-fixtures-when-
present is a failure.

**Beat:** *Assert only "CQLite reports some corruption."* That is the weak claim the manifest already
disclaims; parity means the **same class** on the **same bytes** vs a captured Cassandra verdict. Rejected.

### D4 — Manifest promotion + CI: `mirrored`, fixture-backed, on a workflow that actually runs the comparison

**Chosen:** Promote `cass.corruption_verify.component_corruption_detection` to `status: mirrored` with the
lint-required fixture-backed evidence block (`cassandra_version`, `cassandra_git_sha`,
`storage_format_version`, `fixture_generation_command`, `comparison_command`, `reference_paths`,
`failure_artifacts`) and point `ci.workflow` at a real workflow that invokes `comparison_command` —
extending the existing `compression-corruption-parity.yml` lane (which already generates the corpus and
runs `issue_1000_verifier`) rather than adding a parallel workflow. Regenerate
`docs/reports/cassandra-test-parity.md`; `cassandra-parity` lint green.

**Beat:** *Mark it `byte_for_byte`.* Verify parity is a **verdict/semantic** claim (does CQLite flag the
same corruption Cassandra does), not a byte-identity claim about an output artifact; `mirrored` with a
`comparison_command` is the correct, honest tier. Rejected `byte_for_byte`.

## Risks / Trade-offs

- **Cassandra 5.0.2 Docker availability under emulation is slow** (a known repo hazard). Mitigation: the
  fixture-generation script is run once to commission + capture verdicts; CI regenerates the *corrupted
  binaries* deterministically from committed clean sources without needing live Cassandra on every run
  (the Cassandra verdict is captured-and-committed, not re-derived per CI run).
- **Scope honesty:** out-of-order and negative-deletion-time classes are genuinely unmirrored; the
  manifest scenario's `known_limitations`/scope must say so rather than implying full Verifier parity.

## Migration / Rollout

Additive. New capability spec, new fixtures + script, one promoted manifest row, one extended CI lane.
No API, CLI, or binding changes. Follow-ups filed: scrub/recovery parity; out-of-order + negative-LDT
error classes; integrity-API consolidation.
