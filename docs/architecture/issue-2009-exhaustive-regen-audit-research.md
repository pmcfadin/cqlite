- The `exhaustive-regeneration.yml` lane (weekly + `workflow_dispatch`, issue #1026) has
  **never been green** — 5 runs total, all failures. Until 2026-07-05 every run aborted at
  the #1991 generator bug (`collections_with_udts` KeyError:0), so the **corpus-audit stage
  had never executed**. PR #2002 fixed the abort (verified in-run:
  `collections_with_udts: 50 rows inserted (0 skipped)`); this failure is the debt behind it.
- Release note: the v0.13.0 release ships with an **owner-approved waiver** of the
  parity-release-checklist "recent `exhaustive_regeneration` pass" item (decision 2026-07-05):
  the lane has never passed, so it cannot be a regression bar; the committed corpus is
  independently validated by required_parity (5/5 green on `ad088357`), nightly_docker and
  sstabledump-parity-gate.

## Finding distribution (the load-bearing facts)

**435 findings = 120 `MISSING-REFERENCE` + 315 `UNEXPECTED-COMPONENT-CHANGE`.**

### The 315 CHANGE findings are ALL missing *derived text goldens*

Every single `UNEXPECTED-COMPONENT-CHANGE` is "expected component is **absent from the
regenerated corpus**" and every one is a derived artifact:

| Component type | Count |
|---|---|
| `*-Statistics.db.txt` | 160 |
| `*-Data.db.jsonl` | 155 |

→ **Hypothesis WS1 (biggest win):** the golden-derivation phase (sstabledump → `.jsonl`,
statistics dump → `.txt`) is either not run by the workflow's regeneration flow or writes
to a layout `corpus-audit --corpus .` doesn't see. One wiring fix likely clears 315/435
(72%) of the findings. Check: which script/step in `exhaustive-regeneration.yml` is
responsible for derived goldens, and what directory the audit's `--corpus .` resolves to
relative to the regenerated tree.

Per keyspace (CHANGE): test_types 56, test_deltas 54, system_schema 38, test_tomb 28,
test_timeseries 18, test_wide_rows 16, test_collections 16, test_basic 16, test_oa 12,
system 12, test_signed_coll 8, test_compactionparityudt 8, test_da 7, test_comp 7,
test_writeparity 6, test_compaction_tombstone_ttl 6, test_compactionparity 4,
system_auth 2, test_big 1.

Note `system`/`system_schema`/`system_auth` (52 findings): the audit expects derived
goldens for **Cassandra system keyspaces**. Regenerating system tables is inherently
run-dependent — **WS3** below asks whether these belong in the expected inventory at all.

"scenario … references a corpus component the regeneration did not produce (no regenerated
file shares its table+component identity)". Mix of binary components (Data.db, Index.db,

→ **Hypothesis WS2:** corpora added over recent months (tombstone parity, compaction
parity, write parity, type matrix) are generated by their own scripts
(`generate-tombstone-parity.sh`, compaction-parity generators, etc.) that the
exhaustive-regeneration workflow **does not invoke** — its generator_commands list (above)
covers only 5 scripts. Inventory which script owns each missing keyspace and wire them in
(or record in the manifest that those scenarios' components are pinned, not regenerable).

## Suggested workstream decomposition

1. **WS1 — derived-golden phase (315 findings):** find/wire the sstabledump-JSONL +
   Statistics-txt derivation into the regen flow; verify `--corpus` path semantics.
2. **WS2 — generator coverage of newer corpora (≈120 findings):** map manifest keyspaces →
   owning generator script → wire missing ones into `exhaustive-regeneration.yml`; add a
   completeness check so a new corpus can't be added without regen coverage (this is the
   "documented regen-matrix coverage" acceptance criterion in #2009).
3. **WS3 — audit semantics for system keyspaces (≈52 of WS1's findings):** decide whether
   `system*` derived goldens belong in the expected inventory of a *regeneration* audit, or
   should be excluded/pinned. Fail-closed either way — no silent skips.
