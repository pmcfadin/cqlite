== POSITIVE CONTROL for the gate-integrity guard (#3287 roborev job 308, finding 1) ==

A guard that has never been shown to fire is not evidence. This is the guard finding
the exact defect it was written for: the ORIGINAL ungated window (benchmark
--delay-ms only, no `perf -D`, no control FIFO), measured at the same two probe
sizes the guard uses.

  window          accesses=1e3        accesses=1e5        ratio    guard (>= 10x)
  --------------  ------------------  ------------------  -------  --------------
  UNGATED         243,571,204 instr   244,165,415 instr   1.00x    FAILS  <- caught
  GATED (FIFO)          6,296 instr        600,316 instr  95.35x   PASSES

The GATED row is read from this run's own gate-probe CSVs and shifts slightly on
every re-run; the UNGATED row is a one-off re-measurement of the original
defective window, which no current revision of the probe regenerates.

Read the ungated row: the count barely moves when the workload does 100x more
work, because a CONSTANT term -- buffer init (page faults + permutation build) and
exit-time address-space teardown -- of ~244 MILLION instructions sits inside the
window, against roughly 6,300 instructions of actual 1e3-access chase. The signal
is buried under a factor of ~38,000 of noise that is ASYMMETRIC between the arms.

That is what the original capture published ratios from, and it is why the
friendly->hostile instruction ratio read 9.4 there and reads 1.002 gated. The
instruction ratio is the control's own validity property (#3224 requires it near
1.0), so the ungated capture had not merely inflated numbers -- it had broken the
control while still reporting success.

Two properties of the guard worth keeping:

 1. It is a SCALING test, not a tuned ceiling, so it is host-independent. #3224
    used an absolute ceiling of 1e6 instructions for 1e3 accesses, correct for its
    own machine; importing that constant would risk a false FAIL elsewhere. The
    absolute is still REPORTED for the reader -- it is just not what fails the run.
 2. The discrimination is enormous (1.00x vs 95.33x against a 10x threshold), so
    the bound needs no tuning and is not sensitive to host or load.

Reproduce:
  cc -O2 -std=c99 -pthread -o ch docs/reports/ws0-3224-artifacts/cache-hostile.c -lm
  for n in 1000 100000; do
    taskset -c 2,10 perf stat -x, -e instructions:u -- \
      ./ch chase --buffer-mib 512 --working-kib 0 --accesses $n --arm pc-$n --delay-ms 1500
  done

== POSITIVE CONTROLS for the two HIGH findings of #3287 roborev job 312 ==
================================================================================

Same principle as above: a guard that has never been shown to fire is not
evidence. Both fixes were verified by planting the defect they exist to catch,
AND by running the same plant against the PREVIOUS revision to confirm the
finding was real rather than theoretical.

-- A. Gate A was FAIL-OPEN (finding 1) ----------------------------------------

Revision 4 classified the TMA probe with `TMA_L1=$(tma_probe ...)`. Command
substitution runs the function in a SUBSHELL, so every `note_fail` inside it set
FAILED=1 in a child that then exited; the parent's FAILED stayed 0.

Plant: a TMA probe command that exits 7 with an unrecognised diagnostic — i.e. an
operational error, which must never be read as a capability answer.

  revision 4 (subshell):   exit 0   VERDICT: COMPLETE   <-- FAIL-OPEN, reproduced
  fixed (global return):   exit 1   VERDICT: UNMEASURED
                                    "Gate A: 'PLANTED operational error' failed
                                     operationally (rc=7) — TMA capability NOT
                                     measured, and an operational error is not a
                                     capability answer"

So revision 4 could report a COMPLETE probe over a TMA gate it had not measured —
on the one gate #3287's AC1 turns on. The class was then swept across the whole
file (`grep` for any state-mutating function invoked inside `$( )`): `tma_probe`
was its ONLY instance. `classify` is also called in `$( )` and is safe because it
mutates nothing — verified by reading it, not assumed.

-- B. Stale measurements could outlive their host (finding 2) ------------------

This probe exists to be re-run on a CANDIDATE host. If a group is unavailable on
the new host, no CSV is written for it — and revision 4 left the OLD file in
place, so the report read a PREVIOUS machine's numbers and printed them
beside the current inventory under a COMPLETE verdict. The worst failure
available here: a confident answer about the wrong computer.

Plant: pre-seed the output directory with arm CSVs claiming
`cycle_activity.stalls_l3_miss:u` = 999,999,999 (friendly) and 888,888,888
(hostile) — i.e. a counter that looks alive.

  after the fixed run:  0 files still contain the planted values
                        cycle_activity.stalls_l3_miss:u reads 0 in all three
                        arms of THIS run (differential.txt)

The planted numbers are gone and every number reported is derived from this run
alone. (That line was quoted from the probe's removed auto-classifier; since
#3870 the probe prints the recorded counts and leaves the reading to you. The
purge property being demonstrated here is unchanged, and selftest-guards.sh
case 5 pins it.) All
generated measurement files are removed up front; the hand-written file you are
reading is deliberately not matched by those globs.
