WHAT THIS CONFIRMS -- and one SCOPE LIMIT it surfaces that the report now states:

  1. CONFIRMED. stalls_l3_miss counts EXECUTION STALLS WHILE AN L3-MISS DEMAND
     LOAD IS OUTSTANDING. That is precisely the quantity the classical
     'delta(misses/row) x penalty' product is trying to estimate, so charging it
     directly is sound; and it is inherently MLP-correct, because two
     overlapping misses that stall the same cycle are ONE stalled cycle -- which
     is what a cycles/row accounting must add up.

  2. CONFIRMED. The three cycle_activity terms NEST (l3_miss subset of l2_miss
     subset of total), which is what licenses the additive decomposition in
     report section 5.3 as a PARTITION of the measured delta rather than an
     estimate carrying a slack term.

  3. SCOPE LIMIT (umask=0x6, the definition says 'demand load'). The term is
     DEMAND-LOAD scoped. Stalls arising from PREFETCH traffic -- prefetches
     saturating fill buffers or memory queues -- are NOT counted in it and fall
     into 'other execution stalls'. This matters here specifically: on a
     streaming scan the hardware prefetcher does most of the fetching (report
     section 3.4 -- demand LLC-load-misses x 64 B accounts for only ~2.4 KB of
     the ~22 KB of DRAM traffic per row), so the 67.76% figure is a DEMAND-LOAD
     attribution and some part of the ~32% residual is plausibly prefetch-
     related memory cost that this counter cannot see. The report says so
     rather than letting 67.76% be read as 'all memory cost'.

  4. CONFIRMED. MLP = pending / pending_cycles is the mean number of outstanding
     L1D misses ACROSS CYCLES IN WHICH AT LEAST ONE IS OUTSTANDING (cmask=0x1 on
     pending_cycles, per the definitions above), which is the correct divisor
     for converting an unloaded serial-chase latency into a per-miss cost.
