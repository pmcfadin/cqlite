# WS0 head-to-head: stock Cassandra 5.0.8 vs CQLite on identical SSTable bytes

CQLite issue **#3026** (WS0 of umbrella **#3023**). Measured 2026-07-27 on a single
**c7i.4xlarge** (16 vCPU / **8 physical cores**, 30 GiB RAM, EBS-only root).
Everything below is **measured**, never modelled, unless a line says otherwise.

This file is the reproduction contract: a future agent should be able to re-derive
every number in the WS0 report from the commands here.

---

## 0. What is being compared

| | Arm 1 | Arm 2a | Arm 2b |
|---|---|---|---|
| engine | Cassandra 5.0.8 | CQLite `cqlite-core` | CQLite `cqlite-flight` |
| surface | native CQL protocol | `Database::execute_streaming` | Arrow Flight `do_get` |
| client | `cas-scan.py` (python driver) | in-process harness | `flight-loadgen` |
| delivers rows to a client? | yes (`--mode rows`) / no (`--mode count`) | no | yes |

The two *comparable pairs* are:

* **read + materialise, nothing shipped to a client**
  Cassandra `SELECT count(*)` ↔ CQLite bare `execute_streaming` scan.
* **read + materialise + serialise + ship every row to a real client over a socket**
  Cassandra `SELECT *` ↔ CQLite Flight `do_get`.

`count(*)` is a *legitimate* read-path comparator here, not a cheap row-skip — see
§7 finding **F2**, which proves it from a profile rather than assuming it.

## 3. Box discipline (both arms)

* **One engine at a time.** Cassandra is `nodetool drain`-ed and stopped before Arm 2
  and restarted after; verify `pgrep -x java` is empty and `free -h` shows ~29 GiB
  available. (Its 8 GiB heap / ~9.7 GiB RSS otherwise contends.)
* **`kernel.perf_event_paranoid` silently reverts to 4 on this box.** Every driver
  re-asserts `-1` before each run. Do not trust a stale value.
* **Two pinnings, deliberately** — physical core *N* = logical *N* and *N+8*:
  * `-c 2` — **one hardware thread**, SMT sibling 10 idle. The only valid basis for
    `cycles/row` and `IPC`: with both siblings busy the `cycles` counters on each are
    summed and wall cycles are double-counted.
  * `-c 2,10` — **one whole physical core**. The basis for
    `rows/s per physical core`.
  The client always runs on a *different* physical-core set (`4-7`, `12-15`).
* **CPU-wide perf (`-C <cpus>`), never per-task (`-p` / workload).** Measured on this
  box: per-task counting cost **>2× wall time** on the CQLite scan
  (163k rows/s metered vs 360k unmetered) because that scan performs ~540k context
  switches and per-task counters are saved/restored on every one. CPU-wide counting
  has no per-switch cost, and since the metered CPUs run nothing but the engine, the
  counts are the engine's. **Re-check this if you change either engine's threading.**
* **`samply` records 0 samples on this kernel — do not use it.**
* **Uncore IMC counters do not exist in this VM** (hypervisor-masked;
  `LLC-load-misses` unsupported, `offcore_requests.*` read exactly 0). The memory
  traffic proxy is `l2_lines_in.all × 64`. See §7 **F6** for where that proxy is
  trustworthy and where it is only an upper bound.

## 4. Arm 1 — Cassandra

```bash
# start (MAX_HEAP_SIZE is the ONE non-path deviation from stock; see §6)
cd /home/ubuntu/ws0/apache-cassandra-5.0.8
export JAVA_HOME=/usr/lib/jvm/java-17-openjdk-amd64
MAX_HEAP_SIZE=8G setsid nohup bin/cassandra -f > ../cassandra-logs/stdout.log 2>&1 &

# one measurement point:
#   arm1c-cassandra.sh <label> <warm|cold> <count|rows> <cpus> <shards> [inflight] [ranges]
cd /home/ubuntu/ws0/ws0-h2h
bash arm1c-cassandra.sh cas-warm-count-1core warm count 2,10 6 8 512
bash arm1c-cassandra.sh cas-warm-rows-1hw    warm rows  2    6 8 512
```

`arm1c-cassandra.sh` (in `/home/ubuntu/ws0/ws0-h2h/`) does: select the daemon PID
**by executable name, not `pgrep -f`** (see §5), pin all its threads with
`taskset -acp`, warm or `drop_caches`, then run the sharded client under
`perf stat -C`, and emit a JSON summary including
`daemon_core_utilization` and a `client_bound` flag.

Two client-side traps it exists to avoid:

* `fullscan.py` issues its 512 range queries **strictly sequentially**, so the server
  idles for every round trip. `cas-scan.py` keeps `--inflight` queries in flight.
* Even so, **one** python process cannot saturate one pinned daemon core on
  `SELECT *` (measured utilisation 0.63). `shardrun.sh` runs `--shards` independent
  client processes over disjoint slices of the ring, each on its own core, and sums.
  With 6 shards the daemon core reaches utilisation **1.00** for both modes.
  **Always read `daemon_core_utilization`; if it is < 0.9 the run measured the client.**

## 5. Two `pgrep` traps that silently produce zeros or kill your shell

* **`pgrep -f 'org.apache.cassandra.service.CassandraDaemon'` matches the *shell* that
  launched the node** (that string is in the wrapper's own cmdline). Pinning and
  `perf stat -p` then target a 1-thread bash process and **every counter reads 0**.
  Select by executable instead and assert the thread count:
  ```bash
  for p in $(pgrep -x java); do
    tr '\0' ' ' < /proc/$p/cmdline | grep -q CassandraDaemon && PID=$p && break
  done
  [ "$(ls /proc/$PID/task | wc -l)" -gt 20 ] || exit 1
  ```
* **`pkill -f 'cqlite-flight --data-dir'` matches the running shell's own cmdline and
  kills the shell** (and signals the server mid-stream). Use `pkill -x cqlite-flight`.

## 6. Arm 2 — CQLite

Binaries (pre-built, release + retained DWARF; **do not rebuild** unless needed):
`/home/ubuntu/workspace/wt-3026/target/release/{cqlite,cqlite-flight,flight-loadgen}`.
Throwaway harness `/home/ubuntu/ws0/ws0-cqlite/scan-harness` →
`/home/ubuntu/ws0/ws0-cqlite/harness-target/release/ws0-scan-harness`
(rebuild: `CARGO_BUILD_JOBS=6 CARGO_TARGET_DIR=.../harness-target
CARGO_PROFILE_RELEASE_STRIP=none CARGO_PROFILE_RELEASE_DEBUG=true cargo build --release`
— the manifest hardcodes `strip = true`).

```bash
cd /home/ubuntu/ws0/ws0-h2h
# arm2-cqlite.sh <label> <warm|cold> <scan|scan-arrow|scan-collect> <cpus>
bash arm2-cqlite.sh cq-warm-scan-1core  warm scan       2,10
bash arm2-cqlite.sh cq-warm-arrow-1hw   warm scan-arrow 2

# arm2-flight.sh <label> <warm|cold> <cpus> <step-seconds>
bash arm2-flight.sh fl-warm-1core warm 2,10 140
```

Harness anti-flattery rules that must stay in force:

* `--mode scan` = **bare `execute_streaming`**. `--mode scan-collect`
  (`db.execute()`, O(rows) resident) is measured only for comparability with
  `benches/read.rs::full_scan` and is **not** a throughput surface. Never quote it.
* `--no-fold` is used for all reported numbers; the anti-elision digest costs
  ~+28% cycles and is harness overhead, not CQLite. The row is still received and
  `black_box`-ed, and decode happens inside `cqlite-core` before the row is handed
  over, so nothing can be elided. Run **once without** `--no-fold` per change to
  confirm the digest is stable: `0x4903ffa446163c4b` (fold) over 3,999,890 rows /
  47,998,680 cells.
* 0 rows on a present dataset → exit 2. Passes must agree on rows and digest.
* Warm = one full untimed pre-pass **in a separate process**, then a fresh process
  whose single timed pass is fully page-cache-warm, so every counter belongs to a
  warm scan. Cold = `sync; echo 3 > /proc/sys/vm/drop_caches` immediately before.
* Flight: concurrency 1 (`--ramp 1`), `--shape full`, ticket
  `/home/ubuntu/ws0/ws0-h2h/ws0-events-template.json` (full ring = `token_start` and
  `token_end` both `null`; the server takes its schema from the ticket `ddl` — there
  is no `--schema` flag). Take rows/s from the p50 full-scan latency as well as from
  the step, because a step boundary truncates an in-flight 65 s scan.
  Check `server_cpu_utilization_of_pinned_set`.

**Disclosed deviation from stock Cassandra:** heap pinned to **8 GiB**
(`MAX_HEAP_SIZE=8G`). Stock auto-sizing picks 15.4 GiB (half of RAM) on this box and
such a daemon reached ~17 GB RSS and was OOM-killed earlier in the session
(confirmed in `dmesg`). `file_cache_enabled=false`, so the chunk cache is off and
heap size should barely affect a scan — but this is a deviation and is reported as
one, not assumed harmless. `disk_access_mode` resolves to `standard`
(Data.db pread, Index.db mmap). Only paths/addresses otherwise differ from stock
(`/home/ubuntu/ws0/ws0-corpus/cassandra.yaml.diff`).

## 7. Replicates, and the findings the method exists to protect

Every headline point is the **median of 3 replicate runs** (Flight: 3 at `-c 2,10`);
run-to-run spread is under ±2% for every configuration except one noted below.
`rep-*` labels in `/home/ubuntu/ws0/ws0-results/h2h/` are those replicates.

* **F1 — no correctness bug.** CQLite returns exactly 3,999,890 rows and 12
  cells/row, digest stable across every run, matching Cassandra's two oracles.
* **F2 — Cassandra `count(*)` does NOT skip cell deserialisation**, so it is a fair
  read-path comparator. Proven from the SJK profile, which shows
  `Cell$Serializer.deserialize` (8.0% self) and `ReadResponse.createDataResponse` →
  `UnfilteredPartitionIterators$Serializer.serialize` at **76.6% inclusive** — even a
  *local* `count(*)` materialises rows and re-serialises them into a ReadResponse.
* **F3 — the pre-existing 288,725 rows/s reference is client-bound, not Cassandra's
  throughput.** Reproduced exactly at `--inflight 1` (292,849 rows/s / 13.66 s).
  With concurrency the same warm scan reaches **2,086,231 rows/s** on the full box —
  ~7.1× higher. Do not quote the sequential figure as a Cassandra capability.
* **F4 — CQLite mmaps Data.db; Cassandra preads it.** `/proc/<pid>/maps` shows two
  `r--s` mappings of Data.db (783,799,203 B each, 1,567.6 MB of VA); the whole scan
  issues **115–116 `read()` syscalls / 3.08 MB `rchar`** (metadata only).
  Cassandra: **~4,190 preads / 1,059,659,423 B `rchar`**. Syscall counts across the
  two engines are therefore **descriptive only, never a ratio**.
* **F5 — pinning beats spreading for CQLite.** Unpinned the bare scan takes 18.74 s
  with 1.98M voluntary context switches; pinned to one hardware thread it takes
  11.16 s with 310k. The `tokio::sync::mpsc` producer/consumer handoff, not decode,
  is the scaling limiter.
* **F6 — where the `l2_lines_in.all × 64` proxy is and is not DRAM traffic.**
  For the CQLite bare scan it reads 1,240 B/row = 435 MB/s, against a decompression
  floor of 243 MB/s (2.77 GB per 11.4 s scan) — plausible as real DRAM+L3 traffic and
  **confirming** the prior 1.0–1.9 KB/row band on a genuinely >L3 (784 MB) corpus.
  For the JVM arm it reads 9,650 B/row = 3.0 GB/s, ~12× the decompressed stream:
  allocation/GC churn refilling from **L3**, not DRAM. The proxy's ±1.2% DRAM
  calibration does **not** transfer to Cassandra or to the Arrow path — treat those
  as upper bounds.
* **F7 — `perf stat -p` is not free.** See §3. This artefact alone moved the CQLite
  bare-scan number by 2.1×; it is the single easiest way to publish a wrong ratio.
* Raw artefacts: `/home/ubuntu/ws0/ws0-results/h2h/` — `summary-*.txt` (JSON per
  point), `perf-*.txt`, `scan-*.json`, `flight-*.jsonl`, `prof-*.data`
  (`perf report --stdio --no-children`), `prof-{rows,count}.stcap` + `.txt`
  (Cassandra, SJK; analyse with `/home/ubuntu/ws0/ws0-h2h/aggr-stacks.py`).

## 8. Profiling recipes

```bash
# CQLite / Flight: flat self-time (release + DWARF; frame pointers absent, so -g
# call graphs are unreliable — a flat profile is what these numbers come from)
perf record -C 2 -F 999 -o prof.data -- taskset -c 2 <workload>
perf report -i prof.data --stdio --no-children --percent-limit 0.6

# Cassandra: `perf` cannot see JIT frames (no perf-map agent, no
# -XX:+PreserveFramePointer). SJK, invoked DIRECTLY (nodetool's sjk wrapper
# mangles jcommander args), on cores away from the metered one:
CP=$CAS/lib/sjk-core-0.14.jar:$CAS/lib/sjk-stacktrace-0.14.jar:$CAS/lib/sjk-cli-0.14.jar:\
$CAS/lib/sjk-json-0.14.jar:$CAS/lib/jcommander-1.30.jar:$CAS/lib/jvm-attach-api-1.5.jar:\
$CAS/lib/HdrHistogram-2.1.12.jar
taskset -c 12-15 java -cp "$CP" org.gridkit.jvmtool.SJK stcap -p $PID -i 10ms -o prof.stcap
java -cp "$CP" org.gridkit.jvmtool.SJK ssa -f prof.stcap --print > prof.txt
python3 /home/ubuntu/ws0/ws0-h2h/aggr-stacks.py prof.txt
```
`aggr-stacks.py` keeps only **RUNNABLE `ReadStage-*` / `Native-Transport-Requests-*`**
threads. Without that filter the histogram is 85% `RMI TCP Accept` and
`Reference Handler` — permanently RUNNABLE-but-idle threads that swamp the real work.
These are safepoint-biased samples; treat them as structural, not exact.
