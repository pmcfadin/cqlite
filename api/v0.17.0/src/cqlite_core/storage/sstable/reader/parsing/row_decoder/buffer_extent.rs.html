1//! Issue #3782 — the buffer-extent contract every block-emit parse must STATE.
2//!
3//! # Why this is a type and not a defaulted flag
4//!
5//! The block-emit paths have no `NeedMore`/refill vocabulary (unlike
6//! `drive_partition_sliding`, which decides the same question from its
7//! authoritative `at_final_chunk`), so tolerance cannot be decided inside the
8//! parse: only the CALLER knows whether more bytes can still arrive.
9//!
10//! That question used to be answered by a builder flag defaulting to `false` —
11//! the DATA-LOSING direction. A new parse site therefore inherited the tolerant
12//! break silently, and that is exactly how the BTI (`da`) full scan came to
13//! truncate: `bti_scan_with_metadata_cancellable` stitched the whole data
14//! section and then parsed it with a defaulted parser, so a corrupt row ended
15//! the scan and returned `Ok` with 120 of 468 rows (measured on a real `da`
16//! fixture with one compressed byte flipped). Six stitched-buffer sites were
17//! audited for the same shape after roborev job 48 named one of them.
18//!
19//! Passing the extent EXPLICITLY at the parse call makes that class
20//! unrepresentable: a new call site cannot compile without answering the
21//! question, and the answer sits beside the buffer it describes rather than
22//! several builder calls away.
23/// # Contract — the caller MUST state which of these its buffer is
24///
25/// This type is `pub` because it is a REQUIRED parameter of public methods on
26/// [`V5CompressedLegacyParser`](super::V5CompressedLegacyParser) (re-exported
27/// `doc(hidden)` for integration tests, issue #166): a public method taking an
28/// unnameable type cannot be called at all, so the type is re-exported beside
29/// the parser (`storage::sstable::reader::BufferExtent`).
30///
31/// Choosing the WRONG variant is a correctness bug in both directions, and
32/// neither direction is safe to guess for the caller:
33///
34/// * [`BufferExtent::Complete`] on a buffer that is really a WINDOW turns every
35///   legitimate straddling row — a row whose bytes continue in the next chunk —
36///   into a hard error. The point readers use the tolerant break as their
37///   straddle protocol, so this direction is a false refusal on healthy data.
38/// * [`BufferExtent::Window`] on a buffer that is really COMPLETE silently
39///   drops the remainder of the extent on any decode error: DATA LOSS, reported
40///   as `Ok`. That is the defect issue #3782 removed.
41///
42/// Hence there is deliberately **no** defaulted setter and **no** wrapper that
43/// picks a variant: the previous `with_complete_buffer(bool)` builder flag
44/// defaulted to the data-losing answer, and a new parse site inherited it
45/// silently. A two-variant enum that must be written at the call site keeps the
46/// answer beside the buffer it describes. Do NOT reintroduce a default — the
47/// earlier "narrow the public surface" review nit was about the defaulted
48/// boolean setter, not about this self-documenting required parameter.
49#[derive(Clone, Copy, Debug, PartialEq, Eq)]
50pub enum BufferExtent {
51    /// The buffer holds EVERY byte of the extent being decoded — the whole
52    /// stitched data section, a partition slice already proven fully consumed,
53    /// or a standalone buffer with no continuation. No further bytes can arrive
54    /// to finish a row, so a row that fails to decode is truncation or
55    /// corruption — DATA LOSS — and MUST be reported.
56    Complete,
57    /// The buffer is a chunk-covering WINDOW whose tail may cut a row that
58    /// continues in the next chunk. A decode failure at the tail is the
59    /// ordinary straddling-row case and stays tolerant; refusing here would
60    /// break a legitimate, load-bearing control flow (the point readers use it
61    /// as their straddle protocol) rather than fix a defect.
62    Window,
63}
64
65impl BufferExtent {
66    /// `true` only for [`BufferExtent::Complete`] — the affirmative value, so a
67    /// permissive branch is never keyed on "not the bad one".
68    ///
69    /// Stays `pub(crate)`: the enum has to be NAMEABLE from outside (it is a
70    /// public parameter), but out-of-crate callers construct variants rather
71    /// than inspect them, so the predicate is not widened with the type.
72    pub(crate) fn is_complete(self) -> bool {
73        matches!(self, BufferExtent::Complete)
74    }
75}

77/// Issue #3928 — the ONE predicate that decides whether an undecodable partition
78/// HEADER is refused, asked by both header arms.
79///
80/// # Why this exists, and what it has stopped being
81///
82/// The header arms reached this shape over four review rounds, each moving the
83/// boundary by one case: the arm consulted NOTHING (a `tracing::warn!` and
84/// `offset += 1`, unconditionally); then a per-site byte-count test
85/// (`remaining < 2`, `data.len() < 2`) plus a per-CALL boolean (`bounded`); and
86/// each of those was wrong at its own edges — the byte count because one
87/// surviving byte is the first byte of a truncated header and not a tail, the
88/// call-wide boolean because a row-body window introduces no uncertainty until
89/// its endpoint is REACHED. Both edges are edges of ONE question, so the
90/// question is asked once:
91///
92/// > Can a byte still arrive?
93///
94/// # The second axis was REMOVED, not decided differently (finding B1)
95///
96/// Round 2 gave this type a second field, `attributable`, cleared when the #954
97/// row-body bound stopped the walk: past that bound the outer partition loop was
98/// re-entering the header arm at bytes nothing promised would begin a partition,
99/// so tolerance had to take over there.
100///
101/// Round 3 removed the SITUATION instead. Scanning on past the bound was itself
102/// the defect — it read partitions the caller never asked for and could fabricate
103/// one from misaligned row payload (measured: 99 foreign partition keys from a
104/// walk bounded at offset 62) — so the block walk now TERMINATES at the bound.
105/// With no offset past the bound ever reaching a header arm, `attributable` was
106/// provably always `true`; the compiler said so, by reporting its setter
107/// unreachable. It is gone because the code path it described is gone, NOT
108/// because the reasoning behind it was wrong. If a future stop ever leaves the
109/// walk mid-partition and then probes for a header, that axis has to come back
110/// with it.
111///
112/// Two stops deliberately do NOT get it today: the row loop's unparseable
113/// range-tombstone-marker breaks leave the cursor on the marker, and refusing
114/// there — with the marker NAMED in the diagnostic, see `structural_note_at` —
115/// is louder than tolerating, which is the whole subject of this issue.
116///
117/// # Why still a type
118///
119/// So the two arms cannot drift on the refusal question. That is not
120/// hypothetical: `partition_header_readiness` and this file's own arm held two
121/// implementations of the oa/da DeletionTime sizing rule, and #1741's fix
122/// reached only one of them (finding B2). One `refuses()`, asked from both arms,
123/// is the same defence applied to the tolerance question.
124#[derive(Clone, Copy, Debug, PartialEq, Eq)]
125pub(in crate::storage::sstable::reader::parsing::row_decoder) struct HeaderTolerance {
126    extent: BufferExtent,
127}
128
129impl HeaderTolerance {
130    /// The block-emit walk, which is handed its extent explicitly.
131    pub(in crate::storage::sstable::reader::parsing::row_decoder) fn for_extent(
132        extent: BufferExtent,
133    ) -> Self {
134        Self { extent }
135    }
136
137    /// The sliding drivers, whose `at_final_chunk` IS the "no further bytes can
138    /// arrive" fact — an authoritative property of the window, not a guess about
139    /// the bytes.
140    pub(in crate::storage::sstable::reader::parsing::row_decoder) fn for_final_chunk(
141        at_final_chunk: bool,
142    ) -> Self {
143        Self::for_extent(if at_final_chunk {
144            BufferExtent::Complete
145        } else {
146            BufferExtent::Window
147        })
148    }
149
150    /// Must an undecodable partition header here be REPORTED rather than
151    /// resynchronised past?
152    ///
153    /// Keyed on the AFFIRMATIVE value, so a permissive answer is never derived
154    /// from "not the bad one".
155    pub(in crate::storage::sstable::reader::parsing::row_decoder) fn refuses(self) -> bool {
156        self.extent.is_complete()
157    }
158
159    /// Why this walk is tolerating, for a diagnostic. Never used to decide.
160    pub(in crate::storage::sstable::reader::parsing::row_decoder) fn why_tolerant(
161        self,
162    ) -> &'static str {
163        if self.extent.is_complete() {
164            "nothing is tolerating: this walk is over a proven-complete buffer"
165        } else {
166            "the buffer is a chunk-covering WINDOW, so a header may still be completed by the \
167             next chunk"
168        }
169    }
170}
