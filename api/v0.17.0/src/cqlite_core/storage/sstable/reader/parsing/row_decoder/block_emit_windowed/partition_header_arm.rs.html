1//! Issue #3928 — the ONE partition-HEADER arm of the block-emit walk.
2//!
3//! Split out of `block_emit_windowed.rs` (campsite rule, epic #1116) when that
4//! arm gained a tolerance DECISION: it now answers three different things
5//! (a decoded header, the end of a window, a resynchronisation) and the choice
6//! between the last two rests on the caller's [`BufferExtent`], so it is a
7//! responsibility rather than a few inline bounds checks.
8//!
9//! # What changed, and why the tolerant answer was unsound
10//!
11//! Both arms used to `tracing::warn!` and then `offset += 1` unconditionally.
12//! On a buffer the caller has PROVEN complete that has two consequences, and the
13//! second is the bad one:
14//!
15//! 1. the malformed partition is silently DROPPED, and
16//! 2. the one-byte resync can land on MISALIGNED bytes that parse as a plausible
17//!    header — so the walk INVENTS a partition that does not exist.
18//!
19//! Measured on a real Cassandra 5.0 `da` fixture with ONE compressed byte
20//! flipped so the first partition's `DeletionTime` discriminator reads `0xFF`
21//! (which Cassandra's own `DeletionTime.Serializer.deserialize` throws on,
22//! cassandra-5.0.8 `DeletionTime.java:222-230`): `distinct_partition_keys`
23//! answered `Ok` with **5** partition keys where the pristine fixture has **3**
24//! — 2 FABRICATED — and `get_all_entries` answered `Ok` with **0** of 468 rows.
25//! Both are reported as success. The count moves in BOTH directions, which is
26//! why no count-based check and no total-comparing parity oracle can see this.
27//!
28//! `BufferExtent::Complete` is the authoritative discriminator, exactly as it is
29//! for the row arm #3782 fixed: no further bytes can arrive, so a header that
30//! does not decode is truncation or corruption and both are DATA LOSS. On a
31//! `Window` the SAME condition is the ordinary straddle — a header split across
32//! the chunk boundary — and stays tolerant.
33
34//! # Reachable only from a CONFIRMED boundary (issue #3928 round 5)
35//!
36//! This arm is entered ONLY where the walk has been promised a partition starts:
37//! the block start (the caller's own offset 0), the byte after an
38//! `END_OF_PARTITION` the row loop just consumed, or an offset a
39//! `peek_is_partition_header` confirmed. That property is what makes the
40//! `Ready`-then-unparseable refusal below SAFE rather than merely justified, and
41//! it is maintained by the four breaks in `block_emit_windowed.rs` that leave the
42//! cursor at an UNCONFIRMED position, each of which now ENDS THE WALK instead of
43//! falling through to here:
44//!
45//! * the #954 row-body bound (finding B1) — nothing further was requested;
46//! * the tolerant ROW break — the straddle protocol, so the cursor is MID-ROW;
47//! * the three range-tombstone MARKER failures (finding I2) — the cursor is ON
48//!   the marker. These `return` the MARKER's own error at EVERY extent, which
49//!   delivers the same property a fortiori (a `return` cannot fall through to
50//!   here at all) and is issue #3721's decision, not this one's — see
51//!   "Reconciling #3721 and #3928" below.
52//!
53//! # Why that matters, measured
54//!
55//! `Ready` proves only that enough bytes for a CANDIDATE header exist at this
56//! offset — not that the offset IS a boundary. Readiness reads `data[1]` as the
57//! key length and never inspects byte 0, and any oa/da discriminator byte with
58//! bit 7 set that is not exactly `0x80` fails the full parse. So row payload
59//! classifies `Ready`-then-`Err` at a mid-row offset, and while the row break
60//! fell through to here, the (correct-at-a-boundary) unconditional refusal
61//! REJECTED HEALTHY WINDOWS: measured on the real `da` fixture
62//! `test_da.wide_table` with its own gates, **294096 of 1857615** healthy window
63//! prefixes refused, every one through this arm. The ASCII-payload `da` fixtures
64//! showed 0 of 57548 and 0 of 112255 — the arm is simply unreachable in them, so
65//! they could not have detected it.
66//!
67//! Both directions are pinned in `issue_3928_corrupt_header_refusal.rs`:
68//! `a_windowed_block_read_refuses_a_complete_but_structurally_invalid_header`
69//! (refuse at a boundary) and `no_healthy_window_prefix_is_ever_refused` (never
70//! refuse a healthy window).
71//!
72//! # Reconciling #3721 and #3928 (rebase onto PR #3814)
73//!
74//! Both issues are refuse-don't-swallow fixes to the SAME walk, and at the four
75//! breaks above they were written independently and appeared to disagree. They do
76//! not, once the two questions are separated:
77//!
78//! * **#3721 asks WHETHER a failure is reported to the caller.** Only it can
79//!   tell, and only at the site that holds the error: an
80//!   [`Error::ColumnDecode`] is a per-column decode failure the caller owns the
81//!   tolerance decision for (`column_decode_error::end_of_partition_or_bail`),
82//!   while a range-marker failure is corruption and never a terminator
83//!   (`range_marker_error`).
84//! * **#3928 asks WHERE a failure that is NOT reported leaves the cursor**, and
85//!   hence whether this arm may be entered from it.
86//!
87//! So they compose per site rather than competing:
88//!
89//! * the THREE MARKER sites `return` unconditionally (#3721). #3928's I2
90//!   invariant is satisfied *more* strictly than by its own proposed
91//!   `break 'partitions`, because a `return` ends the walk at every extent and
92//!   can never reach this arm. Gating those returns on `extent.is_complete()` —
93//!   which is what #3928 round 5 wrote, before #3721 landed — was MEASURED to
94//!   reintroduce #3721's defect: the scan passes `Window` even with the whole
95//!   partition buffered, so all three `d9_select_marker_parse_failure` cases went
96//!   back to `Ok` with the marker and every later row silently dropped. And
97//!   nothing #3928 measured argues the other way: all 294096 healthy-window
98//!   refusals above arrived through the ROW break, none through a marker site.
99//! * the ROW break keeps #3721's `end_of_partition_or_bail(..)?` (so a
100//!   `ColumnDecode` still reaches the caller — `issue_3721_bti_point_read_absence`
101//!   pins that) and then `break 'partitions` rather than a plain `break` (#3928),
102//!   because an `Ok` from that call establishes only "not `ColumnDecode`" and
103//!   consumes nothing: the cursor is where the failed row parse STARTED, which is
104//!   a boundary in neither direction.
105//!
106//! ## Residuals, both of them #3721's and both still open
107//!
108//! 1. A marker refusal is `Error::Corruption`, which
109//!    `column_decode_error::indexed_walk_falls_back` does not recognise (it
110//!    matches `is_column_decode` only), so an index-NARROWED read fails instead
111//!    of retracting. The fix is a TYPED retraction signal — matching message text
112//!    would violate the no-heuristics rule (#28) — not tolerance, which would
113//!    merely make the narrowed read silently short.
114//! 2. A `Window` that cuts a VALID marker's body is refused rather than treated
115//!    as the straddle it is. That IS decidable structurally, by the move #1741
116//!    made for headers (`partition_header_readiness`) applied to the marker's own
117//!    framing: every byte present and still failing is corruption, absent bytes
118//!    are a straddle. It is new parse-side machinery rather than a reconciliation
119//!    of two existing changes, so it is named here and not invented.
120//!
121//! Until (1) or (2) lands, the accepted direction at a marker is a conservative
122//! false refusal on a narrowed read — recoverable, and loud — over a silent short
123//! answer from `SELECT`, which is the defect itself.

128/// What the block-emit walk should do with the bytes at a candidate partition
129/// start.
130pub(in crate::storage::sstable::reader::parsing::row_decoder) enum HeaderStep {
131    /// A structurally-valid header: the partition key, the offset of the first
132    /// row/marker, and the partition-level deletion.
133    Parsed(RowKey, usize, Option<(i64, i32)>),
134    /// Fewer bytes remain than even a header needs. Only reachable on a
135    /// [`BufferExtent::Window`] (a `Complete` buffer refuses instead), where it
136    /// is the ordinary end of the window.
137    EndOfBlock,
138    /// The header is undecodable and more bytes may still arrive, so the caller
139    /// skips ONE byte and re-tries. Only reachable on a
140    /// [`BufferExtent::Window`].
141    Resync,
142}
143
144impl V5CompressedLegacyParser {
145    /// Decode the partition header at `offset`, or say what the walk should do
146    /// instead.
147    ///
148    /// Tolerance is decided by ONE piece of state, [`HeaderTolerance`], which the
149    /// caller owns and threads in: "can a byte still arrive, or is this walk's
150    /// progress no longer attributable?" See that type for why it replaced the
151    /// per-site byte count plus per-call boolean this arm used to consult, and
152    /// for the two edges each of those got wrong.
153    ///
154    /// Two consequences worth stating here, at the arm:
155    ///
156    /// * partition 0's own header is refused on a BOUNDED call too. A row-body
157    ///   window supplied at the call is not yet an uncertainty; reaching its
158    ///   endpoint is, and `HeaderTolerance::bounded_out` is called there
159    ///   (finding C2).
160    /// * `row_body_window.is_some() && partition_index == 0` — which reads as
161    ///   that property and was the obvious patch — is NOT what this does, and
162    ///   was measured to be wrong: `partition_index` is incremented at the END of
163    ///   the windowed partition's arm, so at the very offset `body_end` leaves
164    ///   behind it already reads `1`, and the refusal fired on correct input
165    ///   (`regression_1741c_tests::range_tombstone_before_slice_is_shadowed_on_windowed_read`,
166    ///   observed: `only 1 byte(s) remain … (partition=1)`, the byte being that
167    ///   partition's own `END_OF_PARTITION` marker). Tracking the STOP rather
168    ///   than inferring it from a partition index is what makes both edges right
169    ///   at once.
170    pub(in crate::storage::sstable::reader::parsing::row_decoder) fn block_partition_header(
171        &self,
172        data: &[u8],
173        offset: usize,
174        tolerance: HeaderTolerance,
175        partition_index: usize,
176    ) -> Result<HeaderStep> {
177        let refuse = tolerance.refuses();
178        // Issue #3928 fix round 3 (B2) — the oa/da DeletionTime SIZING RULE is
179        // CALLED, never re-derived.
180        //
181        // This arm used to compute its own minimum,
182        // `if has_uint_deletion_time() { 1 } else { 12 }`, with no look at the
183        // discriminator. That is the PRE-#1741 rule: only the LIVE sentinel
184        // (`0x80`) is one byte, and a DELETED oa/da partition carries the full
185        // 12-byte form. So a legitimate deleted header STRADDLING a
186        // `BufferExtent::Window` passed the 1-byte minimum, failed the full
187        // parse, and returned `Resync` — discarding a header byte of HEALTHY
188        // data, the direction `buffer_extent.rs` records as being as much a
189        // defect as a swallow.
190        //
191        // #1741 fixed exactly that, inside `partition_header_readiness`, which
192        // peeks `data[2 + key_len]` to size the form and answers `Incomplete`
193        // when the discriminator itself is absent. The two sliding drivers route
194        // through it; this arm did not, so the two implementations of one rule
195        // DRIFTED — the driver path got the fix and this one kept the bug. It now
196        // asks the same classifier, and the pair is pinned together in
197        // `regression_1741k_tests.rs`.
198        //
199        // The classifier also owns the key-length limits, so this arm no longer
200        // carries its own copy of the 255-byte cap.
201        //
202        // `remaining` survives for the DIAGNOSTICS only: no decision is made from
203        // a byte count (fix round 2), and the sub-two-byte case an earlier
204        // revision handled separately is simply `Incomplete` to the classifier.
205        let remaining = data.len().saturating_sub(offset);
206        // `get(..).unwrap_or_default()` rather than `&data[offset..]`: this is
207        // reachable from `row_decoder` now, so an out-of-range offset must read
208        // as an empty buffer (which the classifier answers `Incomplete`) and
209        // never as a slice panic.
210        let head = data.get(offset..).unwrap_or_default();
211        match self.partition_header_readiness(head) {
212            // The header — or, for an oa/da DELETED partition, its full 12-byte
213            // DeletionTime — is not entirely present.
214            //
215            // On a WINDOW that is the ordinary straddle: the walk ends here and
216            // the caller refills. On an UNBOUNDED, proven-complete buffer no
217            // further bytes can arrive, so the partition Cassandra wrote here was
218            // truncated away and reporting a clean end of block would DROP it —
219            // the same verdict the drivers' arm reaches from the same
220            // classification (finding C1), and the reason the two stitched walks
221            // agree (`data_access/mod.rs:249` vs `:288` hand both the SAME
222            // stitched `Complete` buffer).
223            PartitionHeaderReadiness::Incomplete => {
224                if refuse {
225                    return Err(undecodable_partition_header(
226                        offset,
227                        &format!(
228                            "the header is INCOMPLETE — {remaining} byte(s) remain, too few to \
229                             hold its declared key AND the DeletionTime for its live/deleted \
230                             form (partition={partition_index}){}",
231                            structural_note_at(data, offset)
232                        ),
233                    ));
234                }
235                tracing::debug!(
236                    "V5CompressedLegacy: partition header at offset {offset} is INCOMPLETE \
237                     ({remaining} byte(s) remain), stopping — tolerated because {}",
238                    tolerance.why_tolerant()
239                );
240                return Ok(HeaderStep::EndOfBlock);
241            }
242            // A zero or over-long declared key length — decidable from two bytes,
243            // so no further byte can change the verdict.
244            //
245            // NOTE: no heuristic validation of `flags` (issues #258, #28); the
246            // classifier reads the LENGTH only. Issue #164's concern — that a
247            // block's trailing bytes must not be assumed to begin another
248            // partition just because `offset < data.len()` — is answered by this
249            // arm's three-way classification rather than by a hand-rolled
250            // minimum.
251            PartitionHeaderReadiness::Malformed => {
252                let detail = format!(
253                    "CQLite READ a key length of {} here, which it rejects as zero or \
254                     over-long, with {remaining} byte(s) available (partition={partition_index}){}",
255                    head.get(1).copied().unwrap_or(0),
256                    structural_note_at(data, offset)
257                );
258                if refuse {
259                    return Err(undecodable_partition_header(offset, &detail));
260                }
261                tracing::warn!(
262                    "V5CompressedLegacy: Skipping malformed partition header at offset {offset} \
263                     ({detail}) — resynchronising because {}",
264                    tolerance.why_tolerant()
265                );
266                return Ok(HeaderStep::Resync);
267            }
268            // Every header byte is present, so the full parse below cannot fail
269            // from truncation.
270            PartitionHeaderReadiness::Ready => {}
271        }
272
273        match self.parse_partition_header_full(data, offset) {
274            Ok((key, next_offset, deletion)) => Ok(HeaderStep::Parsed(key, next_offset, deletion)),
275            Err(e) => {
276                // Issue #3928 fix round 4 — REPORTED UNCONDITIONALLY, at every
277                // extent, exactly as the sliding drivers report it.
278                //
279                // `Ready` is an AFFIRMATIVE guarantee from
280                // `partition_header_readiness` that every header byte is present:
281                // the key length, the key, and the `DeletionTime` for its
282                // live/deleted form, sized by PEEKING the discriminator (#1741).
283                // So **a `Ready` header cannot straddle**, and that is what
284                // decides this arm rather than the extent.
285                //
286                // The tolerant break here used to be justified by the point
287                // readers' straddle protocol. That justification does not reach
288                // this arm: the break protects a straddling ROW, and AC1 licenses
289                // tolerance only where "a header can legitimately straddle" —
290                // which a `Ready` header provably cannot. No later chunk can
291                // repair an invalid oa/da deletion-time discriminator, so
292                // resynchronising past it drops a real partition and can invent
293                // misaligned ones.
294                //
295                // Measured on the real `da` fixture with its first partition's
296                // discriminator flipped to `0xFF` (a byte Cassandra's own
297                // `DeletionTime.Serializer.deserialize` throws on) parsed under a
298                // `BufferExtent::Window`: `Ok` with 401 of 468 rows — **180 LOST
299                // and 113 FABRICATED**. Pinned by
300                // `a_windowed_block_read_refuses_a_complete_but_structurally_invalid_header`.
301                //
302                // The corpus cannot evidence this arm in either direction (AC3's
303                // counters record 0 arrivals here across 126 tables), which is
304                // why the absence of a measured loss was never a reason to
305                // tolerate it.
306                //
307                // This arm composes NO message: `e` is `scan_partition_header`'s
308                // own, and after `Ready` it can realistically only be the
309                // `oa`/`da` invalid-IS_LIVE-byte rejection, which does not rest
310                // on the key-length model — so no #3999 caveat is owed here.
311                // Rewording that error's own text belongs to #3999 with the model
312                // it asserts.
313                Err(e)
314            }
315        }
316    }
317}

319/// The refusal a partition header raises where the caller has PROVEN no further
320/// bytes can arrive.
321///
322/// Deliberately NOT shared with `partition_driver.rs` /
323/// `compaction_stream.rs`, which reach the same decision from `at_final_chunk`
324/// and own their own `ParseStep`/`PartitionStreamStep` vocabularies — the same
325/// call the #3782 row arm made when it spelled the rule out in each driver
326/// rather than inventing one abstraction over three different advance
327/// protocols. What must not diverge is the DECISION, and that is one predicate
328/// per driver over its own authoritative signal.
329fn undecodable_partition_header(offset: usize, detail: &str) -> Error {
330    Error::corruption(format!(
331        "V5CompressedLegacy: refusing an undecodable partition header at offset {offset} \
332         ({detail}); this walk is UNBOUNDED over a PROVEN-COMPLETE buffer, so no further \
333         bytes can arrive to finish this header. Skipping a byte to resynchronise would \
334         DROP this partition and can land on misaligned bytes that parse as a plausible \
335         header, INVENTING a partition that does not exist (issue #3928). \
336         NOTE (#3999): CQLite reads the partition key length as ONE byte after a 'flags' \
337         byte, while Cassandra writes an unsigned 2-byte big-endian length and no flags \
338         byte (SortedTablePartitionWriter.start -> ByteBufferUtil.writeWithShortLength), \
339         so the two models agree only for keys under 256 bytes; for a longer key this \
340         refusal may be CQLite's model and not corruption."
341    ))
342}

344/// Issue #3928 — name the leading byte's STRUCTURAL class when it is one this arm
345/// should never have been handed.
346///
347/// Round 1 (I2) added this because the row loop broke with `offset` still ON a
348/// range-tombstone marker it could not parse or feed, and the outer partition
349/// loop then re-entered HERE — so the diagnostic read "undecodable partition
350/// header" for a MARKER failure and sent the next reader to the wrong arm. That
351/// route is GONE as of round 5: all three marker sites now `return` the marker's
352/// own error at every extent (issue #3721), so this arm is reachable only from a
353/// CONFIRMED partition boundary.
354///
355/// The notes are kept because a boundary can still legitimately be REACHED with
356/// a marker or END_OF_PARTITION byte at it on malformed input (two consecutive
357/// end markers, say), and naming that is still the difference between one read
358/// and a debugging session. What they no longer describe is a fall-through.
359fn structural_note_at(data: &[u8], offset: usize) -> &'static str {
360    let Some(&leading) = data.get(offset) else {
361        return "";
362    };
363    if V5CompressedLegacyParser::is_end_of_partition(leading) {
364        " — NOTE: this leading byte is an END_OF_PARTITION marker (0x01), so the walk \
365         re-entered the header arm at a marker rather than at a partition start"
366    } else if V5CompressedLegacyParser::is_range_tombstone_marker(leading) {
367        " — NOTE: this leading byte carries IS_MARKER, i.e. it is a RANGE-TOMBSTONE \
368         marker and not a partition header. Since #3928 round 5 the row loop's marker \
369         failures can no longer leave the cursor here (they return the marker's own error \
370         at every extent), so this indicates a partition BOUNDARY whose first byte is a \
371         marker — malformed input, not a fall-through"
372    } else {
373        ""
374    }
