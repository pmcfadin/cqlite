1//! What a partition row loop does when a range-tombstone MARKER cannot be turned
2//! into output faithfully (issue #3721) — either because it is FRAMED and
3//! unrepresentable ([`range_marker_refused`]) or because it cannot be PARSED at
4//! all on the final chunk ([`range_marker_unparseable`] +
5//! [`unparseable_marker_at_final_chunk`]).
6//!
7//! # The defect this module replaces
8//!
9//! [`super::column_decode_error`] removed the same shape one structural level
10//! down — a per-COLUMN decode failure handled with a bare `break`, so the row was
11//! assembled from the cells gathered so far and returned as `Ok`. The MARKER sites
12//! were the same construct:
13//!
14//! ```text
15//! block_emit.rs           if sh.feed_range_marker(..).is_err() { break; }
16//! block_emit_windowed.rs  if let Err(e) = sh.feed_range_marker(..) { .. break; }
17//! timestamp_policy.rs     if sh.feed_range_marker(..).is_err() { MarkerOutcome::Stop }
18//! compaction.rs           _ => { /* Unknown bound kind: skip it */ }   (#3808)
19//! ```
20//!
21//! # The SECOND census, one arm over — the marker-PARSE arms (roborev job 78)
22//!
23//! Fixing the arms above left their SIBLING arm — the one taken when the marker
24//! cannot be PARSED at all — answering with the framing terminator:
25//!
26//! ```text
27//! timestamp_policy.rs:148/156   Err(_) => MarkerOutcome::Stop
28//! block_emit.rs:149/157         Err(_) => break
29//! block_emit_windowed.rs:385/399 Err(e) => { tracing::debug!(..); break; }
30//! ```
31//!
32//! Every one of those is a SUCCESSFUL, incomplete partition on the user-facing
33//! read path: the marker and every later row of the partition vanish and `SELECT`
34//! returns `Ok`. There is no downstream guard —
35//! [`super::block_emit`]'s `partition_complete` flag gates only the #3095
36//! static-only emission and never rejects an incomplete partition.
37//!
38//! The rationale that had been written beside them ("a genuine framing
39//! terminator") is the SAME one this issue already disproved for
40//! `compaction.rs`. Two facts settle it, and neither is a byte pattern:
41//!
42//! 1. the branch is entered only when `is_range_tombstone_marker(data[offset])`,
43//!    with `is_end_of_partition` handled SEPARATELY one branch above — so a parse
44//!    failure here is abnormal data, never an end-of-partition signal. Authority:
45//!    `UnfilteredSerializer.deserializeOne` (cassandra-5.0.8:458-483) ends a
46//!    partition on `isEndOfPartition(flags)` ALONE (returning `null`); the marker
47//!    kind then deserializes the bound + `deserializeMarkerBody`, whose failure
48//!    throws `IOException` and propagates — Cassandra never converts it into
49//!    "the partition ended", and throws explicitly on corrupt flags;
50//! 2. in `block_emit` the ROW `Err` arm already routes through
51//!    [`super::column_decode_error::end_of_partition_or_bail`] while the MARKER
52//!    arm 120 lines above it just `break`s — rows protected, markers not, inside
53//!    one function.
54//!
55//! Fix 1 of this issue (a marker body must be consumed EXACTLY,
56//! `row_framing::parse_range_tombstone_marker_with_ldt`) makes that hole MORE
57//! reachable, since a body-size mismatch now returns `Err`.
58//!
59//! ## What replaces it, by path kind
60//!
61//! * **buffered** (`parse_block_emit_with_metadata`, `parse_block_emit_windowed`)
62//!   — the whole block is already materialised, so NO refill is possible and the
63//!   failure is unambiguously corruption:
64//!   [`unparseable_marker_in_buffered_block`];
65//! * **streaming policy** ([`super::timestamp_policy`], driven by
66//!   `drive_partition_sliding`, which holds `at_final_chunk`) — the cause is
67//!   carried in [`super::partition_driver::MarkerOutcome::Unparseable`] and the
68//!   DRIVER decides: `NeedMore` on a non-final chunk (unchanged behaviour, since a
69//!   marker body may simply straddle the window boundary) and the preserved cause
70//!   propagated on the final chunk, via
71//!   [`unparseable_marker_at_final_chunk`].
72//!
73//! `MarkerOutcome::Stop` — the variant that expressed "this parse failure IS a
74//! framing terminator" — is GONE with those arms rather than left available: it
75//! had exactly one meaning, that meaning was wrong for every real policy, and a
76//! variant a future policy could reach for is how this defect was written twice.
77//! There is now ONE answer to a marker parse failure: carry the cause and let
78//! whoever holds the finality decide.
79//!
80//! ## Two sites deliberately UNCHANGED, and why
81//!
82//! * `block_emit`'s DELTA-SCAN loop (`:462`) already propagates with `?`,
83//!   wrapping (not discarding) the cause;
84//! * `block_emit_windowed::prime_shadow_before_window` (`:750`) returns `false`,
85//!   which means "cannot prime, decode the FULL partition instead" — a fail-safe
86//!   fallback that drops no rows. The same marker is re-encountered by the full
87//!   decode, where the arms above now refuse it. Turning it into an error would
88//!   remove a legitimate fallback and change nothing about the outcome.
89//!
90//! The fourth site is the COMPACTION policy, and it is the most consequential of
91//! the four (issue #3808): its rows are WRITTEN, so omitting an unrepresentable
92//! deletion marker resurrects the rows that marker shadowed DURABLY, on disk —
93//! and it was the lone fail-open reader of that byte, since
94//! [`super::partition_shadow::PartitionShadow::feed_range_marker`] and delta-scan
95//! `block_emit` already refuse it.
96//!
97//! Each `break`/`Stop` left the partition's row loop and the read then reported
98//! `Ok` — so the marker AND every remaining row of that partition silently
99//! vanished from a successful `SELECT`. `block_emit_windowed`'s instance is on the
100//! point/slice read path, so a clustering-slice query was the worst-affected
101//! surface.
102//!
103//! # Why this is corruption and NOT a boundary — the discriminator
104//!
105//! Two facts, both established at the call site, neither inferred from bytes:
106//!
107//! 1. **The marker is already FRAMED.** These handlers run only inside the `Ok`
108//!    arm of `parse_range_tombstone_marker_full`, which has bound a valid
109//!    `next_offset`. The partition body demonstrably CONTINUES there; the loop
110//!    threw that binding away. So this is not end-of-data, and it is not the
111//!    "no further row parses here" signal the loops use to detect the end of a
112//!    partition body (that signal is a PARSE failure, which yields no resume
113//!    point — see [`super::column_decode_error::end_of_partition_or_bail`]).
114//! 2. **Each site fails on exactly ONE condition** — a bound kind the
115//!    read-side shadow FSM has no faithful representation for
116//!    ([`super::partition_shadow::PartitionShadow::feed_range_marker`]'s
117//!    `unknown =>` arm, the only `Err` it returns; the compaction policy's own
118//!    `unknown =>` arm is the same predicate over the same byte). Every kind a
119//!    well-formed marker can carry is represented; a kind outside that set is
120//!    evidence the cursor or the data is wrong. `row_framing` returns the bound
121//!    kind UNVALIDATED, so an arbitrary byte reaches these matches and giving it a
122//!    permissive default meaning is the inference issue #28 forbids.
123//!
124//! # Why it is not skippable either
125//!
126//! Advancing to `next_offset` and continuing is worse than either alternative: an
127//! unrepresentable bound may OPEN a deletion range covering the rows that follow,
128//! so a read that ignores it emits rows a Cassandra `SELECT` hides — deleted data
129//! resurrected and reported as success. Guessing what the bound covers is exactly
130//! the byte-pattern inference issue #28 forbids. So the condition is FATAL and is
131//! propagated to the caller of the read.
132//!
133//! # The second condition: a marker that cannot be PARSED (roborev job 16)
134//!
135//! The discriminator above turns on the marker being FRAMED. A marker that does
136//! not parse has no resume offset, so it is not that case — and it was handled by
137//! the (now REMOVED) `MarkerOutcome::Stop`, which the drivers converted on the
138//! FINAL chunk into a successful partition completion. For the COMPACTION
139//! policy that is the same durable harm wearing different clothes: a corrupt or
140//! truncated tombstone is dropped and the output SSTable is still written, so the
141//! rows it shadowed come back.
142//!
143//! The discriminator there is the CHUNKING STATE the driver already holds, never a
144//! byte pattern (issue #28):
145//!
146//! * a **non-final** chunk may legitimately have cut the marker body in half, so
147//!   the answer is `NeedMore` — the one explanation a refill can fix;
148//! * on the **final** chunk no further bytes can arrive, so the parse failure is
149//!   corrupt/truncated data and is PROPAGATED, carrying the parser's own cause.
150//!
151//! # Not `Error::ColumnDecode`
152//!
153//! [`crate::error::Error::ColumnDecode`] exists so the row loops can tell a
154//! per-column failure apart from end-of-partition, and the windowed callers
155//! (`column_decode_error::indexed_walk_falls_back`) retract the index optimization
156//! on it. Neither applies here: the failure is not a column, and it is propagated
157//! from the marker arm DIRECTLY rather than through the end-of-partition decision,
158//! so no variant match is needed to disambiguate it. It is reported as
159//! [`crate::error::Error::Corruption`], wrapping the shadow FSM's own message.
160

163/// Build the error a partition row loop propagates when a FRAMED range-tombstone
164/// marker cannot be represented faithfully (issue #3721), and record the condition
165/// at `warn!` — mirroring
166/// [`super::column_decode_error::column_decode_failure`], so an operator sees the
167/// partition, the marker's offset and the resume point that was discarded even
168/// when the caller only surfaces the top-level message.
169///
170/// `offset` is the marker's own offset; `resume_offset` is the `next_offset` the
171/// enclosing `Ok` arm bound — reported precisely because its presence is what
172/// proves this is not the end of the partition body.
173///
174/// `partition` names the partition however the calling loop can: the block loops
175/// count partitions within the block and pass an INDEX, while the sliding driver
176/// decodes one partition per call and has only its KEY. A `&dyn Display` keeps one
177/// helper (and so one message) for both rather than an index the driver would have
178/// to invent.
179pub(super) fn range_marker_refused(
180    cause: Error,
181    partition: &dyn std::fmt::Display,
182    offset: usize,
183    resume_offset: usize,
184) -> Error {
185    tracing::warn!(
186        "V5CompressedLegacy: partition {} range-tombstone marker at offset {} is FRAMED (body \
187         continues at offset {}) but cannot be represented: {}",
188        partition,
189        offset,
190        resume_offset,
191        cause
192    );
193    Error::corruption(format!(
194        "range-tombstone marker at offset {offset} of partition {partition} could not be \
195         represented faithfully; the marker is framed and the partition body continues at offset \
196         {resume_offset}, so this is corrupt data and not the end of the partition — truncating \
197         here would drop the tombstone AND every later row of the partition from a successful \
198         read (issue #3721): {cause}"
199    ))
200}

202/// Build the error a policy PRESERVES in [`super::partition_driver::MarkerOutcome::Unparseable`]
203/// when a range-tombstone marker cannot be PARSED at all (issue #3721, roborev
204/// job 16) — the sibling of [`range_marker_refused`] for the case where no resume
205/// offset exists.
206///
207/// Deliberately does NOT log: at this point the failure may still be an ordinary
208/// window boundary (the marker body straddling a non-final chunk), which is the
209/// hot path of a chunk-stitched compaction scan. Only the driver knows whether more
210/// data is coming, so the report is emitted there — see
211/// [`unparseable_marker_at_final_chunk`]. Constructing the error eagerly is what
212/// keeps the parser's own diagnostic (`cause`) available to that decision instead of
213/// being discarded and re-synthesised.
214pub(super) fn range_marker_unparseable(
215    cause: Error,
216    partition: &dyn std::fmt::Display,
217    offset: usize,
218) -> Error {
219    Error::corruption(format!(
220        "range-tombstone marker at offset {offset} of partition {partition} could not be PARSED, \
221         so no resume point exists (issue #3721): {cause}"
222    ))
223}

225/// The buffered counterpart of [`unparseable_marker_at_final_chunk`] (issue
226/// #3721, roborev job 78): the whole block is ALREADY materialised in `data`, so
227/// finality is established by the BUFFER rather than by a driver's chunking state
228/// and no refill can ever complete this marker.
229///
230/// Composes [`range_marker_unparseable`] so the cause chain and its wording live
231/// in one place, and logs at `warn!` — unlike the streaming builder, where the
232/// condition may still be an ordinary window boundary, here it is a finding the
233/// moment it is constructed.
234pub(super) fn unparseable_marker_in_buffered_block(
235    cause: Error,
236    partition: &dyn std::fmt::Display,
237    offset: usize,
238) -> Error {
239    let inner = range_marker_unparseable(cause, partition, offset);
240    tracing::warn!(
241        "V5CompressedLegacy: range-tombstone marker is unparseable in a FULLY BUFFERED block, \
242         so it cannot be a window boundary: {}",
243        inner
244    );
245    Error::corruption(format!(
246        "the whole block is already buffered, so no further data can complete this \
247         range-tombstone marker: it is corrupt or truncated, not a chunk boundary. Ending the \
248         partition here would report SUCCESS while dropping the tombstone AND every later row \
249         of the partition from the read (issue #3721): {inner}"
250    ))
251}

253/// Finish the [`range_marker_unparseable`] error at the point the driver has
254/// established that the marker's bytes are ALL the bytes there are: the scan is on
255/// its FINAL chunk, so no refill can complete the marker and "unparseable" is
256/// corrupt or truncated data rather than a window boundary.
257///
258/// This is where the condition is reported (`warn!`), mirroring
259/// [`range_marker_refused`] — the non-final path builds the same error and drops
260/// it, because there it is not yet a finding.
261///
262/// BOTH streaming policies reach it (roborev job 78), so the message names both
263/// harms and asserts neither exclusively: a silently truncated `SELECT` on the
264/// read path, and a tombstone missing from WRITTEN output on the compaction path.
265///
266/// The distinction is taken from the driver's own `at_final_chunk` flag — the
267/// chunking state the caller already holds — and never from inspecting bytes to
268/// guess whether more data exists (issue #28).
269pub(super) fn unparseable_marker_at_final_chunk(cause: Error) -> Error {
270    tracing::warn!(
271        "V5CompressedLegacy: range-tombstone marker is unparseable on the FINAL chunk of the \
272         scan, so it cannot be a window boundary: {}",
273        cause
274    );
275    Error::corruption(format!(
276        "the scan is at its FINAL chunk, so no further data can complete this range-tombstone \
277         marker: it is corrupt or truncated, not a chunk boundary. Completing the partition here \
278         would report SUCCESS while dropping the tombstone AND every later row of the partition — \
279         from a `SELECT` on the read path, and from WRITTEN output on the compaction path, where \
280         the rows it shadows come back durably, on disk (issue #3721): {cause}"
281    ))
