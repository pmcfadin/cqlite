1//! Sizing constants for [`QueryRowStream`](super::QueryRowStream) and the
2//! read-ahead bounds derived from them (issue #3384).
3//!
4//! Split out of `query_rows.rs` under the campsite rule (epic #1116): the
5//! derivation below is mostly PROSE — four buffer terms, a precondition, and the
6//! record of how the bound was once wrong — and it pushed the driver file over
7//! the 800-line threshold. Keeping it beside the driver would mean either
8//! deleting the reasoning or growing an over-threshold file, and the reasoning is
9//! the part that stops the bound silently going wrong again.
10//!
11//! Everything here is `const`; there is no behaviour in this file.
12
13use super::super::super::scan_stream_windowed::{BATCH_EMIT_ROWS, MAX_INFLIGHT_BATCH_ROWS};
14use super::super::sequential::batched_scan_stream::batched_channel_capacity;
15
16/// Rows accumulated before a batch is handed to the consumer. Matches the
17/// batched scan surface's emit granularity (issue #1592): one cross-thread
18/// handoff per batch instead of per row.
19pub(crate) const QUERY_ROWS_PER_BATCH: usize = 128;
20
21/// Batches the bounded handoff channel may hold. Resident rows on this channel
22/// are therefore bounded by [`QUERY_ROWS_MAX_RESIDENT_ROWS`] plus the partition
23/// currently being decoded — independent of table size.
24pub(crate) const QUERY_ROWS_CHANNEL_BATCHES: usize = 4;
25
26/// Rows the query-row handoff channel can hold in flight ahead of a consumer that
27/// has stopped reading — [`QUERY_ROWS_CHANNEL_BATCHES`] channel-resident batches
28/// plus the ONE batch a producer parked in `SyncSender::send` still owns (a
29/// blocked send moves the value only on success), each of at most
30/// [`QUERY_ROWS_MAX_HANDOFF_BATCH_ROWS`] rows. The batch currently being
31/// accumulated is not a further term: once it reaches that size it BECOMES the
32/// parked send, and a parked producer accumulates no further rows.
33///
34/// Crate-internal (`pub` for its doc links, not re-exported to the crate root):
35/// the bound OUTSIDE callers need is [`QUERY_ROWS_MAX_READ_AHEAD`].
36///
37/// This bounds the HANDOFF CHANNEL ALONE. It is NOT the walk's read-ahead: the
38/// producer thread pulls from an inner batched scan stream that has bounded
39/// buffers of its own, so a cancelled or abandoned walk can decode up to
40/// [`QUERY_ROWS_MAX_READ_AHEAD`] rows — not this many — after its consumer
41/// stops. Use that constant for "how far can an abandoned walk run"; use this one
42/// only when reasoning about the channel itself.
43pub const QUERY_ROWS_MAX_RESIDENT_ROWS: usize =
44    QUERY_ROWS_MAX_HANDOFF_BATCH_ROWS * (QUERY_ROWS_CHANNEL_BATCHES + 1);
45
46/// The largest batch either arm can put on the handoff channel.
47///
48/// The two arms size their batches DIFFERENTLY, and taking the smaller of the two
49/// is how the exported read-ahead bound came to understate the full-ring arm by
50/// a factor of two (roborev, issue #3384):
51///
52/// * the token-bounded arm accumulates through [`BatchSink`] and emits at
53///   [`QUERY_ROWS_PER_BATCH`] (128) rows;
54/// * the full-ring arm ([`drive_full_scan_rows`]) does NOT re-chunk — `emit_rows`
55///   forwards the inner batched scan stream's batch VERBATIM, and those are capped
56///   at [`BATCH_EMIT_ROWS`] (256).
57///
58/// A bound that must hold on BOTH arms therefore has to use the MAXIMUM, not
59/// either arm's own figure.
60pub(crate) const QUERY_ROWS_MAX_HANDOFF_BATCH_ROWS: usize =
61    if BATCH_EMIT_ROWS > QUERY_ROWS_PER_BATCH {
62        BATCH_EMIT_ROWS
63    } else {
64        QUERY_ROWS_PER_BATCH
65    };
66
67/// `buffer_size` the full-ring arm ([`drive_full_scan_rows`]) hands to the inner
68/// batched scan stream. Named so [`QUERY_ROWS_MAX_READ_AHEAD`] is derived
69/// from the SAME value the call site passes, never a restated copy of it.
70pub(crate) const QUERY_ROWS_FULL_SCAN_BUFFER_ROWS: usize =
71    QUERY_ROWS_PER_BATCH * QUERY_ROWS_CHANNEL_BATCHES;
72
73/// Upper bound, IN ROWS, on what a [`QueryRowStream`] producer can decode AHEAD of its
74/// consumer — and therefore on how much work an ABANDONED or CANCELLED walk can
75/// still do after the consumer stops reading. A CONSTANT: it does not scale with
76/// the table, so a walk over a million partitions abandoned after one row decodes
77/// at most this many more rows, not the rest of the table.
78///
79/// Every term is a bounded buffer between the disk and the consumer, on the
80/// full-ring arm ([`drive_full_scan_rows`], the deepest of the two arms):
81///   1. [`QUERY_ROWS_MAX_RESIDENT_ROWS`] — this stream's handoff channel plus the
82///      producer's parked send.
83///   2. The inner batched scan stream's public channel:
84///      [`batched_channel_capacity`] batches of up to
85///      [`BATCH_EMIT_ROWS`] rows.
86///   3. The one inner batch [`drive_full_scan_rows`] has `recv`'d and still owns
87///      while parked handing it on (up to [`BATCH_EMIT_ROWS`] rows).
88///   4. [`MAX_INFLIGHT_BATCH_ROWS`] — the windowed scan's own batching subsystem
89///      (pending batch + bounded batch channel + producer parked in `send`).
90///
91/// # What it does NOT cover
92///
93/// * The ONE partition currently being decoded: the windowed scan materializes a
94///   confirmed partition in `scratch` before batching it, so a table with wide
95///   partitions adds a `max_partition_size` term on top (the pre-existing #1156
96///   term, see [`MAX_INFLIGHT_BATCH_ROWS`]'s docs).
97/// * Anything resident in the CONSUMER downstream of this stream — a Flight
98///   producer's own Arrow batches, for instance, are bounded by that consumer's
99///   own budget, not by this constant.
100/// * **Regions that decode to NO emitted rows.** This is a PRECONDITION, not a
101///   footnote (roborev, issue #3384). The full-ring arm observes cancellation
102///   only BETWEEN batches it receives from the inner scan, because
103///   `scan_stream_batched_admitted` is not handed the child cancel flag and does
104///   not poll one internally. So the bound holds while decoded partitions keep
105///   YIELDING rows — every decoded partition then pushes the channel toward the
106///   parked state in which cancellation is observed. Over a stretch that survives
107///   nothing (all tombstoned, or all TTL-expired at the read clock) the inner scan
108///   emits no batch, the producer never parks, and it can decode past this bound —
109///   in the limit, to the end of the table. Tracked as a real cancellation gap in
110///   the read path, NOT merely a documentation caveat: see issue #3428.
111/// * **Eager materialization inside a single decode step.** The bound counts rows
112///   RESIDENT IN THE PIPELINE'S BOUNDED BUFFERS, and the work probe it is asserted
113///   against (`work_counters::stream_walk_partitions_parsed`) advances as entries
114///   are ITERATED — which is backpressured, hence bounded. It does NOT bound work
115///   done eagerly *inside* one step before any iteration begins (roborev, issue
116///   #3384): `parse_batched_block` materializes a whole block's entries at once,
117///   and for a format whose data section is one block that is the whole table;
118///   `bti_scan_with_metadata` on the `da` path is materializing too. So read this
119///   constant as *"rows that can be handed onward after the consumer leaves"*, not
120///   as *"CPU and memory an abandoned walk can still spend"*. The two coincide on
121///   the incremental block-iteration path and diverge on the materializing ones.
122pub const QUERY_ROWS_MAX_READ_AHEAD: usize = QUERY_ROWS_MAX_RESIDENT_ROWS
123    + batched_channel_capacity(QUERY_ROWS_FULL_SCAN_BUFFER_ROWS) * BATCH_EMIT_ROWS
124    + BATCH_EMIT_ROWS
125    + MAX_INFLIGHT_BATCH_ROWS;
