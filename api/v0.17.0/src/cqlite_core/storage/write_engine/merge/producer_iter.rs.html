2//!
3//! PURE CODE MOTION out of `merge/mod.rs` (issue #3139): that file is ~13.5k
4//! lines, far over the ~800-line source campsite target (epic #1116). Nothing
5//! here changed behaviourally — the moved items are byte-identical to their

9//! This module owns the PATH-BASED streaming producer shape:
10//! - [`SSTableRowIteratorAdapter`] — the bounded-channel adapter that turns an
11//!   async `SSTableReader` into a sync [`SSTableRowIterator`],
12//! - its constructor + producer-thread body (`open` / `producer_thread`),
13//! - the consumer side ([`SSTableRowIterator`] impl) and the cancel-aware

22//! gauge accounting this module only *calls* lives in
23//! [`channel_depth`](super::channel_depth).
24//!
25//! Issue #3120 CLOSED the defect this module's header used to warn about (a
26//! producer thread that UNWINDS being indistinguishable from an exhausted run):
27//! completion is now an explicit [`MergeMsg::Done`] terminator and this adapter's
28//! [`RunState`] makes "receiver/verdict gone, so assume exhausted" unrepresentable.

41/// Whether this adapter's producer run has been PROVEN finished, proven failed,
42/// or is of unknown standing (issue #3120).
43///
44/// The point of the type is that a verdict can never be DOWNGRADED to "clean end
45/// of input" by accident. Before this issue there were two silent routes to
46/// `None`: a channel disconnect (which an unwinding producer is
47/// indistinguishable from) and a `self.receiver.as_ref()?`. Both are now folded
48/// into this state, and `None` is reachable ONLY from [`RunState::Finished`].
49#[cfg(feature = "write-support")]
50pub(super) enum RunState {
51    /// No terminator observed yet: the producer may still send.
52    Streaming,
53    /// The producer sent [`MergeMsg::Done`] — the ONLY proof of a clean,
54    /// COMPLETE run, and therefore the only state from which
55    /// [`SSTableRowIterator::next`] may report end of input.
56    Finished,
57    /// The producer sent a terminal [`MergeMsg::Failed`], already reported once.
58    ///
59    /// STICKY, and it keeps the payload so a repeat poll re-reports the IDENTICAL
60    /// error instead of degrading to `None`. That matters because
61    /// `RunReader::refill_buffer` propagates our `Err` but keeps NO sticky error
62    /// of its own: a consumer that swallowed the error and advanced again would
63    /// otherwise see a dead producer downgraded to a clean end of input — issue
64    /// #3120 reintroduced inside its own fix, with no test failing.
65    Failed(MergeProducerError),
66    /// STICKY: the channel disconnected with NO terminator, or the receiver was
67    /// gone when a poll arrived. The verdict is "unknown, therefore TRUNCATED",
68    /// so every subsequent poll re-reports the error and never `None`.
69    ///
70    /// Deliberately NOT #3106's non-sticky `terminated` flag, which returns
71    /// `None` on the SECOND poll.
72    Died,
73}

75/// Adapter that wraps async SSTableReader into a true-streaming sync
76/// [`SSTableRowIterator`].
77///
78/// ## Design (Issue #754 — remove 128MB buffer cap residue of #447)
79///
80/// The V5CompressedLegacy format requires chunk stitching: a partition may
81/// straddle compression-chunk boundaries, so the decoder needs a contiguous
82/// view spanning at least one whole partition. The reader's streaming path
83/// keeps only a **sliding window** of that view — one chunk plus the partition
84/// currently being decoded — rather than the whole decompressed file.
85///
86/// A background thread (the producer) opens the SSTable with its own Tokio
87/// runtime and calls
88/// [`stream_all_partitions_for_compaction`](crate::storage::sstable::reader::SSTableReader::stream_all_partitions_for_compaction),
89/// which decompresses one chunk at a time, drains every fully-decoded partition
90/// out of the window, and forwards the entries into a bounded `sync_channel` in
91/// BATCHES (issue #2820 — one cross-thread wake per batch instead of per row; see
92/// [`egress_batch`](super::egress_batch)). The channel's capacity is in MESSAGES,
93/// converted from the [`STREAMING_CHANNEL_CAPACITY`](super::STREAMING_CHANNEL_CAPACITY)
94/// ROW budget, adaptively reduced under concurrent merges (see
95/// [`egress_budget`](super::egress_budget)); once the channel is full the producer
96/// blocks until the consumer (the main merge thread) pulls the next batch.
97///
98/// The bounded window plus the bounded channel together make end-to-end peak
99/// memory independent of total input size: a source's decompressed content is
100/// never fully resident. Peak is roughly `max_partition_size + one_chunk +
101/// egress_batch::max_inflight_rows` per source (issue #827; `4 × rows_cap` since
102/// #2820 — 1024 at the default, 32 at the throttled floor — and additionally
103/// bounded in BYTES by `egress_batch::BATCH_EMIT_BYTES_MERGE` per batch).
104///
105/// ## Issue #591 safety (mmap vs file deletion)
106///
107/// `finalize_merge_async` deletes the input SSTable files once the merged output
108/// is published. We require that no mmap outlives its backing file. The producer
109/// thread opens the reader with `use_mmap = false`, and the thread *fully reads
110/// all file data* (the stitching phase) before it can block on a channel send.
111/// By the time `finalize_merge_async` runs, the merge is complete and all
112/// channel entries have been consumed, so the producer thread has long since
113/// finished and dropped its file handle. No mmap ever exists.
114///
115/// ## Issue #587 safety (async-from-sync bridge)
116///
117/// The producer thread creates its own Tokio runtime (never `Handle::block_on`),
118/// so it cannot panic even when called from within an existing Tokio runtime.
119/// This is the same strategy as [`block_on_async`](super::block_on_async).
120///
121/// ## Issue #2316 thread budget (O(M), no per-producer worker pool)
122///
123/// That per-producer runtime is a **`current_thread`** runtime, NOT a
124/// multi-threaded `Runtime::new()`: it drives the producer's single sequential
125/// scan (no internal `tokio::spawn`) on the producer thread itself, adding ZERO
126/// worker threads. A merge over `M` inputs therefore costs `O(M)` OS threads, not
127/// `M + M·num_cpus` — killing the context-switch storm under concurrent `do_get`.
128#[cfg(feature = "write-support")]
129pub(super) struct SSTableRowIteratorAdapter {
130    /// Receiving end of the bounded channel fed by the producer thread. `Option`
131    /// so [`Drop`] can drop it FIRST (issue #2361) — closing the channel wakes a
132    /// producer blocked on a full `SyncSender::send` (its send returns `Err`), so
133    /// the subsequent producer join is bounded and cannot deadlock.
134    pub(super) receiver: Option<std::sync::mpsc::Receiver<MergeMsg>>,
135    /// Producer thread handle. `Option` so [`Drop`] can `take()` it and JOIN the
136    /// thread (issue #2361) rather than detach it — the pre-#2361 `_producer`
137    /// field's "joined on drop" doc was WRONG (dropping a `JoinHandle` detaches
138    /// the thread, leaving it to run to completion in the background; a cancelled
139    /// `do_get` over a 1M-partition scan would keep burning CPU/IO). Joining after
140    /// dropping the receiver + tripping `scan_cancel` guarantees prompt teardown.
141    pub(super) producer: Option<std::thread::JoinHandle<()>>,
142    /// The PER-CALL cancellation token this adapter's producer scan polls (issues
143    /// #2264/#2346). Held so (a) [`Self::next`] can make its blocking channel
144    /// `recv` cancel-aware and (b) [`Drop`] can trip it, waking a producer that is
145    /// mid-scan (not blocked on send) so it exits promptly before the join.
146    pub(super) scan_cancel: crate::storage::scan_cancel::ScanCancel,
147    /// This adapter's OWN count of DATA entries its producer thread has
148    /// successfully sent into the bounded channel (issue #2419 roborev job
149    /// 1733), shared with the producer thread via `Arc` so `Drop` can read it.
150    /// It only becomes STABLE — no further increments possible — once the
151    /// producer thread has been joined (see `Drop`). Paired with
152    /// [`Self::received_count`] to compute the exact post-join egress-depth
153    /// reconcile residual: reading it BEFORE the join (as the pre-fix drain loop
154    /// did) races a producer send that can slip in after the drain's last
155    /// `Empty` and before the receiver is actually dropped, permanently leaking
156    /// the shared `cqlite.merge.egress_channel_depth` gauge upward across
157    /// repeated cancellations on a long-running server.
158    pub(super) sent_count: std::sync::Arc<std::sync::atomic::AtomicI64>,
159    /// This adapter's own count of DATA entries actually received off the
160    /// channel, incremented by the same batch length as every
161    /// [`channel_depth::received_n`] call this adapter makes ([`Self::next`]'s
162    /// normal consumption). Only ever touched by the thread holding `&mut self`
163    /// (never shared), so a plain `i64`.
164    ///
165    /// Issue #2820: "received" means PULLED OFF THE CHANNEL, not handed to the
166    /// consumer — entries still sitting in [`Self::held`] are counted here,
167    /// because the gauge they balance tracks channel occupancy and they have
168    /// already left it. That keeps the `Drop` reconcile exact for an abandoned
169    /// partial batch: it was never a residual to begin with.
170    pub(super) received_count: i64,
171    /// This run's verdict (issue #3120) — see [`RunState`]. The single place a
172    /// "this run is exhausted" answer may come from.
173    pub(super) state: RunState,
174    /// Test-only (issue #2765): the exact `sync_channel` capacity this adapter's
175    /// egress channel was built with. Since issue #2820 that argument is in
176    /// MESSAGES (batches) — the truth of what was passed to `sync_channel` —
177    /// while the merge-scoped adaptive snapshot the constructor threaded in is in
178    /// ROWS; see [`Self::egress_rows_capacity`]. Observed via
179    /// [`SSTableRowIterator::egress_channel_capacity`] so a wiring test proves the
180    /// budget reaches BOTH construction sites.
181    #[cfg(test)]
182    pub(super) egress_channel_capacity: usize,
183    /// Test-only (issue #2820): the ROW capacity snapshot
184    /// [`Self::egress_channel_capacity`] was derived from — i.e. the value
185    /// `egress_budget::begin_merge` handed the constructor, in the units every
186    /// `egress_budget` doc and test speaks. Keeping BOTH observable is what lets a
187    /// wiring test assert the CONVERSION (`message_capacity_for_rows(rows) ==
188    /// messages`) rather than just a plausible-looking number: a channel silently
189    /// built with the ROW budget as its message capacity is a 256x resident-row
190    /// blow-up that an unconverted assertion would have called correct.
191    #[cfg(test)]
192    pub(super) egress_rows_capacity: usize,
193    /// The BATCH this adapter received from the channel and is handing out one
194    /// entry per [`SSTableRowIterator::next`] (issue #2820). Empty between
195    /// batches; refilled by exactly one `recv`.
196    ///
197    /// Its entries have ALREADY left the bounded channel, so they are already
198    /// accounted on the egress-depth gauge as received — see `next` and the
199    /// `Drop` reconcile.
200    pub(super) held: std::vec::IntoIter<MergeEntry>,
201}

203/// Poll interval for the cancel-aware blocking `recv` in
204/// [`SSTableRowIteratorAdapter::next`] (issue #2361). A bounded wait so a
205/// cancellation that lands while the consumer is blocked waiting for the next
206/// producer entry is observed within one interval, without a busy-spin. This is
207/// an INTERNAL cadence only — never asserted against wall-clock in tests.
208#[cfg(feature = "write-support")]
209const RECV_CANCEL_POLL: std::time::Duration = std::time::Duration::from_millis(50);

211#[cfg(feature = "write-support")]
212impl SSTableRowIteratorAdapter {
213    /// Open an SSTable and start a streaming producer thread.
214    ///
215    /// Returns immediately; the producer thread runs concurrently and populates
216    /// the channel as the consumer advances. The file handle is held only by
217    /// the producer thread and is dropped when the thread finishes.
218    ///
219    /// Uses [`SSTableReader::iterate_all_partitions_for_compaction`] which
220    /// returns actual per-row timestamps decoded from the on-disk row headers.
221    /// This allows the k-way merger to perform timestamp-accurate last-write-wins
222    /// ordering, which is essential for tombstone shadowing (Issue #505).
223    ///
224    /// When the schema has clustering columns, their values are extracted from
225    /// the decoded cells (in the producer thread, by column name in schema order)
226    /// and stored on `MergeEntry.clustering_key` so `merge_partition_rows` groups
227    /// and reconciles distinct clustering rows correctly. The clustering columns
228    /// are left in the cells as well, since the read-back path expects them there.
229    ///
230    /// `channel_capacity` (issue #2765) is the merge-scoped adaptive egress
231    /// capacity snapshotted ONCE by the `KWayMerger` constructor and shared by
232    /// every source channel of that merge — never derived per adapter here.
233    pub(super) fn open(
234        path: &Path,
235        run_index: usize,
236        schema: &TableSchema,
237        udt_registry: Option<crate::schema::UdtRegistry>,
238        scan_cancel: crate::storage::scan_cancel::ScanCancel,
239        channel_capacity: usize,
240        // Issue #1704: WHO counts a failed reopen. Stated by the caller because only
241        // it knows whether its own seam records — see `merge::constructors`.
242        reporting: crate::storage::sstable::reader::OpenErrorReporting,
243    ) -> Result<Self> {
244        let path_buf = path.to_path_buf();
245        let schema = schema.clone();
246        // Held on the adapter for cancel-aware recv + Drop teardown (issue #2361).
247        let adapter_cancel = scan_cancel.clone();
248
249        // Issue #2820: `channel_capacity` is a ROW budget (`egress_budget`'s whole
250        // vocabulary is rows); the channel carries BATCHES, so it is converted to a
251        // MESSAGE capacity here — the same conversion, from the same constant, as
252        // the shared-reader construction site in `from_readers`. Passing the row
253        // budget straight through would budget 256 BATCHES = 65_536 entries per
254        // source. See `egress_batch::message_capacity_for_rows`.
255        let message_capacity = super::egress_batch::message_capacity_for_rows(channel_capacity);
256        let (sender, receiver) = std::sync::mpsc::sync_channel(message_capacity);
257        // Issue #2419 roborev job 1733: this adapter's own sent-count, shared
258        // with the producer thread so `Drop` can read its post-join-stable value
259        // for the egress-depth reconcile (see the field doc).
260        let sent_count = std::sync::Arc::new(std::sync::atomic::AtomicI64::new(0));
261        let producer_sent_count = sent_count.clone();
262
263        // Issue #2316: account this producer on the `cqlite.merge.producer_threads`
264        // gauge BEFORE spawning, so the increment happens-before any possible
265        // decrement. The decrementing `ProducerThreadGuard` is created first thing
266        // inside the child thread (see `producer_thread`); a fast-exiting producer
267        // (e.g. a reader-open error) could otherwise race its own guard's drop
268        // against a post-spawn increment on the parent, transiently underflowing
269        // the live count. Incrementing here first makes the pairing
270        // correct-by-construction — no ordering race is possible.
271        producer_gauge::spawned();
272
273        // Issue #2819: propagate the sub-phase sink onto this path-based producer
274        // thread too (thread-locals are not inherited across a spawn); `None`
275        // (no-op) for non-flight callers. NOTE (roborev L2): this is a DEFENSIVE /
276        // latent propagation, NOT a parity-covered do_get path — production
277        // `do_get` is warm-only (`spawn_streaming_from_readers` → `open_from_reader`,
278        // which has the tested propagation). The path-based `open`
279        // (`MergeInput::Paths`) is the test-only byte-identity oracle, so its
280        // cold_fault/decompress attribution has no e2e assertion (and would fire
281        // only for a stitching/BTI fixture via the `read_next_block` loop). Kept so
282        // a future path-based flight caller is correct by construction, not to
283        // imply current parity coverage. (This file is far over the #1116 campsite
284        // target; the +2 lines are the minimal propagation.)
285        let subphase_sink = crate::observability::stream_subphase::current();
286        // Issue #1707: the read-PHASE sink, propagated the SAME way and for the same
287        // reason — and on THIS path it is exercised in production, unlike the
288        // sub-phase sink above: `generation_merge::stream_generations_for_read`
289        // reaches `KWayMerger::new` → `MergeInput::Paths` → here, so the chunk decode
290        // of every cross-generation read runs on this thread. Installing the sink on
291        // the merge/consumer thread alone left that route recording `merge` and
292        // nothing else. It reaches the shared chunk-decode plane
293        // (`reader::chunk_source`), so DECOMPRESS is measured through it; the io seam
294        // lives only in the windowed scan's read helpers and is therefore still NOT
295        // reached from here — see `observability::read_phase`'s coverage boundary.
296        // `None` (no-op) for an unmetered caller.
297        let read_phase_sink = crate::observability::read_phase::current();
298
299        // Issue #3120: whatever fault a test armed FOR THIS INPUT is captured HERE
300        // (never re-read mid-walk) and owned by the producer thread. Always empty —
301        // and a zero-sized no-op whose scope closure is never called — in a
302        // production build.
303        let fault = MergeProducerFault::capture_for(|| path.to_path_buf());
304
305        // Spawn the producer thread via `Builder::spawn` (rather than the
306        // panic-on-failure `std::thread::spawn`) so an OS thread-creation failure
307        // is a recoverable `Err`, not a process abort: the gauge increment above
308        // must never leak for a thread that never actually started, so roll it
309        // back on this path via `producer_gauge::rollback`. The thread owns a
310        // fresh single-threaded (current_thread) Tokio runtime so it never
311        // collides with any runtime on the calling thread (Issue #587) and adds no
312        // worker threads beyond itself (Issue #2316).
313        let producer = match std::thread::Builder::new().spawn(move || {
314            let _subphase_guard = crate::observability::stream_subphase::install(subphase_sink);
315            let _read_phase_guard = crate::observability::read_phase::install(read_phase_sink);
316            Self::producer_thread(
317                path_buf,
318                run_index,
319                schema,
320                udt_registry,
321                scan_cancel,
322                sender,
323                producer_sent_count,
324                channel_capacity,
325                fault,
326                reporting,
327            );
328        }) {
329            Ok(handle) => handle,
330            Err(e) => {
331                producer_gauge::rollback();
332                return Err(Error::Storage(format!(
333                    "streaming producer: failed to spawn thread: {}",
334                    e
335                )));
336            }
337        };
338
339        Ok(Self {
340            receiver: Some(receiver),
341            producer: Some(producer),
342            scan_cancel: adapter_cancel,
343            sent_count,
344            received_count: 0,
345            held: Vec::new().into_iter(),
346            // Issue #3120: no terminator observed yet. `None` (end of input) is
347            // reachable ONLY from a `Done`-proven `RunState::Finished`.
348            state: RunState::Streaming,
349            #[cfg(test)]
350            egress_channel_capacity: message_capacity,
351            #[cfg(test)]
352            egress_rows_capacity: channel_capacity,
353        })
354    }
355
356    /// Body of the producer thread.
357    ///
358    /// Opens the SSTable with buffered I/O (Issue #591), then **streams** the
359    /// source one partition at a time via
360    /// [`stream_all_partitions_for_compaction`](crate::storage::sstable::reader::SSTableReader::stream_all_partitions_for_compaction),
361    /// converting each entry to a [`MergeEntry`] (populating the clustering key
362    /// from the decoded cells when the schema has clustering columns) and sending
363    /// it through the bounded channel, BATCHED since issue #2820 (issue #827). The
364    /// blocking `SyncSender::send` provides the backpressure that — together
365    /// with the reader's sliding-window stitch+parse — keeps peak memory bounded
366    /// by `max_partition_size + one_chunk + egress_batch::max_inflight_rows`
367    /// (and `egress_batch::max_inflight_bytes`), independent of total source size.
368    ///
369    /// Sends EXACTLY ONE terminal [`MergeMsg`] on EVERY exit path (issue #3120) —
370    /// `Done` on a completed walk, `Failed` on an error return, `Failed(Panicked)`
371    /// on an unwind caught here — so the consumer never has to infer completion
372    /// from a channel disconnect. See [`producer_msg`](super::producer_msg)'s
373    /// header for why both the `catch_unwind` and the `Done` sentinel are needed.
374    #[allow(clippy::too_many_arguments)]
375    fn producer_thread(
376        path_buf: PathBuf,
377        run_index: usize,
378        schema: TableSchema,
379        udt_registry: Option<crate::schema::UdtRegistry>,
380        scan_cancel: crate::storage::scan_cancel::ScanCancel,
381        sender: std::sync::mpsc::SyncSender<MergeMsg>,
382        sent_count: std::sync::Arc<std::sync::atomic::AtomicI64>,
383        // Issue #2820: the merge-scoped adaptive ROW capacity, which bounds this
384        // run's BATCH size as well as its channel's message capacity — see
385        // `egress_batch::batch_limit_ceiling`.
386        channel_capacity: usize,
387        mut fault: MergeProducerFault,
388        reporting: crate::storage::sstable::reader::OpenErrorReporting,
389    ) {
390        // Issue #2316: decrement the live producer-thread gauge when this thread
391        // exits (even on panic). Created FIRST so the spawn-time increment in
392        // `open` is always balanced exactly once.
393        let _thread_guard = producer_gauge::ProducerThreadGuard;
394
395        // Drive the streaming read on an owned Tokio runtime (Issue #587): the
396        // producer owns its single-purpose runtime, so the blocking
397        // `SyncSender::send` inside the emit callback never stalls a shared
398        // runtime, and there is no nested `block_on` / `Handle::current`. The
399        // runtime is `current_thread` (Issue #2316), so it adds no worker threads.
400        // Buffered I/O (Issue #591): the file must not be memory-mapped OR read
401        // via direct I/O because finalize_merge_async may delete it after the
402        // merge completes. The default disk-access mode is `Auto`, which would
403        // otherwise map (or direct-read) inputs above the size thresholds, so we
404        // force `Buffered` explicitly here — clearing `use_mmap` alone is no
405        // longer sufficient now that `Auto` ignores that legacy flag.
406        // Clone the sender for the TERMINAL message: the streaming closure moves
407        // one clone for per-entry sends, leaving this one to report the single
408        // terminator. Issue #3120: it lives OUTSIDE the `catch_unwind` closure, so
409        // an unwind cannot drop it before the terminator is sent.
410        let terminal_sender = sender.clone();
411        // Reborrowed into the closure (and on into the `async move` block) so the
412        // per-row fault checkpoint is reached without the closure taking ownership.
413        let fault = &mut fault;
414        // Issue #3120: an UNWINDING walk must not look like a finished one.
415        // `AssertUnwindSafe` is sound here because nothing the closure touched is
416        // observed after an unwind: the reader, config, schema, cancel token and
417        // fault state are dropped, and the only thing used afterwards is
418        // `terminal_sender` — an mpsc `SyncSender`, which has no
419        // poisoning/broken-invariant state. `sent_count` is an atomic whose value
420        // stays meaningful (it counts sends that already succeeded) and `Drop`
421        // reads it only after joining this thread.
422        let stream_result =
423            std::panic::catch_unwind(std::panic::AssertUnwindSafe(move || -> Result<()> {
424                use crate::config::DiskAccessMode;
425                use crate::platform::Platform;
426                use crate::Config;
427                use std::sync::Arc;
428
429                let mut config = Config::default();
430                config.storage.use_mmap = false;
431                config.storage.disk_access_mode = DiskAccessMode::Buffered;
432
433                // Issue #2316: a `current_thread` runtime drives the scan ON this
434                // producer thread with ZERO extra workers. A multi-threaded
435                // `Runtime::new()` would spin up `num_cpus` workers per producer
436                // (~M·num_cpus threads/merge) that the single sequential scan never
437                // uses — pure overhead. This bounds the per-merge thread cost to O(M).
438                let rt = tokio::runtime::Builder::new_current_thread()
439                    .enable_all()
440                    .build()
441                    .map_err(|e| {
442                        Error::Storage(format!(
443                            "streaming producer: failed to create runtime: {}",
444                            e
445                        ))
446                    })?;
447
448                rt.block_on(async move {
449                    let platform = Arc::new(Platform::new(&config).await?);
450                    // `open_with_reporting`, NOT the self-reporting default (issue #1704): this reopen is an
451                    // INNER STEP. A failure here surfaces mid-stream at `step()` and
452                    // is counted ONCE by the enclosing operation's seam — the measured
453                    // `JoinedStream` on the cross-generation streaming read path, or
454                    // `record_result("compaction", ..)` in `maintenance_step` on the
455                    // write path. `open`, which records its own failure, made one
456                    // failed reopen report TWO increments, under two different
457                    // categories (measured: `io` from the raw EACCES plus `storage`
458                    // from the merge's rewrap).
459                    let mut reader =
460                        crate::storage::sstable::reader::SSTableReader::open_with_reporting(
461                            &path_buf, &config, platform, reporting,
462                        )
463                        .await?;
464
465                    // Issue #1234: wire the authoritative UDT registry onto the reader
466                    // so the compaction read path decodes a top-level `frozen<UDT>`
467                    // value structurally. Without it the value decode errors
468                    // (`UDT not found in registry`), the row reconciles to empty, and
469                    // the partition is dropped — silent data loss during compaction.
470                    // This mutation requires `&mut self`, so it can only happen HERE
471                    // — before the reader is ever shared — not on the shared-reader
472                    // producer path (issue #2346, see `from_readers::open_from_reader`'s
473                    // doc comment for that seam's UDT-registry contract).
474                    if let Some(registry) = udt_registry {
475                        reader.set_udt_registry(registry);
476                    }
477
478                    // Issue #2264/#2346: the cooperative-cancellation token is now a
479                    // PER-CALL parameter to `stream_all_partitions_for_compaction`
480                    // rather than mutated onto the reader (`set_scan_cancel` needed
481                    // `&mut self`, which a SHARED reader cannot offer — see
482                    // `from_readers::drive_compaction_stream`). This path-based
483                    // producer still owns its freshly-opened `reader` exclusively, so
484                    // passing `scan_cancel` by reference here is behaviourally
485                    // identical to the old `set_scan_cancel` + field-read.
486                    //
487                    // Pass the schema so the parser uses the real clustering column
488                    // names; the header-inferred fallback uses generic names like
489                    // "clustering_key", which would defeat extract_clustering_key.
490                    // `drive_compaction_stream` is the SAME streaming helper the
491                    // shared-reader producer thread uses (issue #2346) — the
492                    // conversion/backpressure/cancellation-by-variant semantics are
493                    // defined in exactly one place.
494                    from_readers::drive_compaction_stream(
495                        &reader,
496                        run_index,
497                        &schema,
498                        &scan_cancel,
499                        &sender,
500                        sent_count.as_ref(),
501                        channel_capacity,
502                        fault,
503                    )
504                    .await
505                })
506            }));
507
508        // EXACTLY ONE terminal message, on every exit path (issue #3120).
509        // `Cancelled` is preserved distinctly (issue #2264) by
510        // `MergeProducerError::from`.
511        let terminal = match stream_result {
512            Ok(Ok(())) => MergeMsg::Done,
513            Ok(Err(e)) => MergeMsg::Failed(MergeProducerError::from(e)),
514            Err(panic) => MergeMsg::Failed(panicked_producer_error(panic.as_ref())),
515        };
516        // The BLOCKING `send`, never `try_send`: dropping the terminator because
517        // the bounded channel happened to be full would recreate exactly the
518        // ambiguity this protocol removes. A failed send means the consumer is
519        // already gone, which is fine — nobody is left to mislead.
520        let _ = terminal_sender.send(terminal);
521        // Channel closed naturally when sender is dropped here.
522    }
523}

525#[cfg(feature = "write-support")]
526impl SSTableRowIterator for SSTableRowIteratorAdapter {
527    /// Pull the next entry of this run.
528    ///
529    /// `None` means EXHAUSTED, and issue #3120 made that answer reachable from
530    /// exactly ONE place: a [`RunState::Finished`] proven by the producer's
531    /// [`MergeMsg::Done`] terminator. Every other way this adapter can stop —
532    /// a bare channel disconnect, a torn-down receiver, a terminal failure — is
533    /// an `Err`, because a run whose standing is unknown is a TRUNCATED run, and
534    /// merging (or REWRITING) a truncated run as if it were complete is silent
535    /// data loss.
536    fn next(&mut self) -> Option<Result<MergeEntry>> {
537        use std::sync::mpsc::RecvTimeoutError;
538        // A terminal state is STICKY: re-poll it as many times as a consumer
539        // likes, and it never decays into a clean end of input. `RunReader::
540        // refill_buffer` propagates our `Err` but keeps no sticky error of its
541        // own, so this is where the stickiness has to live (issue #3120).
542        match &self.state {
543            RunState::Finished => return None,
544            RunState::Failed(e) => return Some(Err(e.to_error())),
545            RunState::Died => return Some(Err(dead_producer_error())),
546            RunState::Streaming => {}
547        }
548        // The receiver is torn down ONLY by `Drop`, so a live poll that finds it
549        // gone has NO verdict at all. Pre-#3120 this was a `?`, i.e. a second
550        // silent route to "exhausted"; fail closed instead.
551        let receiver = match self.receiver.as_ref() {
552            Some(receiver) => receiver,
553            None => {
554                self.state = RunState::Died;
555                return Some(Err(dead_producer_error()));
556            }
557        };
558        // Cancel-aware blocking recv (issue #2361): a plain `recv()` blocks
559        // indefinitely inside `KWayMerger::step`, so a `do_get` cancellation that
560        // lands while the consumer is waiting for the next producer entry was NOT
561        // observed until an entry (or channel close) arrived. Poll `scan_cancel`
562        // at a bounded interval so `drive_merge` sees `Error::Cancelled` promptly
563        // even while blocked here.
564        loop {
565            // A CANCELLED scan must never be reported as a dead producer (issue
566            // #3120): that is this fix's likeliest false positive. The check stays
567            // at the TOP of the loop so it wins over a queued terminator, and
568            // `ScanCancel` is set-once, so a repeat poll keeps answering
569            // `Cancelled` — no state transition is needed or wanted here (the run
570            // is abandoned, not truncated-and-misreported).
571            if self.scan_cancel.is_cancelled() {
572                return Some(Err(Error::Cancelled));
573            }
574            // Hand out the next entry of the batch already in hand (issue #2820)
575            // BEFORE touching the channel. Deliberately BELOW the cancel check, so
576            // cancellation wins over a partially-drained batch too: the run is
577            // abandoned, and a torn-down consumer that kept draining buffered rows
578            // would delay the very teardown the cancel exists to start. Its
579            // entries were already accounted as received when the batch was pulled
580            // off the channel, so abandoning them here cannot unbalance the
581            // egress-depth gauge (nor the `Drop` reconcile, which is computed from
582            // the SAME `received_count`).
583            if let Some(entry) = self.held.next() {
584                // Issue #2096: one merge entry decoded from `Data.db` by THIS
585                // adapter-driven run — a full scan, compaction, or (via the
586                // fail-safe `SinglePartitionFilterRun`) a point read all share
587                // this increment site, so `merge_run_entries_decoded` counts
588                // entries for any of them, not point reads alone. It is counted
589                // per ENTRY HANDED OUT (never per batch received): its unit is
590                // entries decoded, and every existing bound test reads it as such.
591                // See `work_counters::merge_run_entries_decoded`'s doc for the
592                // process-global caveat when using it as a delta assertion.
593                crate::storage::sstable::work_counters::add_merge_run_entry_decoded();
594                return Some(Ok(entry));
595            }
596            match receiver.recv_timeout(RECV_CANCEL_POLL) {
597                Ok(MergeMsg::Batch(entries)) => {
598                    // Issue #2419 (WS2): these DATA entries just left the bounded
599                    // egress channel — decrement the live occupancy gauge by the
600                    // BATCH LENGTH, balancing the `channel_depth::sent_n` at its
601                    // send site (`egress_batch::EgressBatcher::flush`).
602                    // `received_count` is this adapter's OWN mirror of that
603                    // decrement (roborev job 1733), read by `Drop` post-join to
604                    // compute the exact reconcile residual — see the field doc.
605                    // Issue #2820: BOTH must move by entries, never by 1 per
606                    // message, or the residual drifts by `entries - messages` and
607                    // the `> 0` guard plus `max(0)` floor hide it forever.
608                    //
609                    // Issue #3120 — the receive-side half of "a TERMINATOR is
610                    // untracked on both sides". Note what enforces it HERE: this
611                    // arm does NOT call `MergeMsg::tracked_entries` (that is the
612                    // send site's compile-time tripwire). It is correct because
613                    // (a) the `match` it belongs to is EXHAUSTIVE with no wildcard
614                    // arm, so a future 4th variant is a compile error rather than
615                    // a silent catch-all, and (b) `channel_depth::received_n` and
616                    // `received_count` each appear at exactly ONE site in the
617                    // crate — both right here, both passed the same length.
618                    let received = entries.len();
619                    channel_depth::received_n(received);
620                    self.received_count += received as i64;
621                    // Hold the batch and loop: the top of the loop re-checks the
622                    // cancel flag, then hands out its first entry. An EMPTY batch
623                    // (never sent by `EgressBatcher`, which returns early on an
624                    // empty accumulator) simply polls again — it can never be
625                    // mistaken for end-of-input, which only `Done` proves.
626                    self.held = entries.into_iter();
627                    continue;
628                }
629                // TERMINAL failure. Recorded so a repeat poll re-reports the
630                // identical error. `Cancelled` stays a distinct `Error::Cancelled`
631                // (issue #2264) — `drive_merge` matches on the variant, not on a
632                // side-channel flag — via `MergeProducerError::to_error`.
633                Ok(MergeMsg::Failed(e)) => {
634                    let error = e.to_error();
635                    self.state = RunState::Failed(e);
636                    return Some(Err(error));
637                }
638                // The ONLY proof of a clean, COMPLETE run.
639                Ok(MergeMsg::Done) => {
640                    self.state = RunState::Finished;
641                    return None;
642                }
643                // No entry yet: re-poll the cancel flag and keep waiting.
644                Err(RecvTimeoutError::Timeout) => continue,
645                // The sender was dropped WITHOUT a terminator. Only a dead
646                // producer can do that (a healthy one sends `Done`; a failing one
647                // sends `Failed`), so this run is TRUNCATED at an arbitrary point.
648                // Pre-#3120 this returned `None` — "the run is exhausted" — which
649                // is the defect: a short read result, or a short REWRITTEN SSTable.
650                Err(RecvTimeoutError::Disconnected) => {
651                    self.state = RunState::Died;
652                    return Some(Err(dead_producer_error()));
653                }
654            }
655        }
656    }

659    /// `sync_channel` was constructed with — in MESSAGES since issue #2820.
660    #[cfg(test)]

662        Some(self.egress_channel_capacity)
663    }

674/// Cancel-aware teardown (issue #2361): trip the scan token, close the channel,
675/// then JOIN the producer thread — so a dropped merger (LIMIT satisfied, client
676/// disconnect, error, panic) does not leave a detached producer streaming a
677/// multi-million-partition scan in the background.
678///
679/// ## Step order is LOAD-BEARING and must not change
680///
681/// cancel → drop receiver → join → reconcile. (1)+(2) are what make (3) bounded,
682/// and (4) is only race-free once (3) has proven the producer can no longer send.
683///
684/// ## The join is a DIAGNOSTIC, never the verdict (issue #3120)
685///
686/// `std::thread::JoinHandle::join(self)` CONSUMES the handle and BLOCKS, so —
687/// unlike the `tokio::JoinHandle` that issue #3106 could poll in place — it can
688/// never be the mechanism that decides whether a run finished. The verdict comes
689/// entirely from the producer's explicit terminator (see
690/// [`SSTableRowIterator::next`] above and [`producer_msg`](super::producer_msg)),
691/// which is why `next()` performs no join at all and stays non-blocking.
692///
693/// What step 3 does now is stop DISCARDING the join outcome: a producer that
694/// unwound is logged here rather than silently swallowed. That is deliberately a
695/// log/metric only — this `Drop` must stay NON-PANICKING (`teardown_tests` drops
696/// mergers on purpose; issue #2361 pins that), and by the time a `Drop` runs the
697/// consumer is gone, so there is nobody left to return an error to. The
698/// correctness answer was already delivered through the channel.
699#[cfg(feature = "write-support")]
700impl Drop for SSTableRowIteratorAdapter {
701    fn drop(&mut self) {
702        // 1. Trip the cooperative token so a producer that is mid-scan (polling
703        //    `scan_cancel`, NOT blocked on a channel send) abandons its walk.
704        self.scan_cancel.cancel();
705        // 2. Drop the receiver so a producer BLOCKED on a full `SyncSender::send`
706        //    wakes immediately (send returns `Err`, and `drive_compaction_stream`
707        //    maps that to `ControlFlow::Break`). Without this the join below could
708        //    block until the channel drained. Dropping it here (before the join)
709        //    rather than relying on field-drop order (which runs AFTER this `Drop`)
710        //    is what makes the join bounded.
711        //
712        //    Issue #2419 roborev job 1733: do NOT try to drain-and-decrement the
713        //    egress-depth gauge HERE. A prior version looped `try_recv` until
714        //    `Empty` and decremented per drained entry before dropping the
715        //    receiver — but the producer runs on another OS thread, so a send can
716        //    slip in and succeed (incrementing the shared gauge) in the window
717        //    between that loop's last `Empty` and this `drop`, with no entry ever
718        //    physically drained to balance it: a PERMANENT, monotonic upward leak
719        //    of `cqlite.merge.egress_channel_depth` across every
720        //    cancelled/disconnected scan on a long-running server. The gauge is
721        //    reconciled instead in step 4, AFTER the join, using this adapter's
722        //    own sent/received delta — which only becomes authoritative once the
723        //    producer thread has provably stopped sending.
724        drop(self.receiver.take());
725        // 3. Join the producer — bounded, because after (1)+(2) the producer
726        //    cannot block indefinitely: it either observes the cancel in its scan
727        //    loop or its next send fails. Issue #3120: the join outcome is no
728        //    longer DISCARDED. It is a diagnostic, not the verdict (see this
729        //    impl's doc): a producer that unwound has already reported itself
730        //    through the terminator protocol, and a `Drop` has no caller to return
731        //    an error to, so an unwind is LOGGED here — never re-panicked, which
732        //    would abort a teardown that is frequently itself running during an
733        //    unwind.
734        //
735        //    NOT exercised by the injected-panic tests, on purpose: both producer
736        //    bodies wrap their whole walk in `catch_unwind`, so under
737        //    `panic = "unwind"` a caught panic never reaches the join as an `Err`.
738        //    This is the residual backstop for an unwind that escapes the
739        //    `catch_unwind` — a panic between it returning and the terminal `send`,
740        //    or inside the `send` itself — which is also the shape the bare-
741        //    disconnect arm of `next()` above reports (see
742        //    `producer_panic_tests::a_producer_that_disconnects_without_a_terminator_*`).
743        if let Some(handle) = self.producer.take() {
744            if handle.join().is_err() {
745                tracing::warn!(
746                    "streaming merge producer thread PANICKED (issue #3120); its run \
747                     was reported to the merge as a terminal error via the channel \
748                     terminator, so no row was silently dropped"
749                );
750            }
751        }
752        // 4. Issue #2419 roborev job 1733: reconcile the shared egress-depth
753        //    gauge AFTER the producer thread has definitively exited — `join`
754        //    returning guarantees `self.sent_count` can never increase again, so
755        //    this read is race-free (unlike reading it, or draining the channel,
756        //    before the join). Any DATA entries this adapter's producer
757        //    successfully sent but this consumer never received — abandoned when
758        //    the channel was torn down while entries were still buffered —
759        //    are exactly `sent_count - received_count`. Issue #2820: entries of a
760        //    partially-drained HELD batch are NOT part of that residual; they were
761        //    counted as received when the batch left the channel, which is the same
762        //    moment the gauge was decremented for them, so abandoning them here is
763        //    already balanced. reconcile the shared
764        //    gauge by that residual in ONE atomic op so a cancelled/disconnected
765        //    scan returns `cqlite.merge.egress_channel_depth` to baseline instead
766        //    of drifting upward.
767        let residual =
768            self.sent_count.load(std::sync::atomic::Ordering::SeqCst) - self.received_count;
769        channel_depth::reconcile_residual(residual);
770    }
