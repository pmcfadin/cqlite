12// ---------------------------------------------------------------------------
13// Read-path PHASE timings + reader-reported resource gauges (issue #1707, AI7 of
14// epic #1686). A slow `SELECT` used to be un-localisable from metrics alone:
15// `READ_DURATION` says the read was slow and nothing says WHERE the time went.
16// These four histograms split one completed scan's accumulated wall time into
17// io / decompress / decode / merge — accumulated at existing function seams into a
18// per-scan `ReadPhaseTimings`, and emitted as exactly ONE sample per phase per
19// COMPLETED scan (never per chunk, never per row).
20//
21// NAMING (#1707): the issue text spelled these `read.phase.io_ms` etc. The `_ms`
22// suffix was deliberately NOT adopted — every timing metric in this catalog is
23// base-unit SECONDS ([`super::READ_DURATION`], [`super::WAL_SYNC_DURATION`], the `cqlite.rpc.*`
24// durations), which is what OTel's semantic conventions ask for, so an `_ms`-named
25// metric carrying [`super::unit::SECONDS`] would misdescribe its own values and an `ms`
26// unit would break the repo-wide (and OTel) base-unit convention.
27//
28// ACCOUNTING CAVEAT, stated here because it changes how the numbers are read: the
29// read pipeline is CONCURRENT (an IO/decode feed thread, a blocking parse thread, a
30// merge consumer thread), so these phases OVERLAP in wall-clock and DO NOT sum to
31// the scan's [`super::READ_DURATION`]. They are per-phase totals for attribution — which
32// phase dominates, and how it moves between two runs — not a decomposition of
33// latency. Same caveat as the #2819 `stream_*` sub-phases.
34// ---------------------------------------------------------------------------
35
36/// `cqlite.read.phase.io` — histogram `s` (issue #1707).
37///
38/// Wall time ONE completed scan spent in `Data.db` READS: the synchronous
39/// positional chunk/piece reads the windowed scan's IO half performs
40/// (`read_compressed_chunk_sync` / `read_uncompressed_piece_sync`), CRC verify
41/// included, decompression excluded (that is [`READ_PHASE_DECOMPRESS`]).
42///
43/// **Healthy vs alarming**: on a warm page cache this is a small fraction of the
44/// scan; io dominating (say > half the recorded phase time) means the scan is
45/// disk/page-fault bound — cold storage, an evicted page cache, or a network
46/// filesystem — not CPU bound, so a decode/merge optimisation will not help it.
47/// Compare it against [`READ_PHASE_DECODE`] before tuning anything.
48///
49/// **Coverage**: the windowed scan driver (the dominant `SELECT *` path). A read
50/// that never enters that driver (a point read, the BTI trie walk) records NO
51/// sample at all — absence means the phase DID NOT RUN. A `0.0` sample is a
52/// different statement: the phase ran and measured zero. **Attributes**: none.
53pub const READ_PHASE_IO: &str = "cqlite.read.phase.io";
54
55/// `cqlite.read.phase.decompress` — histogram `s` (issue #1707).
56///
57/// Wall time ONE completed scan spent DECOMPRESSING chunk payloads, measured
58/// inside the single chunk-decode plane (`reader::chunk_source`) around the
59/// compressor call ONLY — the read that fetched the compressed bytes is
60/// [`READ_PHASE_IO`], and a resident decompressed-chunk cache HIT does no
61/// decompression and so adds nothing.
62///
63/// **Healthy vs alarming**: proportional to compressed bytes; a growing share
64/// points at chunk-length/compressor choice or at re-decompressing the same chunks
65/// (a cache too small for the scan's window).
66///
67/// **ABSENT, never zero, for an UNCOMPRESSED SSTable** — CQLite's own write surface
68/// emits uncompressed SSTables (#1406) and those reads decompress NOTHING, so this
69/// series carries no sample at all for them. Absence and `0.0` are DIFFERENT
70/// statements and the emitter distinguishes them by tracking phase ENTRY separately
71/// from duration (#1707): absence means the phase did not run, while `0.0` means it
72/// ran and measured zero — decompression too fast for the clock, not the absence of
73/// decompression. **Attributes**: none.
74pub const READ_PHASE_DECOMPRESS: &str = "cqlite.read.phase.decompress";
75
76/// `cqlite.read.phase.decode` — histogram `s` (issue #1707).
77///
78/// Wall time ONE completed scan spent DECODING rows/cells out of already-resident
79/// decompressed bytes — accumulated per PARTITION at the windowed scan's parse
80/// boundary (`parse_one_partition_with_timestamps`), which is the coarsest boundary
81/// that still separates decode from io. Deliberately NOT per row: the row/cell
82/// decoder is the hottest loop in the read path and is never instrumented.
83///
84/// **Healthy vs alarming**: normally the largest phase of a warm full scan (decode
85/// is CPU-bound work over resident bytes). Alarming when it grows relative to the
86/// rows delivered — wide partitions, many collection/UDT cells, or a schema-less
87/// fallback decode doing more work per row. **Attributes**: none.
88pub const READ_PHASE_DECODE: &str = "cqlite.read.phase.decode";
89
90/// `cqlite.read.phase.merge` — histogram `s` (issue #1707).
91///
92/// Wall time ONE completed cross-generation read spent in the k-way MERGE +
93/// reconcile step (`KWayMerger::step`), with the blocking merge-input recv-wait
94/// SUBTRACTED — that wait is producer starvation (i.e. io on another thread), not
95/// merge CPU, and counting it would make every disk-bound scan look merge-bound.
96/// Same exclusion the #2819 `stream_merge` sub-phase applies, through the same
97/// per-thread recv-wait accumulator.
98///
99/// **Coverage, stated because it is narrower than its siblings**: this phase is
100/// recorded only on the CROSS-GENERATION merge route (`stream_generations_for_read`).
101/// A single-generation scan performs no k-way merge, so it records NO sample —
102/// absence here means "there was nothing to merge", not "merge was free".
103///
104/// **A `0.0` sample means a merge DID run and measured zero**, which on this series
105/// has a specific and useful reading: the recv-wait subtraction consumed the whole
106/// step, i.e. the merge thread spent all its time waiting on starved producers. That
107/// case used to be reported as ABSENCE — "single generation" — which was a false
108/// statement produced by the subtraction that exists to keep the number honest
109/// (#1707). Entry is now tracked separately from duration, so the zero is emitted.
110///
111/// **Healthy vs alarming**: grows with the number of overlapping generations and
112/// with reconcile work (tombstones, LWW collapse); a merge-dominated read with few
113/// delivered rows is the compaction-lag smell — cross-check
114/// [`super::COMPACTION_LAG`]. **Attributes**: none.
115pub const READ_PHASE_MERGE: &str = "cqlite.read.phase.merge";

117/// `cqlite.reader.fds.open` — gauge `{fd}` (issue #1707).
118///
119/// OS file descriptors the SSTable READERS currently hold open, reported BY the
120/// readers themselves: a process-wide atomic incremented at each site that really
121/// mints a descriptor (a scan source's buffered/`O_DIRECT` handle, a positional
122/// reader's handle, a reader cold-open) and decremented in the matching `Drop`.
123///
124/// **It counts descriptors, so an mmap-backed source contributes 0** — `Mapped`
125/// sources hold a mapping, not an fd, and an `Arc` clone of an existing handle is
126/// not a new descriptor. Neither is invented as a number here.
127///
128/// **Healthy vs alarming**: rises with concurrent scans and falls as they complete
129/// (there is no reader pool, by #815 design: each scan opens its own handles);
130/// a level that climbs toward the process `ulimit -n` is the `EMFILE` pressure this
131/// gauge exists to make visible BEFORE an open fails.
132///
133/// DISTINCT from [`super::PROC_FDS`], and the difference is the point: `PROC_FDS` is the
134/// PROCESS total sampled from `/proc/self/fd` (~2s cadence, Linux only), so it
135/// includes sockets, the WAL, and everything else. This gauge is the READER-OWNED
136/// subset, needs no `/proc`, and is exact at its update points. `PROC_FDS` minus
137/// this is roughly the non-reader footprint. **Attributes**: none.
138pub const READER_FDS_OPEN: &str = "cqlite.reader.fds.open";
