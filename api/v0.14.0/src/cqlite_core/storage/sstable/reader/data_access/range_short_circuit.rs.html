1//! First/last-key range short-circuit for point lookups (issue #1576, Epic C / C5).
2//!
3//! An SSTable's partitions occupy a contiguous slice of the token ring: everything
4//! sorts between the physically-first partition (`first_key`) and the
5//! physically-last (`last_key`). Cassandra persists those two bounds in `Summary.db`
6//! (`summary_reader.rs`), and [`SummaryReader::get_first_key`] /
7//! [`SummaryReader::get_last_key`] already parse them — but nothing consulted them,
8//! so every candidate SSTable paid bloom / `Index.db` / trie work even for a query
9//! key that provably cannot live in it.
10//!
11//! [`SSTableReader::partition_key_out_of_range`] closes that gap. When the query
12//! key sorts outside `[first_key, last_key]` the point read
13//! ([`SSTableReader::get_with_resolution`]) returns authoritative absence
14//! (`Ok(None)`) BEFORE any bloom check, `Index.db` probe, or BTI trie descent,
15//! recording one [`record_range_short_circuit`](crate::storage::sstable::read_work_counters::record_range_short_circuit).
16//!
17//! ## No-heuristics + no-false-miss (the load-bearing correctness property)
18//!
19//! The bound comes ONLY from authoritative metadata (`Summary.db`), never a guess.
20//! The comparison is performed in the index's OWN order domain — ascending Cassandra
21//! Murmur3 token, ties broken by unsigned-lexicographic key bytes — the exact
22//! ordering the on-disk partitions are sorted by and that
23//! [`sort_by_token_order`](super::model::sort_by_token_order) and the write engine's
24//! `DecoratedKey::cmp` use (spec §5, Appendix B §313). Comparing raw bytes
25//! alone would be WRONG (physical order is token order, not byte order) and could
26//! drop a present partition — the exact false-miss footgun the audit warns against.
27//! The bound is INCLUSIVE at both ends: a key equal to `first_key` or `last_key` is
28//! in range and is NEVER short-circuited.
29//!
30//! When no authoritative bound is available (no `Summary.db` — e.g. a BTI "da"
31//! reader, which has no Summary and whose trie is itself the authoritative presence
32//! oracle — or an empty endpoint), the check conservatively reports "cannot rule
33//! out" (`false`) and the normal presence path runs unchanged. It can therefore only
34//! ever turn a would-be miss into a cheaper miss; it can never manufacture one.
35//!
36//! ## Precondition: Murmur3 partitioner
37//!
38//! The token ordering above uses [`cassandra_murmur3_token`], so this short-circuit
39//! is correct ONLY for SSTables sorted by Cassandra's `Murmur3Partitioner` — the sole
40//! partitioner CQLite targets (Cassandra 5.0; see the version floor in `CLAUDE.md`).
41//! Under any other partitioner the on-disk partition order would follow a different
42//! token function, so tokenizing the query key and the `Summary.db` endpoints with
43//! Murmur3 could place a present key outside `[first_key, last_key]` and manufacture a
44//! false miss on this absence fast path. This is NOT a new assumption — it is exactly
45//! the invariant that
46//! [`sort_by_token_order`](super::model::sort_by_token_order) (and the write engine's
47//! `DecoratedKey::cmp`) already rely on; it is documented here because the comparison
48//! now gates an authoritative-absence return rather than only ordering results.
49
50use super::super::SSTableReader;
51use crate::util::cassandra_murmur3::cassandra_murmur3_token;
52
53impl SSTableReader {
54    /// Return `true` iff `key` provably sorts OUTSIDE this SSTable's authoritative
55    /// `[first_key, last_key]` partition-key bound, so the partition is definitely
56    /// absent and the caller may skip all presence work.
57    ///
58    /// Returns `false` (cannot rule out) when no authoritative bound is available
59    /// (`Summary.db` absent, e.g. a BTI reader) or an endpoint is empty. See the
60    /// module docs for the no-false-miss contract: the comparison is in Cassandra
61    /// token order (Murmur3 token, unsigned-byte tiebreak), inclusive at both ends.
62    ///
63    /// Precondition: the SSTable is sorted by Cassandra's `Murmur3Partitioner` (the
64    /// only partitioner CQLite targets — Cassandra 5.0). See the module docs.
65    pub fn partition_key_out_of_range(&self, key: &[u8]) -> bool {
66        let Some(summary) = self.summary_reader.as_ref() else {
67            // No Summary.db → no authoritative bound (BTI readers, or a BIG reader
68            // whose Summary failed to load). Conservatively cannot rule out.
69            return false;
70        };
71
72        let first = summary.get_first_key();
73        let last = summary.get_last_key();
74        if first.is_empty() || last.is_empty() {
75            // A degenerate/absent endpoint cannot bound the ring slice safely.
76            return false;
77        }
78
79        // Authoritative on-disk partition order: ascending Murmur3 token, ties broken
80        // by unsigned-lexicographic key bytes. `key` (the raw serialized partition
81        // key) and the Summary endpoints share this domain, so tokenizing each and
82        // comparing the (token, bytes) tuple reproduces `DecoratedKey.compareTo`
83        // exactly. Inclusive bound: `< first` OR `> last` is out of range; equality
84        // with either endpoint is in range.
85        //
86        // The two endpoint tokens are IMMUTABLE for the reader's lifetime, so they
87        // are computed ONCE at open and cached in `endpoint_tokens` (issue #1576,
88        // Epic C/C5 perf finding); the hot path only hashes the QUERY key. The
89        // cached tokens are byte-identical to `cassandra_murmur3_token(first/last)`.
90        // The `unwrap_or_else` is a defensive recompute that never runs on the
91        // armed path (`endpoint_tokens` is `Some` exactly when Summary.db is present
92        // with two non-empty endpoints, which the guards above already established).
93        let (first_token, last_token) = self.endpoint_tokens.unwrap_or_else(|| {
94            (
95                cassandra_murmur3_token(first),
96                cassandra_murmur3_token(last),
97            )
98        });
99        let key_token = cassandra_murmur3_token(key);
100
101        (key_token, key) < (first_token, first) || (key_token, key) > (last_token, last)
102    }
103}
