1//! Observability foundation (epic #1031, issues #1032 + #1038).
2//!
3//! This module is the single shared foundation every other observability issue
4//! builds on. It owns OpenTelemetry initialisation, the `CQLITE_OTEL_*` config,
5//! the metric-naming [`catalog`], the error-rate schema ([`ObsErrorCategory`] +
6//! [`record_error`]), and graceful shutdown — and it is designed so that
7//! **instrumentation call sites are identical whether or not the
8//! `observability` feature is enabled.** When the feature is off, every helper
9//! here compiles to a no-op and `cargo tree -p cqlite-core` links no
10//! OpenTelemetry crates.
11//!
12//! # The contract for downstream issues (#1033–#1043)
13//!
14//! Downstream code MUST go through this module rather than touching
15//! `opentelemetry`/`tracing-opentelemetry` directly, so telemetry stays
16//! consistent and zero-cost-when-off:
17//!
18//! **Initialisation (CLI #1033, Flight #1041, bindings #1039/#1040):**
19//! ```ignore
20//! let cfg = observability::ObservabilityConfig::from_env();
21//! let _guard = observability::init(cfg)?;            // RAII; flushes on drop
22//! // compose the tracing layer into your own subscriber (feature-gated):
23//! # #[cfg(feature = "observability")]
24//! tracing_subscriber::registry()
25//!     .with(tracing_subscriber::fmt::layer())
26//!     .with(observability::tracing_layer())
27//!     .init();
28//! ```
29//!
30//! **Spans (read/query/write/compaction #1034–#1037):** use the ordinary
31//! `tracing` macros (`#[tracing::instrument]`, `tracing::info_span!`) — they are
32//! always available and the OTel layer bridges them when active. Do NOT create
33//! per-cell spans on hot paths; aggregate with metrics instead.
34//!
35//! **Metrics:** call [`add_counter`], [`record_histogram`], [`record_gauge`]
36//! with a name from [`catalog`] and bounded [`Attr`] attributes whose keys come
37//! from [`catalog::attr`]:
38//! ```ignore
39//! use cqlite_core::observability::{self as obs, catalog, AttrValue};
40//! obs::add_counter(catalog::READ_ROWS, n, &[(catalog::attr::SSTABLE_FORMAT, "bti".into())]);
41//! obs::record_histogram(catalog::QUERY_DURATION, elapsed.as_secs_f64(), &[]);
42//! ```
43//!
44//! **Errors (#1038):** at every boundary instrumented by #1034–#1037, call
45//! [`record_error`] when an error escapes — it increments
46//! [`catalog::ERRORS_TOTAL`] keyed by the bounded `{category, subsystem}` label
47//! set and marks the active span errored. Never attach the raw error message.
48//!
49//! # Why was this query slow? (issue #1707)
50//!
51//! [`catalog::READ_DURATION`] tells you a read was slow. These four histograms tell
52//! you WHERE the time went, so the next step is a decision rather than a profiler:
53//!
54//! 1. **Localise with `cqlite.read.phase.*`.** One sample per phase per completed
55//!    scan — [`catalog::READ_PHASE_IO`], [`catalog::READ_PHASE_DECOMPRESS`],
56//!    [`catalog::READ_PHASE_DECODE`], [`catalog::READ_PHASE_MERGE`]. Compare them
57//!    against EACH OTHER:
58//!    * **io dominant** → disk / page-cache bound (cold storage, evicted cache, a
59//!      network filesystem). Decode and merge tuning cannot help this read.
60//!    * **decompress dominant** → chunk length / compressor choice, or the same
61//!      chunks being decompressed repeatedly (a decompressed-chunk cache too small
62//!      for the scan's window).
63//!    * **decode dominant** → normally HEALTHY on a warm scan (decode is the CPU
64//!      work of a read). Suspicious only when it grows relative to the rows
65//!      DELIVERED: wide partitions, many collection/UDT cells, or a schema-less
66//!      fallback decode.
67//!    * **merge dominant** → too many overlapping generations, or heavy reconcile
68//!      (tombstones, LWW collapse). Cross-check [`catalog::COMPACTION_LAG`]; the
69//!      recv-wait is already excluded, so this really is merge work and not a
70//!      producer starving.
71//! 2. **Read the ABSENCES, they are informative.** A phase that never ran records NO
72//!    sample rather than `0.0`: no `decompress` series means the SSTable is
73//!    uncompressed (the #1406 write-surface shape), and no `merge` series means the
74//!    read had a single generation. Absence is a fact about the read; `0.0` would be
75//!    a claim that a measurement was taken.
76//! 3. **Know which surfaces are instrumented before you read an absence.** The
77//!    phases come from the STREAMING scan surfaces and the streaming
78//!    cross-generation merge. The materializing `SSTableManager::scan`, the BIG
79//!    reverse-clustering scan, the BTI trie walk, point reads and compaction reads
80//!    emit [`catalog::READ_DURATION`] with NO phase series at all — for those, an
81//!    empty breakdown means NOT MEASURED, never "fast". The full list, and why
82//!    instrumenting them needs async-safe propagation rather than another seam, is in
83//!    [`read_phase`]'s "Coverage boundary" section.
84//! 4. **Check fd pressure.** [`catalog::READER_FDS_OPEN`] is what the readers hold
85//!    (exact, every platform, no `/proc`); [`catalog::PROC_FDS`] is the whole process
86//!    (sampled ~2s, Linux). A reader level climbing toward `ulimit -n` explains
87//!    latency that is really queueing behind failing/retried opens — and it is
88//!    visible BEFORE the first `EMFILE`. `PROC_FDS` minus the reader level is roughly
89//!    the non-reader footprint (sockets, WAL).
90//! 5. **Check startup / durability stalls.** [`catalog::WAL_SIZE`] should saw-tooth;
91//!    a level that only climbs means flushes are not keeping up, and next open's
92//!    [`catalog::WAL_RECOVERY_DURATION`] grows with it. A slow FIRST query after a
93//!    restart is usually WAL recovery, not the read path.
94//!
95//! **The accounting caveat, and it matters for step 1:** the read pipeline is
96//! CONCURRENT — an IO/decompress feed thread, a blocking parse thread, a merge
97//! producer thread — so the phases OVERLAP in wall-clock and DO NOT sum to
98//! `read.duration`. Their sum can even exceed it. They are per-phase TOTALS for
99//! attribution ("which phase dominates, and how did that move between two runs?"),
100//! never a decomposition of latency, and a dashboard that stacks them as a
101//! breakdown of wall time will mislead. Same caveat as the #2819 `stream_*`
102//! sub-phases.
103//!
104//! # Always-compiled vs feature-gated
105//!
106//! [`catalog`], [`config`], the [`ObsErrorCategory`] taxonomy, and the helper
107//! signatures here are ALWAYS compiled (they pull in no OTel types), so call
108//! sites and tests build in any configuration. Only the exporter/runtime wiring
109//! ([`otel`]) is gated behind `observability`.

174/// A bounded attribute value for catalog metrics.
175///
176/// Mirrors the small set of types OpenTelemetry attributes accept, but is always
177/// available regardless of the `observability` feature so instrumentation call
178/// sites compile identically when telemetry is off. Keep values bounded
179/// (prefer [`AttrValue::StaticStr`] / numbers); never feed unbounded data such
180/// as raw error messages, partition keys, or full query text.
181#[derive(Debug, Clone)]
182pub enum AttrValue {
183    /// An owned string. Use only for genuinely bounded values.
184    Str(String),
185    /// A `&'static str` — the preferred, allocation-free form.
186    StaticStr(&'static str),
187    /// A signed integer.
188    Int(i64),
189    /// A floating-point value.
190    Float(f64),
191    /// A boolean.
192    Bool(bool),
193}
194
195impl From<&'static str> for AttrValue {
196    fn from(v: &'static str) -> Self {
197        AttrValue::StaticStr(v)
198    }
199}
200impl From<String> for AttrValue {
201    fn from(v: String) -> Self {
202        AttrValue::Str(v)
203    }
204}
205impl From<i64> for AttrValue {
206    fn from(v: i64) -> Self {
207        AttrValue::Int(v)
208    }
209}
210impl From<u64> for AttrValue {
211    fn from(v: u64) -> Self {
212        AttrValue::Int(v as i64)
213    }
214}
215impl From<f64> for AttrValue {
216    fn from(v: f64) -> Self {
217        AttrValue::Float(v)
218    }
219}
220impl From<bool> for AttrValue {
221    fn from(v: bool) -> Self {
222        AttrValue::Bool(v)
223    }
224}

226/// A single bounded metric attribute: a `&'static str` key (always from
227/// [`catalog::attr`]) paired with a bounded [`AttrValue`].
228pub type Attr = (&'static str, AttrValue);
229
230#[cfg(feature = "observability")]
231fn to_key_values(attrs: &[Attr]) -> Vec<opentelemetry::KeyValue> {
232    use opentelemetry::{KeyValue, Value};
233    attrs
234        .iter()
235        .map(|(k, v)| {
236            let value = match v {
237                AttrValue::Str(s) => Value::from(s.clone()),
238                AttrValue::StaticStr(s) => Value::from(*s),
239                AttrValue::Int(i) => Value::from(*i),
240                AttrValue::Float(f) => Value::from(*f),
241                AttrValue::Bool(b) => Value::from(*b),
242            };
243            KeyValue::new(*k, value)
244        })
245        .collect()
246}

248/// Add `value` to the monotonic counter identified by a [`catalog`] name, with
249/// bounded [`Attr`] attributes. No-op (and zero-cost) when the `observability`
250/// feature is off.
251#[inline]
252pub fn add_counter(name: &'static str, value: u64, attrs: &[Attr]) {
253    #[cfg(feature = "observability")]
254    {
255        if otel::metrics_active() {
256            otel::add_counter(name, value, &to_key_values(attrs));
257        } else {
258            let _ = (name, value, attrs);
259        }
260    }
261    #[cfg(not(feature = "observability"))]
262    {
263        let _ = (name, value, attrs);
264    }
265}

320/// Record an error that escaped a critical section (issue #1038).
321///
322/// Increments [`catalog::ERRORS_TOTAL`] keyed by the bounded
323/// `{cqlite.error.category, cqlite.subsystem}` label set and marks the active
324/// span as errored. `subsystem` is a `&'static str` (e.g. `"reader"`,
325/// `"query"`, `"write"`, `"compaction"`) so its value space stays bounded. The
326/// raw error message is never recorded. No-op when the `observability` feature
327/// is off.
328#[inline]
329pub fn record_error(err: &Error, subsystem: &'static str) {
330    #[cfg(feature = "observability")]
331    {
332        if otel::metrics_active() {
333            let attrs = [
334                opentelemetry::KeyValue::new(
335                    catalog::attr::ERROR_CATEGORY,
336                    err.obs_category().as_str(),
337                ),
338                opentelemetry::KeyValue::new(catalog::attr::SUBSYSTEM, subsystem),
339            ];
340            otel::add_counter(catalog::ERRORS_TOTAL, 1, &attrs);
341            otel::mark_span_error(err.obs_category());
342        } else {
343            let _ = (err, subsystem);
344        }
345    }
346    #[cfg(not(feature = "observability"))]
347    {
348        let _ = (err, subsystem);
349    }
350}

352/// Record an error into [`catalog::ERRORS_TOTAL`] with EXTRA bounded attributes
353/// beyond the canonical `{cqlite.error.category, cqlite.subsystem}` pair.
354///
355/// Identical to [`record_error`] but appends the caller-supplied `extra`
356/// attributes to the same single counter increment (and still marks the active
357/// span errored with the derived category). The extra keys MUST be bounded
358/// (closed value sets), e.g. the Flight `do_get` abort taxonomy's
359/// `cqlite.flight.abort_reason` (issue #2681) — never a raw message, ticket, or
360/// key. No-op when the `observability` feature is off.
361#[inline]
362pub fn record_error_with_attrs(err: &Error, subsystem: &'static str, extra: &[Attr]) {
363    #[cfg(feature = "observability")]
364    {
365        if otel::metrics_active() {
366            let mut attrs = to_key_values(extra);
367            attrs.push(opentelemetry::KeyValue::new(
368                catalog::attr::ERROR_CATEGORY,
369                err.obs_category().as_str(),
370            ));
371            attrs.push(opentelemetry::KeyValue::new(
372                catalog::attr::SUBSYSTEM,
373                subsystem,
374            ));
375            otel::add_counter(catalog::ERRORS_TOTAL, 1, &attrs);
376            otel::mark_span_error(err.obs_category());
377        } else {
378            let _ = (err, subsystem, extra);
379        }
380    }
381    #[cfg(not(feature = "observability"))]
382    {
383        let _ = (err, subsystem, extra);
384    }
385}

387/// Mark the active span as errored WITHOUT counting the failure (issue #1704).
388///
389/// [`record_error`] does TWO things: it increments [`catalog::ERRORS_TOTAL`] and it
390/// marks the active span errored. Those have different owners. The COUNT belongs to
391/// the operation — exactly one per user-visible failure, which is why an inner step
392/// whose caller records must not increment. The SPAN belongs to the call that opened
393/// it, and an inner step that returns `Err` under an unmarked span reports a
394/// successful-looking span for a failed operation.
395///
396/// Suppressing the whole of `record_error` therefore over-suppresses. This is the
397/// span-only half, for a call site that defers only the counter. Gated identically to
398/// [`record_error`] so the marked/unmarked decision cannot diverge between the two.
399#[inline]
400pub fn mark_span_error(err: &Error) {
401    #[cfg(feature = "observability")]
402    {
403        if otel::metrics_active() {
404            otel::mark_span_error(err.obs_category());
405        } else {
406            let _ = err;
407        }
408    }
409    #[cfg(not(feature = "observability"))]
410    {
411        let _ = err;
412    }
413}

415/// Convenience: run a `Result`-returning closure and [`record_error`] on the
416/// `Err` path, returning the result unchanged. Lets call sites instrument an
417/// operation without restructuring their error handling.
418#[inline]
419pub fn record_result<T>(subsystem: &'static str, result: Result<T>) -> Result<T> {
420    if let Err(e) = &result {
421        record_error(e, subsystem);
422    }
423    result
424}

426/// Parent a `tracing` span under a remote trace described by a W3C
427/// [`traceparent`](https://www.w3.org/TR/trace-context/#traceparent-header)
428/// header string (issues #1039/#1040/#1041).
429///
430/// Hosts (the Python/Node bindings, the Flight server) frequently receive an
431/// incoming `traceparent` from a caller's tracer and want the per-call CQLite
432/// span to attach to that remote trace. This helper extracts the W3C trace
433/// context with the standard [`TraceContextPropagator`] and sets it as the
434/// parent of `span` via `tracing-opentelemetry`'s `set_parent`.
435///
436/// It is always callable: when the `observability` feature is off — or when
437/// `traceparent` is `None`/empty/unparseable — it is a no-op, so call sites
438/// stay identical across builds. Pass the per-open or per-call traceparent
439/// straight from the binding boundary; never synthesise one.
440#[inline]
441pub fn set_span_parent_from_traceparent(span: &tracing::Span, traceparent: Option<&str>) {
442    #[cfg(feature = "observability")]
443    otel::set_span_parent_from_traceparent(span, traceparent);
444    #[cfg(not(feature = "observability"))]
445    {
446        let _ = (span, traceparent);
447    }
448}

468/// Initialise observability from `cfg`. When the `observability` feature is
469/// disabled this is a no-op (no OTel wiring) that returns an inert
470/// [`ObservabilityGuard`], so callers (CLI, Flight, bindings) can call it
471/// unconditionally.
472///
473/// It STILL plumbs `cfg.verify_presence_oracle` into the presence-oracle
474/// false-negative verification switch (issue #2163, roborev r4): that switch is
475/// an always-compiled storage-layer knob, independent of whether the OTel export
476/// stack is linked, so a config-only build without the `observability` feature
477/// can still enable the confirmation-scan correctness check (its counter emit is
478/// simply a no-op in that build, per the module's zero-cost-when-off contract).
479///
480/// # Observability honesty (issue #1702, epic #1686)
481///
482/// When `cfg.enabled` is `true` this build CANNOT export anything, so it emits
483/// ONE `WARN` naming the knob, the missing cargo feature and the consequence.
484/// Without it, `CQLITE_OTEL_ENABLED=1` is a completely silent no-op and an
485/// operator cannot tell "collector down / endpoint misconfigured" from "this
486/// binary was built without the feature". It stays a warning, never an error:
487/// degraded-but-running is the correct behavior — the defect was VISIBILITY.
488#[cfg(not(feature = "observability"))]
489#[inline]
490pub fn init(cfg: ObservabilityConfig) -> Result<ObservabilityGuard> {
491    crate::storage::sstable::reader::presence_verification::apply_config(
492        cfg.verify_presence_oracle,
493    );
494
495    // Issue #1702. Emitted with `tracing::warn!`, not the `log` crate's `warn!`
496    // as the issue text spells it (that literal spelling is deliberately avoided
497    // here: the `logging_facade_tracing` guard scans this directory textually and
498    // is not comment-aware, so writing it out trips the residual-macro check):
499    // `cqlite-core` has no `log` dependency at all — its facade
500    // is `tracing` (the #1706 log->tracing migration) — and `tracing` satisfies
501    // the same constraint, since every host composes the fmt layer onto STDERR
502    // so stdout stays clean for `--out json/csv` (issue #129).
503    //
504    // Fired unconditionally on each `init` call rather than behind a `Once`.
505    // Every in-repo caller invokes `init` exactly once per process (CLI
506    // `run_main`, the Flight server, `init_once` in both bindings), so "once at
507    // init" is "once per process" for them — but that is a CONVENTION of those
508    // callers, NOT something this function enforces. `cqlite-core` is a library:
509    // an out-of-tree embedder that calls `init` per connection or per request
510    // with `enabled = true` on a default build gets one WARN per call. A `Once`
511    // would bound that, at the cost of making the warning unobservable to the
512    // second of two tests in one binary; if per-call spam ever shows up in the
513    // field, that is the tradeoff to revisit.
514    //
515    // `cfg.enabled` is the ONLY field a feature-off build silently discards, so
516    // it is the only one that warns. `verify_presence_oracle` is genuinely
517    // honored above. The remaining `CQLITE_OTEL_*` vars (endpoint, protocol,
518    // service name/version, sampling ratio, timeout) are all subordinate to
519    // `enabled`: with `enabled == false` they change nothing even in a
520    // feature-ON build, so a separate warning for them would be noise, not
521    // honesty. This omission is deliberate, not an oversight.
522    //
523    // Wording note: `init` receives an already-RESOLVED config and cannot know
524    // which source enabled it (the CLI accepts `CQLITE_OTEL_ENABLED`, the
525    // `--otel-enabled` flag, and a config file, all feeding this one field), so
526    // the message must not assert that the env var is set. It names the env var
527    // as the common spelling — operators grep for it — without claiming
528    // provenance.
529    //
530    // The warning carries NO fields, deliberately (roborev r2, blocker). An
531    // earlier version attached `requested_endpoint = %cfg.endpoint`, i.e. a
532    // user-controlled URL rendered verbatim by the fmt layer. That is two defect
533    // classes in one field: an endpoint of the form
534    // `http://user:pass@collector:4317` writes credentials into the log, and an
535    // endpoint containing newlines/control characters can FORGE additional log
536    // lines. Neither is sanitized here — the field is simply gone, which removes
537    // the class instead of filtering it. Nothing diagnostic is lost: this build
538    // never contacts the endpoint, and the message says so.
539    if cfg.enabled {
540        tracing::warn!(
541            "OpenTelemetry export is ENABLED in configuration (CQLITE_OTEL_ENABLED / \
542             --otel-enabled / config file) but this binary was built WITHOUT the \
543             `observability` cargo feature: OpenTelemetry is compiled out, so NO \
544             metrics and NO traces will be emitted and the OTLP endpoint is never \
545             contacted — this is NOT a collector or endpoint problem. Rebuild with \
546             `--features observability` to export telemetry, or disable \
547             OpenTelemetry (e.g. CQLITE_OTEL_ENABLED=0, or drop --otel-enabled) \
548             to silence this warning."
549        );
550    }
551
552    Ok(ObservabilityGuard { _private: () })
553}
