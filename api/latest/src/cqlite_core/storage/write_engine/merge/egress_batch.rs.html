1//! BATCHED producer→consumer fan-in for the k-way merge egress channel (issue
2//! #2820).
3//!
4//! # The defect this closes
5//!
6//! Every merge run is fed by a detached producer THREAD over a bounded
7//! `sync_channel` (`producer_iter` for the path-based shape, `from_readers` for
8//! the shared-reader shape). `from_readers::forward_row` used to `send` ONE
9//! message per ROW, so a merged row cost one cross-thread park/wake pair.
10//! Phase-0 profiling of the single-stream Flight scan measured that hand-off at
11//! **49.9% of single-stream CPU, ~94% of it kernel park/wake** — the largest
12//! single item in the profile, and pure overhead: nothing about the merge needs
13//! per-row synchronisation.
14//!
15//! The fix is the one issue #1592/#1143 already applied to the windowed scan's
16//! blocking→async boundary (`sstable::reader::scan_stream_windowed`): accumulate
17//! rows into a `Vec` and send ONE message per batch, amortising the wake
18//! ~[`BATCH_EMIT_ROWS_MERGE`]× while keeping every ordering, backpressure and
19//! terminator guarantee. Order is preserved (rows are pushed and drained FIFO,
20//! batches sent in order); the consumer holds ONE received batch and hands out
21//! one entry per `next()`.
22//!
23//! # Capacity is a ROW budget; the channel counts MESSAGES (the #2765 seam)
24//!
25//! `egress_budget`'s whole vocabulary is in ROWS — `EGRESS_ROW_BUDGET`,
26//! `MIN_CAP`, `MAX_CAP` (= `STREAMING_CHANNEL_CAPACITY`) — and stays that way:
27//! it is what bounds the aggregate buffered working set across concurrent
28//! merges. So the row budget is converted to a MESSAGE capacity at the
29//! `sync_channel` call site by [`message_capacity_for_rows`]. Getting that
30//! conversion wrong is the one catastrophic failure mode of this change: an
31//! UNCONVERTED capacity would budget 256 *batches* — `256 × 256 = 65_536`
32//! entries per source, times `K` sources, times every active merge — a 256×
33//! blow-up of resident rows straight through the memory target.
34//!
35//! ## The batch size is bounded BY the row capacity, or #2765 becomes inert
36//!
37//! The conversion alone is not enough, and the first revision of this change got
38//! it wrong. Over the whole REACHABLE range of `egress_budget` row capacities
39//! (`[MIN_CAP, MAX_CAP]` = `[8, 256]`, `MAX_CAP` being
40//! `STREAMING_CHANNEL_CAPACITY` itself) `rows_cap.div_ceil(256)` is `1`, so
41//! [`message_capacity_for_rows`] is floored at [`MIN_MSG_CAP`] = 2 for EVERY
42//! setting the adaptive budget can produce. If the per-batch limit were then a
43//! flat [`BATCH_EMIT_ROWS_MERGE`], resident rows would be a CONSTANT `4 × 256 =
44//! 1024` per source at every setting — i.e. at the documented throttled floor
45//! (`rows_cap = 8`) a source channel would hold 1024 rows where the pre-change
46//! code held 8, a **128×** increase, and `egress_channel_capacity_for` would have
47//! ZERO effect on resident memory. That defeats the #2765/#2600/#2367 aggregate
48//! bound this module is co-designed with.
49//!
50//! So the ramp's ceiling is [`batch_limit_ceiling`] = `min(rows_cap,
51//! BATCH_EMIT_ROWS_MERGE)`, and every derived bound is a MULTIPLE of the row
52//! capacity rather than a constant. Three DISTINCT quantities follow, and they
53//! are routinely confused — each has its own function here, and callers must pick
54//! the one that answers their question:
55//!
56//! | quantity | function | value |
57//! |---|---|---|
58//! | channel-resident (what the #2419 depth gauge can reach) | [`rows_resident_in_channel`] | `msg_cap × ceiling` = `2 × rows_cap` |
59//! | total in-flight (the MEMORY bound) | [`max_inflight_rows`] | `(msg_cap + 2) × ceiling` = `4 × rows_cap` |
60//! | cold-start fill (what a fixture must exceed to PARK a producer) | [`rows_in_full_channel`] `+ ceiling + 1` | ramp sum, far below either |
61//!
62//! At the default `rows_cap = 256` that is 512 / 1024; at the throttled floor
63//! `rows_cap = 8` it is 16 / 32. The throttle therefore keeps a 32× dynamic
64//! range instead of being a constant, and the 4× multiplier over the pre-change
65//! flat capacity is uniform at EVERY setting.
66//!
67//! [`max_inflight_rows`] is the resulting explicit TOTAL IN-FLIGHT bound (never
68//! called "resident": that word is reserved for the strictly smaller
69//! channel-resident figure the gauge can reach), the
70//! sibling of `scan_stream_windowed::MAX_INFLIGHT_BATCH_ROWS` and derived the
71//! same way (channel-resident + consumer-held + producer-blocked-in-send).
72//!
73//! # A row bound is not a memory bound: the BYTE budget
74//!
75//! A row count says nothing about bytes — 1024 rows is a few hundred KiB of
76//! Flight scan rows and ~49 MiB of 48 KiB blob rows. The `#827` merge memory
77//! fixture is exactly that second shape (4 sources × 800 rows × 48 KiB), and a
78//! purely row-bounded 4× would put `4 × 4 × 256 × 48 KiB ≈ 196 MiB` of
79//! channel-resident payload against a 128 MiB budget. So the accumulator ALSO
80//! carries a byte budget ([`BATCH_EMIT_BYTES_MERGE`]) and flushes on whichever
81//! bound trips FIRST. Sizes come from `RunReader::estimate_entry_size`, the same
82//! estimator the merge's own read-ahead buffer is bounded by — reused rather than
83//! re-derived so the two cannot drift, and adequate for this purpose for the same
84//! reason it is adequate there: it counts the heap actually owned by the
85//! `MergeEntry` (key bytes, per-cell column names, per-value payload) with a
86//! per-variant approximation for values whose size is not carried inline. It is
87//! an ESTIMATE, not an exact `size_of` closure over the graph, so the byte bound
88//! is approximate in the same direction the read-ahead bound already is; what it
89//! buys is that the bound tracks row SIZE at all, which no row count can.
90//!
91//! The threshold is checked AFTER the push, so one batch may reach
92//! `BATCH_EMIT_BYTES_MERGE + one entry` — a single row larger than the whole
93//! budget is still sent (never split, never dropped). The honest per-source
94//! byte bound is therefore `(msg_cap + 2) × (BATCH_EMIT_BYTES_MERGE +
95//! max_row_bytes)`.
96//!
97//! # First-row latency: the ramp, and the two alternatives rejected
98//!
99//! PURE batching regresses first-row latency — a sparse or sub-batch result set
100//! would emit nothing until the walk ended. That is #1143's own recorded lesson
101//! (`scan_stream_windowed`'s per-chunk flush comment), so it is designed for
102//! here rather than rediscovered:
103//!
104//! * The windowed scan flushes its pending tail at every CHUNK boundary. That
105//!   is NOT available here: this module's emit funnel is a per-ROW callback with
106//!   no chunk/window event to hang a flush on.
107//! * Flushing per PARTITION boundary is available (the callback carries the
108//!   partition key) and was REJECTED: the dominant fixture/table shape in this
109//!   repo is one row per partition (`test_basic/simple_table` = 999 partitions ×
110//!   1 row), where a per-partition flush degenerates to one message per row —
111//!   i.e. it would silently disable the entire optimisation for exactly the
112//!   workload that motivated it.
113//!
114//! So the batch limit RAMPS: the first batch of a run carries
115//! [`FIRST_BATCH_EMIT_ROWS`] = 1 row (the first row is therefore NEVER delayed
116//! by batching), and each subsequent flush doubles the limit up to
117//! [`BATCH_EMIT_ROWS_MERGE`]. A consumer that wants the first `K` rows waits for
118//! `O(K)` rows to be produced, never for a full batch, while a full scan pays
119//! only `log2(BATCH_EMIT_ROWS_MERGE)` = 8 extra messages per run before the
120//! limit saturates. The pending tail is ALSO flushed before the run's terminator
121//! (`from_readers`), so a sub-batch result set never waits for a full batch.

130/// Rows accumulated into ONE egress channel message once the ramp has saturated
131/// (issue #2820). Mirrors `scan_stream_windowed::BATCH_EMIT_ROWS`, and for the
132/// same reason: a modest value keeps the per-batch heap small (a batch holds at
133/// most this many already-owned `MergeEntry` values — the same values the
134/// pre-change code handed over one at a time) while amortising the cross-thread
135/// wake ~256×.
136pub(super) const BATCH_EMIT_ROWS_MERGE: usize = 256;
137
138/// Rows in the FIRST batch of a run; the limit doubles per flush up to
139/// [`BATCH_EMIT_ROWS_MERGE`]. `1` so batching NEVER delays the first row of a
140/// run — see the module doc's first-row-latency section.
141pub(super) const FIRST_BATCH_EMIT_ROWS: usize = 1;
142
143/// Minimum MESSAGE capacity of an egress `sync_channel`, whatever the row budget
144/// converts to. `2` (matching `scan_stream_windowed::BATCH_CHANNEL_CAP`): a
145/// capacity-1 bounded channel serialises producer and consumer — the producer
146/// can hold no batch while the consumer drains one — which is the
147/// producer/consumer overlap the whole streaming architecture exists for.
148pub(super) const MIN_MSG_CAP: usize = 2;
149
150/// Estimated BYTES accumulated into ONE egress channel message before it is
151/// flushed regardless of row count (issue #2820) — the row-size-independent half
152/// of the bound, see the module doc.
153///
154/// `1 MiB`. Chosen so the byte bound is INERT for ordinary merge rows and
155/// governs only for large ones: at a few hundred bytes per row a full
156/// [`BATCH_EMIT_ROWS_MERGE`] batch is ~128 KiB, well under this, so the default
157/// row-bounded amortisation is unchanged; it engages above ~4 KiB/row average,
158/// where the row bound stops being a memory bound. The resulting per-source
159/// worst case is `(msg_cap + 2) × (this + max_row_bytes)` ≈ 4 MiB at the default
160/// message capacity — a bounded, row-size-independent term, versus the ~49 MiB
161/// per source a flat 1024-row bound implies for 48 KiB rows.
162pub(super) const BATCH_EMIT_BYTES_MERGE: usize = 1024 * 1024;
163
164/// Convert `egress_budget`'s per-channel ROW capacity into the MESSAGE capacity
165/// the bounded `sync_channel` is actually constructed with (issue #2820).
166///
167/// THE conversion of this change — see the module doc: the channel now carries
168/// batches, so passing a row budget straight to `sync_channel` would multiply
169/// resident rows by [`BATCH_EMIT_ROWS_MERGE`].
170pub(super) fn message_capacity_for_rows(rows_cap: usize) -> usize {
171    rows_cap.div_ceil(BATCH_EMIT_ROWS_MERGE).max(MIN_MSG_CAP)
172}
173
174/// The per-batch ROW ceiling for a run whose egress channel was budgeted
175/// `rows_cap` ROWS (issue #2820): `min(rows_cap, BATCH_EMIT_ROWS_MERGE)`.
176///
177/// THE line that keeps #2765's adaptive throttle effective — see the module doc's
178/// "bounded BY the row capacity" section. A flat [`BATCH_EMIT_ROWS_MERGE`]
179/// ceiling would make every derived resident bound a CONSTANT across the whole
180/// reachable capacity range.
181///
182/// Floored at `1` so a degenerate (0) row budget can never produce a 0-row batch
183/// limit, which would make the accumulator flush an empty batch per push.
184pub(super) fn batch_limit_ceiling(rows_cap: usize) -> usize {
185    rows_cap.clamp(1, BATCH_EMIT_ROWS_MERGE)
186}
187
188/// The next batch limit after a flush: double, capped at this run's
189/// `ceiling` ([`batch_limit_ceiling`]) — the ramp, see the module doc.
190fn next_batch_limit(current: usize, ceiling: usize) -> usize {
191    current.saturating_mul(2).min(ceiling)
192}
193
194/// Rows that can be resident IN the bounded channel itself for a run budgeted
195/// `rows_cap` ROWS (issue #2820): `msg_cap × ceiling`, i.e. `2 × rows_cap` over
196/// the reachable capacity range.
197///
198/// This — NOT [`max_inflight_rows`] — is the ceiling of the #2419
199/// `cqlite.merge.egress_channel_depth` gauge: that gauge is incremented on a
200/// successful `send` and decremented on the consumer's `recv`, so it counts
201/// neither the consumer-HELD batch (already decremented) nor the batch a
202/// producer is PARKED holding (never sent). Documenting the gauge's ceiling as
203/// the in-flight bound overstates it by exactly those two batches (2× at the
204/// shipped default), which is an operator-facing alert-threshold error.
205pub(super) fn rows_resident_in_channel(rows_cap: usize) -> usize {
206    message_capacity_for_rows(rows_cap).saturating_mul(batch_limit_ceiling(rows_cap))
207}
208
209/// Documented WORST-CASE rows the batching subsystem of ONE run may hold in
210/// flight ahead of a stalled consumer, for a channel budgeted `rows_cap` ROWS
211/// (issue #2820) — the sibling of `scan_stream_windowed::MAX_INFLIGHT_BATCH_ROWS`
212/// and derived exactly the same way. Three populations coexist at one instant,
213/// each up to [`batch_limit_ceiling`] rows:
214///
215/// 1. **Channel-resident** — the bounded channel is FULL: `msg_cap` messages
216///    ([`rows_resident_in_channel`]).
217/// 2. **Consumer-held** — the adapter `recv`'d one batch and is handing it out
218///    one entry per `next()`; it has LEFT the channel (+1).
219/// 3. **Producer-blocked-in-send** — the producer assembled its next full batch
220///    and is PARKED in `SyncSender::send`, still OWNING it because `send` moves
221///    the value only on success (+1).
222///
223/// The pending accumulator is NOT a fourth: once it reaches the limit it BECOMES
224/// (3) via that same `send`, and a parked producer accumulates nothing further.
225///
226/// Because the ceiling is bounded by `rows_cap`, this is `4 × rows_cap` at EVERY
227/// reachable setting — 1024 rows at the default 256, 32 at the throttled floor of
228/// 8 — a uniform 4× over the pre-batching flat capacity rather than a constant
229/// that would ignore the #2765 throttle entirely.
230///
231/// **This is a ROW bound and therefore NOT a memory bound on its own.** For a
232/// 48 KiB-row workload (the `#827` fixture shape) `4 × 256` rows would be ~49 MiB
233/// per source. The memory bound is the BYTE budget the accumulator enforces
234/// alongside it ([`BATCH_EMIT_BYTES_MERGE`]): per source, whichever of
235/// `(msg_cap + 2) × ceiling` rows and `(msg_cap + 2) × (BATCH_EMIT_BYTES_MERGE +
236/// max_row_bytes)` bytes binds first — ≈4 MiB at the default message capacity.
237pub(super) fn max_inflight_rows(rows_cap: usize) -> usize {
238    message_capacity_for_rows(rows_cap)
239        .saturating_add(2)
240        .saturating_mul(batch_limit_ceiling(rows_cap))
241}
242
243/// Worst-case estimated BYTES one run's batching subsystem may hold in flight
244/// (issue #2820) — the byte sibling of [`max_inflight_rows`], over the same three
245/// populations, each holding at most `BATCH_EMIT_BYTES_MERGE + max_row_bytes`
246/// (the threshold is checked after the push, so one oversized row can carry a
247/// batch past the budget).
248///
249/// `max_row_bytes` is the caller's own knowledge of its workload; there is no
250/// process-wide row-size bound to substitute for it.
251pub(super) fn max_inflight_bytes(rows_cap: usize, max_row_bytes: usize) -> usize {
252    message_capacity_for_rows(rows_cap)
253        .saturating_add(2)
254        .saturating_mul(BATCH_EMIT_BYTES_MERGE.saturating_add(max_row_bytes))
255}

257/// Rows a run's producer can place INTO a FULL egress channel budgeted
258/// `rows_cap` ROWS, FROM A COLD START (issue #2820) — the ramp sum over the
259/// channel's `msg_cap` slots.
260///
261/// Distinct from [`max_inflight_rows`], and both are needed: the ramp means the
262/// first `msg_cap` batches of a run are NOT full ones, so a producer whose
263/// consumer never steps (the backpressure fixtures of issues #2316/#2419/#2361)
264/// parks in `send` holding only this many rows — far below the saturated worst
265/// case. A test that derives its "the producer is genuinely backed up" threshold
266/// from the worst-case bound instead would wait for rows that, by construction,
267/// can never be sent.
268///
269/// **This is the CHANNEL's content only — a parked producer also OWNS the batch
270/// it is trying to hand over.** So a fixture that must observe the producer
271/// actually blocked needs
272/// `rows_in_full_channel(rows_cap) + batch_limit_ceiling(rows_cap) + 1` rows
273/// available, which is what every caller writes (`+ batch_emit_rows + 1` via the
274/// probe). The in-flight batch term is NOT folded in here because the two are
275/// separately meaningful: this is what the #2419 depth gauge can observe from a
276/// cold start, the extra batch is what the producer holds off-gauge.
277pub(super) fn rows_in_full_channel(rows_cap: usize) -> usize {
278    let ceiling = batch_limit_ceiling(rows_cap);
279    let mut limit = FIRST_BATCH_EMIT_ROWS.min(ceiling);
280    let mut rows = 0usize;
281    for _ in 0..message_capacity_for_rows(rows_cap) {
282        rows = rows.saturating_add(limit);
283        limit = next_batch_limit(limit, ceiling);
284    }
285    rows
286}

288/// DATA messages (batches) successfully sent into any merge egress channel since
289/// process start.
290static MESSAGES_SENT: AtomicU64 = AtomicU64::new(0);
291/// DATA entries carried by those messages (issue #2820): `MESSAGES_SENT` counts
292/// cross-thread wakes, this counts rows, and their ratio IS the fan-in
293/// amortisation the change buys.
294static ENTRIES_SENT: AtomicU64 = AtomicU64::new(0);
295/// Peak rows in any single sent batch since process start — the observable half
296/// of the per-batch cap invariant (`<= BATCH_EMIT_ROWS_MERGE`).
297static PEAK_BATCH_ROWS: AtomicUsize = AtomicUsize::new(0);
298
299/// Account one successfully sent batch of `entries` rows.
300///
301/// Called BEFORE the `SeqCst` egress-depth/`local_sent` stores at the send site,
302/// deliberately: an integration test establishes "the producer has sent N rows"
303/// by observing the SeqCst gauge and then asserts these counters by EXACT
304/// equality (`tests/issue_2419_egress_depth_gauge.rs`). Storing them after the
305/// gauge left no happens-before at all — the producer then parks in `send` with
306/// no further synchronisation, so a reader could see the gauge move and the
307/// counters still stale. Ordering these first makes the gauge store the release
308/// that publishes them.
309fn record_batch_sent(entries: usize) {
310    MESSAGES_SENT.fetch_add(1, Ordering::Relaxed);
311    ENTRIES_SENT.fetch_add(entries as u64, Ordering::Relaxed);
312    PEAK_BATCH_ROWS.fetch_max(entries, Ordering::Relaxed);
313}

315/// Doc-hidden integration-test probe (issue #2820): a snapshot of the
316/// process-global egress fan-in counters plus the batching constants they must
317/// be read against. Re-exported from `merge`.
318///
319/// Process-global, exactly like `work_counters` and the `#2765` active-merge
320/// hook: a DELTA assertion around one merge is valid only in a test binary with
321/// no concurrent merge (the counters are monotonic, so a concurrent merge can
322/// only ADD messages and entries — never make a batched run look per-row).
323#[doc(hidden)]
324#[derive(Debug, Clone, Copy, PartialEq, Eq)]
325pub struct EgressBatchProbe {
326    /// DATA messages (batches) sent into merge egress channels. The pre-#2820
327    /// code sent one per ROW, so `entries_sent` is exactly what this counter
328    /// would have read then — which is what makes the reduction measurable
329    /// without keeping a per-row code path alive to compare against.
330    pub messages_sent: u64,
331    /// DATA entries carried by those messages.
332    pub entries_sent: u64,
333    /// Peak rows observed in a single batch (must never exceed
334    /// [`Self::batch_emit_rows`]).
335    pub peak_batch_rows: usize,
336    /// [`BATCH_EMIT_ROWS_MERGE`] — the saturated per-batch row cap.
337    pub batch_emit_rows: usize,
338    /// [`FIRST_BATCH_EMIT_ROWS`] — the ramp's first-batch row limit.
339    pub first_batch_emit_rows: usize,
340    /// [`BATCH_EMIT_BYTES_MERGE`] — the per-batch estimated-BYTE budget, the
341    /// row-size-independent half of the bound (issue #2820).
342    pub batch_emit_bytes: usize,
343}

360    /// The MESSAGE capacity a channel built from the ROW capacity `rows_cap` gets
361    /// ([`message_capacity_for_rows`]).
362    pub fn message_capacity_for_rows(&self, rows_cap: usize) -> usize {
363        message_capacity_for_rows(rows_cap)
364    }
365
366    /// The per-batch ROW ceiling a run budgeted `rows_cap` ROWS uses
367    /// ([`batch_limit_ceiling`]) — bounded BY `rows_cap`, so a throttled budget
368    /// shrinks the batches too. Use this, not [`Self::batch_emit_rows`], wherever
369    /// a bound must hold at a NON-default capacity.
370    pub fn batch_limit_ceiling(&self, rows_cap: usize) -> usize {
371        batch_limit_ceiling(rows_cap)
372    }
373
374    /// Rows that can be resident IN the bounded channel for a run budgeted
375    /// `rows_cap` ROWS ([`rows_resident_in_channel`]) — the ceiling of the #2419
376    /// egress-depth GAUGE, which counts neither the consumer-held nor the
377    /// producer-parked batch. Strictly below [`Self::max_inflight_rows`].
378    pub fn rows_resident_in_channel(&self, rows_cap: usize) -> usize {
379        rows_resident_in_channel(rows_cap)
380    }
381
382    /// WORST-CASE resident rows of one run's batching subsystem for a channel
383    /// built from the ROW capacity `rows_cap` ([`max_inflight_rows`]). Lets a
384    /// memory/fixture-sizing test derive the bound from the shipped constants
385    /// instead of a literal that re-rots the moment either constant moves.
386    pub fn max_inflight_rows(&self, rows_cap: usize) -> usize {
387        max_inflight_rows(rows_cap)
388    }
389
390    /// WORST-CASE in-flight estimated BYTES for a run budgeted `rows_cap` ROWS
391    /// whose largest row estimates at `max_row_bytes`
392    /// ([`max_inflight_bytes`]) — the row-size-independent bound a memory
393    /// fixture must size against, since a row count alone bounds no memory.
394    pub fn max_inflight_bytes(&self, rows_cap: usize, max_row_bytes: usize) -> usize {
395        max_inflight_bytes(rows_cap, max_row_bytes)
396    }
397
398    /// Rows a producer can place into a FULL channel built from `rows_cap`, FROM
399    /// A COLD START ([`rows_in_full_channel`]) — the threshold the #2316/#2419
400    /// backed-up-merge fixtures must derive their "the producer is genuinely
401    /// blocked" premise from. CHANNEL content only; add
402    /// [`Self::batch_limit_ceiling`] `+ 1` for the batch a parked producer owns
403    /// (see [`Self::rows_that_park_the_producer`]).
404    pub fn rows_in_full_channel(&self, rows_cap: usize) -> usize {
405        rows_in_full_channel(rows_cap)
406    }
407
408    /// Rows a fixture must make available before its producer is GUARANTEED to be
409    /// parked in `send` on a channel budgeted `rows_cap` ROWS: the cold-start
410    /// channel fill, PLUS the full batch the parked producer still owns, plus one
411    /// more row it could not even accumulate.
412    ///
413    /// The one place this sum lives (issue #2820 review round 2): six #2316/#2419/
414    /// #2370/#2361 fixtures each wrote it out by hand, so the premise the probe
415    /// exists to make un-rottable was re-copied six times one level up.
416    pub fn rows_that_park_the_producer(&self, rows_cap: usize) -> usize {
417        rows_in_full_channel(rows_cap)
418            .saturating_add(batch_limit_ceiling(rows_cap))
419            .saturating_add(1)
420    }
421
422    /// The exact number of MESSAGES a run of `entries` rows sends at the ROW
423    /// capacity `rows_cap`: the ramp (`first_batch_emit_rows`, doubling to
424    /// [`Self::batch_limit_ceiling`]) followed by the pre-terminator tail flush.
425    /// Deterministic, so a send-count oracle can assert an EXACT expected count
426    /// rather than a hand-waved "fewer".
427    ///
428    /// Models the ROW bound only. A workload whose rows trip the BYTE budget
429    /// ([`Self::batch_emit_bytes`]) sends MORE messages than this, so it is a
430    /// lower bound there — never assert exact equality against it for large rows.
431    pub fn expected_messages_at(&self, rows_cap: usize, entries: u64) -> u64 {
432        let mut left = entries;
433        // `max(1)` on BOTH the seed and the step: a future `FIRST_BATCH_EMIT_ROWS`
434        // (or a zero ceiling) would otherwise make `take` 0 and spin this loop
435        // forever — a hang in a probe method used by tests.
436        let mut limit = (self.first_batch_emit_rows as u64).max(1);
437        let cap = (batch_limit_ceiling(rows_cap) as u64).max(1);
438        let mut messages = 0u64;
439        while left > 0 {
440            let take = limit.min(left);
441            left -= take;
442            messages += 1;
443            limit = limit.saturating_mul(2).min(cap);
444        }
445        messages
446    }
447
448    /// [`Self::expected_messages_at`] at the SATURATED ceiling
449    /// (`batch_emit_rows`), i.e. what a run at the DEFAULT/unthrottled row budget
450    /// sends. A run whose adaptive budget was squeezed sends more.
451    pub fn expected_messages(&self, entries: u64) -> u64 {
452        self.expected_messages_at(self.batch_emit_rows, entries)
453    }
454}

456/// Producer-side row accumulator for ONE run's egress channel (issue #2820).
457///
458/// Owns the pending `Vec<MergeEntry>` and the ramping batch limit, and is the
459/// ONLY place a `MergeMsg::Batch` is built — so the egress-depth accounting
460/// (`channel_depth` + the adapter's own `local_sent`, both in ENTRIES, issue
461/// #2419) happens at exactly one site, per successful send, for the whole batch.
462///
463/// Created per driven stream by `from_readers`, which MUST flush the pending
464/// tail before its producer thread sends a terminator: a row still in this
465/// accumulator when `Done` goes out is a LOST row (issue #3120's silent-short-read
466/// class, reintroduced through the back door).
467pub(super) struct EgressBatcher<'a> {
468    sender: &'a SyncSender<MergeMsg>,
469    /// This adapter's own sent-count in ENTRIES (issue #2419 roborev job 1733),
470    /// read post-join by `SSTableRowIteratorAdapter::drop` for the exact
471    /// reconcile residual — so it must be incremented by the BATCH LENGTH, never
472    /// by one per message.
473    local_sent: &'a AtomicI64,
474    pending: Vec<MergeEntry>,
475    /// Estimated heap bytes of `pending` (`RunReader::estimate_entry_size`),
476    /// accumulated per push and reset with it — the byte half of the flush
477    /// predicate, see the module doc.
478    pending_bytes: usize,
479    limit: usize,
480    /// This run's per-batch ROW ceiling, [`batch_limit_ceiling`] of the ROW
481    /// capacity its channel was budgeted. NOT a global constant: bounding the
482    /// batch by the run's own capacity is what keeps #2765's adaptive throttle
483    /// effective (module doc).
484    ceiling: usize,
485}
486
487impl<'a> EgressBatcher<'a> {
488    /// `rows_cap` is the merge-scoped adaptive ROW capacity
489    /// (`egress_budget`'s snapshot) this run's channel was built from — the SAME
490    /// value [`message_capacity_for_rows`] converted for the `sync_channel`. It
491    /// bounds the batch size, so both halves of the resident bound scale with the
492    /// throttle instead of one of them being a constant.
493    pub(super) fn new(
494        sender: &'a SyncSender<MergeMsg>,
495        local_sent: &'a AtomicI64,
496        rows_cap: usize,
497    ) -> Self {
498        let ceiling = batch_limit_ceiling(rows_cap);
499        let limit = FIRST_BATCH_EMIT_ROWS.min(ceiling);
500        Self {
501            sender,
502            local_sent,
503            pending: Vec::with_capacity(limit),
504            pending_bytes: 0,
505            limit,
506            ceiling,
507        }
508    }
509
510    /// Accumulate one converted row, flushing when EITHER the current ramp row
511    /// limit or the [`BATCH_EMIT_BYTES_MERGE`] byte budget is reached — whichever
512    /// trips first. `Break` means the consumer has dropped the channel.
513    ///
514    /// The byte half is what makes the bound row-SIZE-independent: at a few
515    /// hundred bytes per row it never trips and the row limit governs (so the
516    /// default amortisation is unchanged), while a 48 KiB-row workload flushes on
517    /// bytes long before 256 rows — the difference between a bounded ~4 MiB per
518    /// source and ~49 MiB.
519    pub(super) fn push(&mut self, entry: MergeEntry) -> ControlFlow<()> {
520        // Reuses the merge's OWN read-ahead-buffer estimator rather than a second
521        // size model, so the two accountings cannot drift (module doc).
522        self.pending_bytes = self
523            .pending_bytes
524            .saturating_add(super::RunReader::estimate_entry_size(&entry));
525        self.pending.push(entry);
526        if self.pending.len() >= self.limit || self.pending_bytes >= BATCH_EMIT_BYTES_MERGE {
527            self.flush()
528        } else {
529            ControlFlow::Continue(())
530        }
531    }
532
533    /// Send the pending rows as ONE message (a no-op when empty). Called for the
534    /// full-batch flush AND as the pre-terminator tail flush.
535    ///
536    /// The BLOCKING `send`, exactly as the pre-batching per-row code used: it is
537    /// what carries the backpressure that keeps peak memory independent of total
538    /// input size, now in units of batches (see [`max_inflight_rows`]).
539    pub(super) fn flush(&mut self) -> ControlFlow<()> {
540        if self.pending.is_empty() {
541            return ControlFlow::Continue(());
542        }
543        let next_limit = next_batch_limit(self.limit, self.ceiling);
544        let batch = std::mem::replace(&mut self.pending, Vec::with_capacity(next_limit));
545        self.pending_bytes = 0;
546        let msg = MergeMsg::Batch(batch);
547        // Issue #2419 (WS2) / #3120: only DATA entries are tracked on the
548        // egress-depth gauge, and a TERMINATOR is untracked on both send and
549        // receive so it can never unbalance the level. ONE predicate, shared with
550        // the consumer's recv site — see `MergeMsg::tracked_entries`, whose
551        // exhaustive match is the compile-time tripwire for a future variant.
552        // Captured BEFORE `send` moves `msg`.
553        let tracked = msg.tracked_entries();
554        match self.sender.send(msg) {
555            Ok(()) => {
556                if tracked > 0 {
557                    // The probe counters are stored FIRST, the `SeqCst` gauge/
558                    // `local_sent` stores second: a test that observes the gauge and
559                    // then reads the probe by exact equality has no other
560                    // happens-before to rely on (see `record_batch_sent`).
561                    record_batch_sent(tracked);
562                    // These entries now occupy a channel slot; balanced by exactly
563                    // one `channel_depth::received_n` of the same count at the
564                    // consumer's recv site (or by the post-join reconcile in
565                    // `Drop`) — see `channel_depth`.
566                    channel_depth::sent_n(tracked);
567                    self.local_sent.fetch_add(tracked as i64, Ordering::SeqCst);
568                }
569                self.limit = next_limit;
570                ControlFlow::Continue(())
571            }
572            // The consumer is gone; the batch is dropped with it. Same outcome as
573            // the pre-batching per-row send failure: the walk stops via `Break`.
574            Err(_) => ControlFlow::Break(()),
575        }
576    }
577}
