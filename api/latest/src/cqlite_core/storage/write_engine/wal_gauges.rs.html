1//! WAL observability gauges for the write engine (issue #1707, AI7 of epic #1686).
2//!
3//! Two readings an operator needs and the engine already holds, so nothing here
4//! stats a file or samples anything:
5//!
6//! * [`record_wal_size`] — the size the [`super::wal::WriteAheadLog`] TRACKS, emitted
7//!   at the same post-write seam as the memtable gauges so "memtable growing / WAL
8//!   growing" are two readings taken at one instant, AND immediately after every
9//!   successful WAL append (see below), AND once at engine open (see below);
10//! * [`record_wal_recovery_duration`] — how long WAL recovery at engine open took.
11//!
12//! A sibling file, not more lines in `mod.rs`, per the campsite rule (#1116): that
13//! file is far over the source target already.
14//!
15//! # Why the WAL gauge is emitted through the engine's paired `record_size_gauges`
16//!
17//! [`record_wal_size`] and the memtable gauges are emitted by ONE engine helper
18//! called at all THREE seams — the sync write, the async write, and after the
19//! post-flush WAL truncate — so the two readings are taken at one instant and
20//! neither can be wired into a code path the other is missing from.
21//!
22//! That pairing exists because the unpaired version failed in both directions
23//! (issue #1707): the WAL gauge originally had a SINGLE call site inside the sync
24//! `write_into_memtable`, while `write_async_inner` duplicates that logic and
25//! emitted only the memtable gauges — so an async-API caller got no
26//! `cqlite.wal.size` series AT ALL — and the post-flush truncate emitted nothing, so
27//! a sync caller's gauge only ever CLIMBED. The operator doc reads a monotonic climb
28//! as "flushes are not keeping up", so a flush that worked perfectly manufactured an
29//! alarm. The healthy shape the doc promises is a saw-tooth, and the post-truncate
30//! emission is the falling edge of it.
31//!
32//! # Why the size is ALSO emitted immediately after every successful append
33//!
34//! The paired seam runs only after the WHOLE mutation succeeds, and the append is
35//! the FIRST of its steps: `wal.append()` advances the tracked size and returns, and
36//! then the fsync, the decorated-key computation and the memtable insert can each
37//! fail and return early. The WAL grew; the gauge did not move — and it stayed
38//! unmoved for as long as the failure persisted, which is exactly when an operator
39//! is watching it (issue #1707, roborev job 149). A disk filling up or an fsync
40//! erroring made `cqlite.wal.size` report FLAT while the file grew: the metric was
41//! at its most wrong precisely during the incident it exists for. So the size is
42//! published the instant the append succeeds, independent of everything downstream.
43//! It is an ADDITIONAL site, not a replacement: the paired post-mutation emission
44//! still gives the WAL/memtable pair at one instant, and the truncate and open sites
45//! still cover the falling edge and the write-less recovery.
46//!
47//! # Why the size is ALSO emitted once at engine open
48//!
49//! The write/flush seams cover a process that writes. A process that RECOVERS a
50//! non-empty WAL and then receives no writes touches none of them, so it reported a
51//! [`record_wal_recovery_duration`] and no size at all (issue #1707, roborev job
52//! 145) — the operator could see that startup spent N seconds in recovery and had no
53//! way to see the WAL that caused it. `WriteEngine::open`'s single emission closes
54//! that, and it is placed AFTER the lossy-recovery branch so a corrupt-prefix reset
55//! reports the trimmed size the engine is really starting from; announcing the
56//! pre-reset size for bytes no longer on disk would be worse than the silence.
57
58use std::time::Duration;
59
60use crate::observability::{self as obs, catalog};
61
62/// Emit the current WAL size (bytes). No-op when the `observability` feature is off
63/// or no meter is installed.
64pub(super) fn record_wal_size(size: u64) {
65    obs::record_gauge(catalog::WAL_SIZE, size as i64, &[]);
66}
67
68/// Emit the duration of the WAL recovery performed at engine open — the CRC
69/// validation scan run while opening the log plus the replay of its entries.
70///
71/// A free function because recovery runs during CONSTRUCTION, before a
72/// `WriteEngine` value exists. See [`catalog::WAL_RECOVERY_DURATION`] for why this is
73/// a histogram in base-unit seconds rather than an `i64` gauge (a sub-second
74/// recovery would truncate to a fabricated `0`), and why it is recorded even when
75/// there was nothing to recover and even when replay found corruption.
76pub(super) fn record_wal_recovery_duration(elapsed: Duration) {
77    obs::record_histogram(catalog::WAL_RECOVERY_DURATION, elapsed.as_secs_f64(), &[]);
78}
