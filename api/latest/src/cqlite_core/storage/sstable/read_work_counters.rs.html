1//! Cfg-gated read-work counters for the read-path optimization program
2//! (Issue #1566, Epic A / A5).
3//!
4//! File-size note (issues #2430/#2470, campsite rule): this file was already over
5//! the ~800-line source target on `main` before #2430 (`index_backed_partitions_
6//! resolved`) and #2470 (the `record_seek`/`record_index_probe` scope wiring) — a
7//! cohesive, single-responsibility registry (one `Counters` struct + `record_*`/
8//! getter pairs). #2470's ~210-line thread-local scope + its regression test live in
9//! the sibling `read_work_counters/read_work_scope.rs` (extracted, not grown here);
10//! the residual few lines are the essential recorder wiring. Fully splitting this
11//! file by counter group is out-of-scope, tracked under epic #1116;
12//! `CQLITE_ALLOW_FILE_GROWTH=1` acknowledged for this change.
13//!
14//! # Why this exists
15//!
16//! The July 2026 read-path audit (`docs/reports/read-path-performance-audit-2026-07-01.md`
17//! §Epic A) is measurement-first: land the gauges before the optimizations so every
18//! later claim (epics B–G) is pinned. Correct result rows never prove *how much
19//! work* a read did — a regression can return the right answer while decompressing
20//! the whole file, walking the trie twice, or reopening `Data.db` per lookup. These
21//! counters make that work observable so a later epic can assert on it the
22//! no-heuristics way: observe the *work*, not just the result.
23//!
24//! # Why cfg-gated (unlike [`work_counters`](super::work_counters))
25//!
26//! The existing [`work_counters`](super::work_counters) sit on *cold per-lookup
27//! boundaries* (once per candidate SSTable / once per returned partition) and are
28//! therefore always-on. A5's counters sit on *per-chunk / per-seek / per-open*
29//! paths that are much hotter, and the issue's DoD demands "zero overhead in
30//! release builds". So the pattern here (design.md Decision 1) is:
31//!
32//! - The `record_*()` functions are **unconditional public functions** — the read
33//!   path calls e.g. [`record_decompress`] with no `#[cfg]` at the call site, so
34//!   production code reads identically in every build.
35//! - Their **body** is `#[cfg(any(test, feature = "work-counters"))]`. In a
36//!   default/release build (no `work-counters`, no `cfg(test)`) the body is empty
37//!   and the `#[inline(always)]` no-op is optimized away → **zero overhead**. No
38//!   atomic is even linked (the static and its module are compiled only under the
39//!   same cfg), so the release read path pays literally nothing.
40//! - The **getters + [`reset`]** are `#[cfg(any(test, feature = "work-counters"))]`:
41//!   only test/feature builds read the values. In-crate unit tests get them via the
42//!   `test` cfg; integration tests in `tests/` and benches enable the
43//!   `work-counters` feature (they compile the lib WITHOUT its `test` cfg — the same
44//!   reason the `SCAN_FOR_KEY_CALLS` probe exists).
45//!
46//! A local-[`Counters`]-instance unit test (per issue #1071) gives deterministic
47//! absolute-value assertions immune to parallel tests mutating the process-global.
48//!
49//! # Counters and their consuming epic-children
50//!
51//! Grep a counter name to find its consumer, the same discoverability
52//! [`work_counters`](super::work_counters) provides:
53//!
54//! - [`record_trie_walk`] / [`trie_walks`] — **`TRIE_WALKS`**: one per BTI trie
55//!   descent (`lookup_partition_via_bti_trie`). Consumers **C3** (single-walk point
56//!   lookup) and **C4** (hoist the trie rehash out of the loop): both must prove a
57//!   point lookup descends the trie exactly once.
58//! - [`record_key_hash`] / [`key_hash_calls`] — **`KEY_HASH_CALLS`**: one per
59//!   Murmur3 hash + BTI byte-comparable encoding of a query partition key
60//!   (`encode_partition_key_for_bti_trie`). Consumer **C4** (hoist per-candidate
61//!   rehashing): a multi-generation `WHERE pk = ?` point read must hash+encode the
62//!   query key exactly ONCE per read (the encoding is identical for every candidate
63//!   SSTable), not once per candidate. On `main`/pre-C4 the candidate-prune loop
64//!   re-encoded per candidate (N hashes for N generations); after C4 it is 1.
65//! - [`record_range_short_circuit`] / [`range_short_circuits`] —
66//!   **`RANGE_SHORT_CIRCUITS`**: one per point read answered as authoritative
67//!   absence from the SSTable's `[first_key, last_key]` bound (parsed from
68//!   Summary.db) BEFORE any bloom check, `Index.db` probe, or BTI trie descent.
69//!   Consumer **C5** (first/last-key range short-circuit): an out-of-range point
70//!   read performs zero presence work (`INDEX_PROBES == 0`, `scan_for_key`
71//!   untouched) and records exactly one short-circuit; an in-range read records
72//!   zero so the normal presence path runs unchanged (no false miss).
73//! - [`record_decompress`] / [`decompress_calls`] — **`DECOMPRESS_CALLS`**: one per
74//!   compression-chunk decompress (`Compressor::decompress`). Consumers **B1**
75//!   (chunk cache — a cache hit must skip the decompress) and **E3** (copy-chain —
76//!   count the decompress invocations a read triggers).
77//! - [`record_seek`] / [`seek_calls`] — **`SEEK_CALLS`**: one per production
78//!   read-path seek. Wired across every read-path seek site: the compressed
79//!   chunk-read seek in `reader/block_io.rs` and the point-lookup / single-partition
80//!   / whole-section / scan seeks in the `reader/data_access` modules
81//!   (`bti.rs` BTI target-chunk + fallback + scan, `big_promoted.rs` BIG
82//!   reverse-block target-chunk + last-partition seek-to-end). Consumer **E4** (drop
83//!   redundant seeks): a sequential chunk walk must not re-seek to the position it is
84//!   already at.
85//! - [`record_file_open`] / [`file_opens`] — **`FILE_OPENS`**: one per `open(2)` that
86//!   mints a reader `BlockSource` file descriptor (`reader/source.rs` scan opens +
87//!   the reader's cold-open sites). Consumer **C2** (pread / kill the per-lookup
88//!   open): a point lookup must not `open(2)` `Data.db` on every call.
89//! - [`fd_high_water`] — the **fd high-water helper**: samples the process's current
90//!   open-fd count (`/dev/fd` on macOS, `/proc/self/fd` on Linux, `None` elsewhere).
91//!   Consumer **C2** (fd-exhaustion guard): a test brackets an operation with this
92//!   to bound fd growth. It is a *sample*, not an atomic — wrapping every
93//!   `open`/`close` to keep a live count is invasive and racy; sampling at a test
94//!   checkpoint is what the guard actually needs.
95//!
96//! # Parser work counters (Issue #1618, Epic H / H5)
97//!
98//! H5 lands the *parser* gauges the audit (`§Epic H`, block 2) needs so epics
99//! J1/K2/K3/L1/L3 can assert their claims ("zero `to_lowercase` per cell", "one
100//! header try-parse per partition", "<40 BTI nodes visited"). Same cfg-gated,
101//! zero-in-release pattern as the A5 counters above:
102//!
103//! - [`record_type_normalize`] / [`type_normalize_calls`] — **`TYPE_NORMALIZE_CALLS`**:
104//!   the per-cell decode-path type-normalization gauge. **J1 (issue #1635) delivered**:
105//!   dispatch is now resolved ONCE per column at `RowColumnResolution::build`
106//!   (cached on `ColumnToParse.kind`/`is_complex`), so the per-cell `to_lowercase`
107//!   sites — the value-parse normalization (`row_decoder/cell_value.rs`) and
108//!   the per-row complex-check (`row_decoder/udt.rs::is_complex_column`) —
109//!   are gone. A full fixture scan therefore records `0` (on `main`/pre-J1 it was
110//!   ≥2/cell). No production site calls [`record_type_normalize`] anymore; the counter
111//!   is retained as a regression tripwire — any reintroduced per-cell normalization
112//!   must record it, flipping the J1 `== 0` assertions red.
113//! - [`record_partition_header_try_parse`] / [`partition_header_try_parses`] —
114//!   **`PARTITION_HEADER_TRY_PARSES`**: one per speculative partition-header parse
115//!   (`row_decoder/row_framing.rs::parse_partition_header_full`, the single
116//!   boundary-peek/try-parse primitive every emit path routes through). Consumer
117//!   **K2/K3** (one try-parse per partition): flips to an exact per-partition bound.
118//! - [`record_bti_node_visited`] / [`bti_nodes_visited`] — **`BTI_NODES_VISITED`**:
119//!   one per node the BTI DFS enters (`bti/parser/traversal.rs`). Consumer **L1/L3**
120//!   (<40 BTI nodes visited): flips to the bounded-descent count.
121//! - [`record_bti_pointer_decode`] / [`bti_pointer_decodes`] — **`BTI_POINTER_DECODES`**:
122//!   one per BTI CHILD-pointer decode (`node_decode.rs` records one per materialized child
123//!   slot; `slice_walk.rs` records exactly one for the single matching child). Consumer
124//!   **L1/L3**: a targeted descent decodes ONE pointer per byte (Dense-256 node = 1, not 256).
125//! - [`record_row_sort`] / [`row_sort_invocations`] — **`ROW_SORT_INVOCATIONS`**:
126//!   the per-row cell `sort_by` gauge at the shared display-row builder
127//!   (`row_decoder/mod.rs::build_display_row`, which #1334 consolidated the
128//!   former `block_emit`/`block_emit_windowed` sort sites into). **K3 (issue #1642)
129//!   delivered**: the decoder now emits cells positionally in serialization-header
130//!   column order (deterministic by CONSTRUCTION), so `build_display_row` performs
131//!   NO per-row sort and a full scan of standard fixtures through the primary
132//!   decoder records `0` (on `main`/pre-K3 it was one per returned live row). The
133//!   only remaining callers are the two cold schema-less fallbacks in
134//!   `reader/parsing/mod.rs` (`extract_value_from_parsed_row_fallback` and
135//!   `extract_value_from_parsed_row_with_schema`), which sort recovered cells for a
136//!   deterministic emit order and DO record it — so the counter honestly counts
137//!   EVERY per-row cell sort. The primary V5 decoder path records `0`; the counter
138//!   is a regression tripwire — any reintroduced per-row cell sort on the primary
139//!   path must record it, flipping the K3 `== 0` scan assertions red.

141// The atomics, the process-global, the struct methods, the getters, and `reset`
142// exist ONLY in test/feature builds — a release build links none of them, which is
143// what makes the counters zero-overhead there.
144#[cfg(any(test, feature = "work-counters"))]
145use std::sync::atomic::{AtomicU64, Ordering};

147/// The four read-work counters as one value (test/feature builds only).
148///
149/// Production code shares a single process-global instance ([`COUNTERS`]) reached
150/// through the unconditional `record_*` free functions; the increment sites and the
151/// integration probes all operate on that instance. Bundling the atomics in a
152/// struct also lets a unit test exercise the add/get/reset contract against a
153/// *local* instance, immune to other tests concurrently mutating the global
154/// (issue #1071) — the global is shared with read-path code that any parallel test
155/// can drive.
156#[cfg(any(test, feature = "work-counters"))]
157struct Counters {
158    /// BTI trie descents (`TRIE_WALKS`) — consumers C3/C4.
159    trie_walks: AtomicU64,
160    /// Compression-chunk decompress invocations (`DECOMPRESS_CALLS`) — consumers B1/E3.
161    decompress_calls: AtomicU64,
162    /// Block-read seeks in the chunk read path (`SEEK_CALLS`) — consumer E4.
163    seek_calls: AtomicU64,
164    /// `open(2)` calls minting a reader `BlockSource` fd (`FILE_OPENS`) — consumer C2.
165    file_opens: AtomicU64,
166    /// `read_exact` reads in the compressed-chunk read path (`READ_CALLS`) —
167    /// consumer E3. One per logical read of a compression chunk's bytes. Before
168    /// E3 a chunk cost TWO reads (payload then trailing CRC as separate
169    /// `read_exact` calls); E3 folds them into one `read_exact` into a single
170    /// `payload+CRC` buffer, so a steady-state chunk read records exactly one.
171    read_calls: AtomicU64,
172    /// Heap allocations in the per-chunk read→decompress→window-fill copy chain
173    /// (`CHUNK_PATH_ALLOCS`) — consumer E3/#1940. **Instrumented today at ONE site
174    /// only**: the compressed-bytes `payload+CRC` buffer allocated in the cursor
175    /// chunk-read path (`block_io`). The other two copy-chain allocation sites —
176    /// the decompression output buffer (`compression`) and the cached decompressed
177    /// `Arc<[u8]>` (`DecompressedChunkCache`) — are NOT yet instrumented, so this
178    /// counter currently reflects the compressed-buffer allocation alone and
179    /// undercounts the full copy chain. Wiring those sites (and the ≤1-alloc/chunk
180    /// reduction they measure) is the A4 work deferred to issue #1940.
181    chunk_path_allocs: AtomicU64,
182    /// `data_type.to_lowercase()` calls in the per-cell decode path
183    /// (`TYPE_NORMALIZE_CALLS`, Issue #1618) — consumer J1.
184    type_normalize_calls: AtomicU64,
185    /// Speculative partition-header parses (`PARTITION_HEADER_TRY_PARSES`,
186    /// Issue #1618) — consumers K2/K3.
187    partition_header_try_parses: AtomicU64,
188    /// BTI DFS node entries (`BTI_NODES_VISITED`, Issue #1618) — consumers L1/L3.
189    bti_nodes_visited: AtomicU64,
190    /// BTI node/pointer decodes (`BTI_POINTER_DECODES`, Issue #1618) — consumers L1/L3.
191    bti_pointer_decodes: AtomicU64,
192    /// Per-row cell `sort_by` invocations (`ROW_SORT_INVOCATIONS`, Issue #1618) —
193    /// consumers K2/L.
194    row_sort_invocations: AtomicU64,
195    /// `CompressionInfo.db` parses (`COMPRESSION_INFO_PARSES`, Issue #1597 / G1) —
196    /// one per `compression_info::CompressionInfo::parse`. Consumer G1: a reader
197    /// open must parse `CompressionInfo.db` exactly once (was 2 — a legacy
198    /// `parse_binary` plus the modern `parse`).
199    compression_info_parses: AtomicU64,
200    /// BIG `Index.db` partition probes (`INDEX_PROBES`, Issue #1570 / B4) — one per
201    /// real `index_reader.lookup_partition` in `lookup_partition_with_index`.
202    /// Consumer B4 (key→partition-offset cache): a repeated point read served from
203    /// the cache must skip the `Index.db` probe, so `INDEX_PROBES` stays 0 on a hit —
204    /// the BIG analogue of `TRIE_WALKS == 0` for BTI.
205    index_probes: AtomicU64,
206    /// Query-key Murmur3 hash + BTI byte-comparable encodings (`KEY_HASH_CALLS`,
207    /// Issue #1575 / C4) — one per `encode_partition_key_for_bti_trie`. Consumer C4:
208    /// a multi-candidate point read hashes+encodes the key ONCE (hoisted out of the
209    /// candidate-prune loop), not once per candidate generation.
210    key_hash_calls: AtomicU64,
211    /// First/last-key range short-circuits (`RANGE_SHORT_CIRCUITS`, Issue #1576 /
212    /// C5) — one per point read the reader answered as authoritative absence from
213    /// the SSTable's `[first_key, last_key]` bound BEFORE any bloom check, Index.db
214    /// probe, or BTI trie descent. Consumer C5: an out-of-range point read performs
215    /// zero presence work (`INDEX_PROBES == 0`, no `scan_for_key`) and records
216    /// exactly one short-circuit; an in-range read records zero (the bound never
217    /// fires, so the normal presence path runs).
218    range_short_circuits: AtomicU64,
219    /// Per-partition `Rows.db` row-index entry deserializations
220    /// (`ROWS_DB_ENTRY_RESOLVES`, Issue #1647 / L1) — one per
221    /// `bti::parser::resolve_rows_db_entry` (`TrieIndexEntry.deserialize`). Consumer
222    /// L1: a single BTI clustering read must resolve the per-partition entry EXACTLY
223    /// once (the pre-L1 window path resolved it twice — once directly, once inside
224    /// `iterate_rows_for_partition`).
225    rows_db_entry_resolves: AtomicU64,
226    /// Partitions resolved from an already-loaded `Index.db` entry on the
227    /// MATERIALISING full-index walk (`INDEX_BACKED_PARTITIONS_RESOLVED`, Issue
228    /// #2430) — one per partition `iterate_all_partitions_via_full_index` resolves
229    /// directly from `entries[i].data_offset`, WITHOUT a `lookup_partition_with_index`
230    /// re-probe. This is the surviving discriminator for "the index-backed
231    /// materialising path was genuinely taken, not a silent `sequential_scan`
232    /// fallback" (issue #2302's `written_summary_index_pair_resolves_via_index_probes`
233    /// / `fully_shadowed_partition_keeps_index_path`): after #2430 removed the
234    /// redundant per-partition probe, `index_probes` reads 0 on this path even when
235    /// it fully resolves, so those two tests' oracle moved here.
236    index_backed_partitions_resolved: AtomicU64,
237}

424/// The process-global counters every read-path increment site and integration
425/// probe shares (test/feature builds only). Unit tests that assert absolute values
426/// use a local [`Counters`] instead (issue #1071).
427#[cfg(any(test, feature = "work-counters"))]
428static COUNTERS: Counters = Counters::new();

430/// Record one BTI trie descent (`TRIE_WALKS`; consumers C3/C4).
431///
432/// Called unconditionally at the single trie-descent entry
433/// ([`lookup_partition_via_bti_trie`](super::reader)); the body compiles to a no-op
434/// in a release build (design.md Decision 1).
435#[inline(always)]
436pub fn record_trie_walk() {
437    #[cfg(any(test, feature = "work-counters"))]
438    COUNTERS.record_trie_walk();
439}

441/// Record one compression-chunk decompress (`DECOMPRESS_CALLS`; consumers B1/E3).
442///
