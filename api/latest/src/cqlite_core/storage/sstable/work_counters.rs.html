1//! Process-global read-work counters for partition-targeted lookups
2//! (Issue #958, Epic #951).
3//!
4//! # Why this exists
5//!
6//! #949 added a partition-targeted lookup ([`SSTableManager::scan_partition`])
7//! that prunes the SSTable set via the bloom filter / BTI trie before parsing,
8//! so a `WHERE pk = ?` over a table backed by *N* SSTables touches only the
9//! handful of candidates that can hold the key — not all *N*. Correct result
10//! rows do not prove that pruning happened: a regression could quietly revert to
11//! "open and scan every SSTable, then filter in memory" and still return the
12//! right answer.
13//!
14//! These counters make the *work* observable so a CI test can fail the moment a
15//! single-partition read starts scaling with the total SSTable count. They
16//! mirror the [`scan_for_key_call_count`](crate::storage::sstable::SSTableReader::scan_for_key_call_count)
17//! probe (issue #831) and the access-path probe (issue #960): a process-global
18//! atomic with [`reset`]/getter accessors, observable from an integration test
19//! without parsing logs and from the streaming path's spawned task.
20//!
21//! # What each counter counts
22//!
23//! - [`sstables_scanned`] — incremented **once per candidate SSTable reader that
24//!   `scan_partition` actually parses** for a partition-targeted lookup. After
25//!   bloom/BTI pruning drops the SSTables that cannot hold the key, every
26//!   surviving candidate whose `Data.db` is parsed (whether through the
27//!   cross-generation k-way merge or the per-reader concat fallback) bumps this
28//!   by one. It is the O(candidates) signal: for a key living in one SSTable it
29//!   must stay near 1 (plus any bloom false-positives), never grow to N. It is
30//!   **not** incremented on the full-scan path — only the targeted lookup is
31//!   instrumented, which is exactly the path #949/#958 protect.
32//!
33//! - [`partitions_parsed`] — incremented **once per partition row a
34//!   partition-targeted lookup returns** (after retaining only the target key /
35//!   the merge emits the partition). For a single-partition point lookup this is
36//!   0 (absent key) or the number of rows that partition holds; it never scales
37//!   with the table's total partition count, which a full scan would.
38//!
39//! - [`chunks_decompressed`] — incremented **once per compression chunk the
40//!   single-candidate seek path actually decompresses** while buffering the
41//!   target partition's bytes (Issue #953 / #951). Where `partitions_decoded`
42//!   proves we returned only one partition, this proves the seek bounded its
43//!   *decompression I/O* to that partition's chunk span rather than reading the
44//!   whole `Data.db` to EOF. A head-of-file point lookup must NOT decompress the
45//!   tail chunks of a large SSTable: a regression that stitches to EOF (the bug
46//!   the bound replaces) bumps this by the file's whole chunk count, which the
47//!   `issue_953` bound test catches even though `partitions_decoded` stays 1.
48//!   Incremented at the seek's single decompression site
49//!   (`SSTableReader::bti_pull_decompressed_chunk`), so every chunk the seek
50//!   materializes — BIG (`nb`, bounded by the `Index.db` size) or BTI (`da`,
51//!   bounded by the next-partition boundary) — is counted exactly once. The
52//!   whole-section `stitch_all_chunks` fallback does **not** bump it (it is the
53//!   unbounded path the seek avoids when chunk targeting is possible).
54//!
55//! - [`partitions_decoded`] — incremented **once per partition actually decoded
56//!   out of `Data.db`** by the single-candidate *seek* path (Issue #953). Where
57//!   `sstables_scanned` proves we touched few SSTables, this proves that *within*
58//!   a touched SSTable we did not decode every partition: the seek resolves the
59//!   target partition's `Data.db` offset (via the BTI trie or `Index.db`) and
60//!   decodes only that one partition, so this stays O(1) for a point lookup. A
61//!   regression that reverts the single-candidate path to a full parse-then-retain
62//!   would bump this by the SSTable's whole partition count (~N), failing the
63//!   `issue_953` bound. It is incremented at the per-partition decode site of the
64//!   seek (`SSTableReader::scan_single_partition` → the emit closure that captures
65//!   a complete partition), NOT at the result-count boundary. The full-scan +
66//!   retain fallback does **not** bump it (it is the unoptimized path the seek
67//!   replaces); a candidate that cannot be seeked therefore reads 0 here, which is
68//!   why the test asserts a *small upper bound* (decode happened cheaply) rather
69//!   than an exact equality.
70//!
71//! # Cost
72//!
73//! Each increment is a single `Relaxed` atomic add on the cold per-lookup
74//! boundary (once per candidate / once per returned partition), never inside an
75//! inner byte-decoding loop, so the hot path is unaffected. The counters are not
76//! gated behind `cfg(test)` because integration tests in `tests/` compile
77//! against the library crate without its `test` cfg (same rationale as
78//! `SCAN_FOR_KEY_CALLS`).
79
80use std::sync::atomic::{AtomicU64, Ordering};

82/// The five read-work counters as one value.
83///
84/// Production code shares a single process-global instance ([`COUNTERS`]) reached
85/// through the free functions below; the increment sites and integration probes
86/// all operate on that instance. Bundling the atomics in a struct also lets a
87/// unit test exercise the add/get/reset contract against a *local* instance,
88/// immune to other tests concurrently mutating the global (issue #1071) — the
89/// global is shared with read-path code that any parallel test can drive.
90struct Counters {
91    /// Candidate SSTables actually parsed by a partition-targeted lookup.
92    sstables_scanned: AtomicU64,
93    /// Partitions a partition-targeted lookup has returned.
94    partitions_parsed: AtomicU64,
95    /// Partitions DECODED from `Data.db` by the single-candidate seek (Issue #953).
96    partitions_decoded: AtomicU64,
97    /// Compression chunks DECOMPRESSED by the single-candidate seek (Issue #953 / #951).
98    chunks_decompressed: AtomicU64,
99    /// Individual rows DECODED within a partition by the seek path (Issue #954).
100    rows_decoded: AtomicU64,
101    /// Promoted-index blocks DECODED back-to-front by the BIG reverse partition
102    /// iterator (Issue #1184). One per block the reverse walk visits.
103    reverse_blocks_decoded: AtomicU64,
104    /// Peak number of decoded rows held in a SINGLE block buffer by the BIG
105    /// reverse iterator (Issue #1184) — the per-iteration memory high-water mark.
106    /// A regression that materialises the whole partition before reversing pushes
107    /// this to the partition's full row count instead of one block's worth.
108    reverse_peak_block_rows: AtomicU64,
109    /// Full re-reads of a finished `Data.db` performed to compute checksums
110    /// (Issue #1663). Bumped once each time the re-read CRC oracle
111    /// (`crc_writer::build_crc_bytes`) or the digest re-read
112    /// (`SSTableWriter::compute_crc32`) OPENS `Data.db`. The streaming write path
113    /// accumulates both checksums as it writes, so a non-empty
114    /// `SSTableWriter::finish()` must leave this at 0; a regression that
115    /// reintroduces the finish-time double re-read bumps it (2 on the old path).
116    data_db_checksum_full_reads: AtomicU64,
117    /// Partition BODIES read + parsed by a `do_get` compaction-merge scan — one
118    /// per partition whose `Data.db` slice is decoded (Issue #2398). Incremented on
119    /// BOTH per-SSTable enumeration paths: the streaming full-index walk
120    /// (`stream_all_partitions_via_full_index`, the uncompressed `V5_0Uncompressed`
121    /// field path, issue #2361) AND the chunk-stitching walk
122    /// (`drain_compaction_window`, the `nb`/`V5CompressedLegacy` path). This is the
123    /// O(partitions actually walked) signal for a scan. A token-range split must
124    /// walk only the entries whose token falls in the split's `(start, end]` range
125    /// (the index/data are token-ordered), NOT every partition in the SSTable: the
126    /// current read paths apply the token filter only DOWNSTREAM at the consumer
127    /// (`MergeProducer::drive_merge`), so this bumps by the SSTable's WHOLE
128    /// partition count regardless of how narrow the split range (or `LIMIT`) is —
129    /// the fixed multi-second warm-scan setup this counter exists to make visible.
130    stream_walk_partitions_parsed: AtomicU64,
131    /// Merge ENTRIES decoded from `Data.db` by ANY [`KWayMerger`]-adapter-driven
132    /// run (Issue #2096) — full scans, compaction, AND multi-candidate point
133    /// reads all share the same [`SSTableRowIteratorAdapter`]/`PathProbe::Seeked`
134    /// increment sites, so this counts entries for all of them, not point reads
135    /// alone. Bumped once per merge entry a run actually materialises out of
136    /// `Data.db`: once per `Ok(entry)` streamed on the full-scan adapter run, and
137    /// once per entry built from a seeked partition on the seek run's
138    /// `PathProbe::Seeked` arm. A single partition with N clustering rows bumps
139    /// this N times (an ENTRY-granularity counter, not partition-granularity).
140    ///
141    /// This makes a merge run's decode volume observable, which the existing
142    /// `partitions_decoded` (#953, single-candidate seek only) does not cover.
143    /// For a multi-candidate `WHERE pk = ?` point read specifically: the OLD
144    /// full-scan `KWayMerger::new` decodes every partition with token <= the
145    /// target in every generation, so the DELTA around that call balloons far
146    /// past the number of candidates holding the key; the partition-SEEKING
147    /// merger (#2096) decodes only the target partition's entries per candidate,
148    /// so its delta stays O(target rows). It is process-global, so a bound
149    /// test's delta assertion around one call is polluted by ANY concurrent
150    /// scan/compaction in the same test binary — callers must `reset()` first
151    /// and serialize (`#[serial_test::serial]`) against other counter-reading
152    /// tests, exactly like the other counters in this file.
153    merge_run_entries_decoded: AtomicU64,
154}

280/// The process-global counters every read-path increment site and integration
281/// probe shares. Unit tests that assert absolute values use a local
282/// [`Counters`] instead (issue #1071).
283static COUNTERS: Counters = Counters::new();

285/// Record that `count` candidate SSTables were parsed by a partition-targeted
286/// lookup. Called once per `scan_partition` invocation with the number of
287/// surviving (post-prune) candidates whose `Data.db` is parsed.
288///
289/// Only the default (`not(tombstones)`) build has the bloom/BTI-pruning
290/// `scan_partition`; the `tombstones` build serves a single-partition read by a
291/// full scan + filter and has no candidate set to count, so the mutators are
292/// compiled only for the build whose pruning they instrument. The getters and
293/// [`reset`] remain available in every build for the test API.
294#[cfg(not(feature = "tombstones"))]
295pub(crate) fn add_sstables_scanned(count: u64) {
296    COUNTERS.add_sstables_scanned(count);
297}

302    COUNTERS.add_partitions_parsed(count);
303}

333/// Record that one row was DECODED from `Data.db` within a partition by the
334/// single-candidate seek path (Issue #954). Called once per row the partition
335/// decoder actually parses out of the (clustering-narrowed) byte window — the
336/// row-granularity signal that proves a `WHERE pk = ? AND ck </>/= ?` slice
337/// query decodes O(matched rows + index block slack), not the whole partition.
338///
339/// Where [`add_partition_decoded`] counts WHICH partition was touched (1 for a

341/// that reverts the clustering seek to a full-partition decode bumps this by the
342/// partition's whole row count, failing the `issue_954` bound even though
343/// `partitions_decoded` stays 1.
344///
345/// Gated on `not(tombstones)` like the other seek-path mutators: only the
346/// default build reaches the seek; under `tombstones` the full-scan fallback
347/// never seeks, so the counter stays 0.
348#[cfg(not(feature = "tombstones"))]
349pub(crate) fn add_rows_decoded(count: u64) {
350    COUNTERS.add_rows_decoded(count);
351}

399/// Number of partition bodies a `do_get` scan read + parsed since the last
400/// [`reset`] (Issue #2398).
401///
402/// For a token-range split this SHOULD stay bounded by the number of partitions
403/// whose token falls in the split's `(start, end]` range, NOT the SSTable's whole
404/// partition count. The current read paths filter tokens only at the consumer, so
405/// today this reads the full count for any overlapping SSTable — the fixed
406/// warm-scan setup cost independent of the split range and of `LIMIT` that issue
407/// #2398 tracks.
408///
409/// This global getter is for CROSS-THREAD / integration observability (a
410/// detached compaction producer thread bumping the counter, read from the test
411/// thread). A same-thread *delta* assertion — "this scan drove EXACTLY N
412/// partition parses" — must NOT use it: the counter is process-global, so a
413/// concurrent test on another thread contaminates the delta under thread-parallel
414/// `cargo test` (issue #2428). Such assertions use [`stream_walk_scope`]'s
415/// thread-local [`StreamWalkScope`](stream_walk_scope::StreamWalkScope) instead,
416/// which is immune by construction.
417pub fn stream_walk_partitions_parsed() -> u64 {
418    COUNTERS.stream_walk_partitions_parsed()

421/// Thread-local scoping for [`stream_walk_partitions_parsed`] delta assertions
422/// (issue #2428).
423///
424/// # Why this exists
425///
426/// [`stream_walk_partitions_parsed`] is a process-global `AtomicU64` shared by
427/// every read-path scan and every test that drives one. A test that asserts a
428/// *delta* — "my scan drove EXACTLY N partition parses" — by
429/// `reset()`-ing the global, scanning, then reading the global back is
430/// contaminated the moment ANY other test in the same test binary drives a scan
431/// concurrently between the reset and the read: under thread-parallel
432/// `cargo test --lib --all-features` (the CI "Required PR Gate" invocation, which
433/// does NOT use nextest's per-process isolation) the observed delta jumps to an
434/// arbitrary inflated value. `#[serial(work_counters)]` only serialises tests
435/// that BOTH carry the tag, so a single untagged scan-driving test anywhere in
436/// the crate reintroduces the flake — a fragile, easy-to-miss invariant across a
437/// large and growing set of reachable tests.
438///
439/// # The structural fix
440///
441/// cargo runs each `#[test]` on its own OS thread, and a default (current-thread)
442/// `#[tokio::test]` drives all of its `.await`s on that one thread. So a
443/// thread-local counter, activated for the duration of one test's scan, records
444/// ONLY the increments that execute on that test's own thread — structurally
445/// immune to any concurrent test on another thread mutating the process-global
446/// counter. A delta assertion opens a [`StreamWalkScope`] before its scan and
447/// reads [`StreamWalkScope::count`] after; no `reset()`, no global read, no
448/// serial tag, and no way for a future scan-driving test to contaminate it.
449///
450/// # Boundaries
451///
452/// The scope only sees increments on THE THREAD that opened it, so it is for
453/// same-thread delta assertions of an inline (non-`spawn`) scan. A scan that
454/// fans work onto detached producer threads (the compaction merge path) would
455/// bump the global on those threads without touching the scope — such tests keep
456/// using the global [`stream_walk_partitions_parsed`] getter. This module is
457/// `#[cfg(test)]`: it exists only in the library's own test build (the binary
458/// where the contamination occurs); integration tests in `tests/` compile the
459/// library without its `test` cfg and never see it.
460#[cfg(test)]
461pub(crate) mod stream_walk_scope {
462    use std::cell::Cell;
463
464    thread_local! {
465        /// `Some(count)` while a [`StreamWalkScope`] is active on this thread,
466        /// `None` otherwise. Only `add_stream_walk_partition_parsed()` calls that
467        /// execute on this thread bump it.
468        static SCOPED: Cell<Option<u64>> = const { Cell::new(None) };
469    }
470
471    /// Bump the active scope on the current thread, if any. A no-op on threads
472    /// (production scans, detached producers, other tests) with no active scope.
473    pub(crate) fn record() {
474        SCOPED.with(|c| {
475            if let Some(v) = c.get() {
476                c.set(Some(v.saturating_add(1)));
477            }
478        });
479    }
480
481    /// A per-thread recording scope for `stream_walk_partitions_parsed`. Open one
482    /// before an inline scan whose partition-parse count you assert, and read
483    /// [`count`](StreamWalkScope::count) after. Immune to concurrent tests on
484    /// other threads (issue #2428). Dropping it clears the scope.
485    ///

922// NB: this module is gated ONLY on `test` (NOT `not(tombstones)`): the CI
923// Required-PR-Gate invocation this issue exists to fix is
924// `cargo test --lib --all-features`, which enables `tombstones`. The
925// `add_stream_walk_partition_parsed` mutator and the `stream_walk_scope` are both
926// present under every feature set, so this regression must run under all of them.
927#[cfg(test)]
928mod stream_walk_scope_tests {
929    use super::*;
930
931    /// Structural regression for issue #2428: a [`StreamWalkScope`] records ONLY
932    /// the `add_stream_walk_partition_parsed()` increments that execute on its own
933    /// thread, so a *concurrent* thread bumping the same process-global counter
934    /// cannot contaminate a same-thread delta assertion.
935    ///
936    /// This is the mechanism that made
937    /// `sequential_scan_fallback_counts_each_partition_exactly_once` flake under
938    /// thread-parallel `cargo test --lib` (the CI Required-PR-Gate invocation,
939    /// which does NOT isolate tests per-process like nextest): another
940    /// scan-driving test running between that test's `reset()` and its read
941    /// inflated the observed global delta. Here we reproduce that exact shape —
942    /// a foreign thread hammering the global while a scope is open — and prove the
943    /// scoped count stays exactly the number of increments made on THIS thread.
944    #[test]
945    fn stream_walk_scope_is_immune_to_a_concurrent_thread() {
946        use super::stream_walk_scope::StreamWalkScope;
947        use std::sync::mpsc;
948
949        const LOCAL: u64 = 10; // mirrors the flaky test's N
950        const FOREIGN: u64 = 500; // the contaminating "other test" load
951
952        let scope = StreamWalkScope::new();
953
954        // A foreign thread bumps the SAME process-global counter (its own thread
955        // has no active scope, so `record()` is a no-op there). Handshakes force
956        // its increments to interleave DURING this thread's scope, exactly like a
957        // concurrent scan-driving test.
958        let (started_tx, started_rx) = mpsc::channel::<()>();
959        let (proceed_tx, proceed_rx) = mpsc::channel::<()>();
960        let foreign = std::thread::spawn(move || {
961            started_tx.send(()).expect("send started");
962            proceed_rx.recv().expect("recv proceed");
963            for _ in 0..FOREIGN {
964                add_stream_walk_partition_parsed();
965            }
966        });
967
968        started_rx.recv().expect("foreign thread must start");
969        // Bump on THIS thread before, ...
970        for _ in 0..(LOCAL / 2) {
971            add_stream_walk_partition_parsed();
972        }
973        // ... let the foreign thread run its whole contaminating load, ...
974        proceed_tx.send(()).expect("release foreign thread");
975        foreign.join().expect("foreign thread must not panic");
976        // ... and after. The foreign 500 landed squarely between our increments.
977        for _ in 0..(LOCAL - LOCAL / 2) {
978            add_stream_walk_partition_parsed();
979        }
980
981        assert_eq!(
982            scope.count(),
983            LOCAL,
984            "the scope must count only this thread's {LOCAL} increments, never the \
985             foreign thread's {FOREIGN} on the shared global (issue #2428)"
986        );
987        drop(scope);
988        // After drop the scope is cleared: a fresh increment records nowhere.
989        assert_eq!(
990            StreamWalkScope::new().count(),
991            0,
992            "a fresh scope starts at zero (the previous scope's count did not leak)"
993        );
994    }
