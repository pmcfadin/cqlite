1//! What row assembly does when ONE column fails to decode (issue #3721).
2//!
3//! # The defect this module replaces
4//!
5//! [`super::row_data`]'s per-column loop had exactly one error handler per column
6//! path, and both were a bare `break`:
7//!
8//! * the COMPLEX arm — shared by `parse_complex_column_inner` (the compaction /
9//!   elements-out read, under `if compaction_complex_out.is_some()`) and
10//!   `parse_complex_column` (the user-facing read), which are merely the two arms
11//!   producing one `parse_result` binding; and
12//! * the SIMPLE arm, whose comment (`// CRITICAL FIX: Stop parsing remaining
13//!   columns …`) was honest about the mechanism and silent about the consequence.
14//!
15//! `break` leaves the loop, and the row is then assembled from the cells gathered
16//! SO FAR and returned as `Ok`. So the failing column **and every later on-disk
17//! column** silently vanished while the read reported SUCCESS. Measured at the
18//! public surface over committed Cassandra fixtures before the fix:
19//!
20//! ```text
21//! test_da.simple_table,  `name` read as INET     -> Ok, 3 rows, each missing
22//!                                                   `name` AND `salary`
23//! test_signed_coll.signed_int_collections,
24//!                        `m` key read as BIGINT  -> Ok, ZERO rows
25//! ```
26//!
27//! A successful `SELECT` with missing columns is the worst shape a read defect can
28//! take: it is indistinguishable from a row that legitimately has no value there,
29//! so nothing downstream can defend against it. It also silenced every corruption
30//! check the decoders make on Cassandra's authority (a non-4/16-byte `inet`, a
31//! wrong fixed width, a composite whose components do not consume the slice): the
32//! check fired, the row truncated, and the query reported success.
33//!
34//! # The rule: PROPAGATE. Which class goes where, and why nothing is skippable
35//!
36//! `break` conflated two different facts — "this column's value failed to decode,
37//! but the offset is known and the rest of the row is intact" (which could in
38//! principle be skipped) and "we cannot advance the offset safely" (which cannot).
39//! At these call sites the SECOND is the only one that can be established, for
40//! both paths and for every error class:
41//!
42//! * **Complex columns.** Neither `parse_complex_column` nor
43//!   `parse_complex_column_inner` returns an offset alongside its `Err`, so a
44//!   framing failure (a bad vint, an implausible cell count, a truncated cell) and
45//!   a value failure (a cell-path key or element that does not decode as its
46//!   declared type) are indistinguishable from here, and neither yields a resume
47//!   point.
48//! * **Simple columns.** Sharper still: a simple cell's FRAMING is
49//!   type-dependent — a fixed-width type consumes its width with no length prefix,
50//!   a variable-width type reads a vint length first — so when the decode fails
51//!   the number of bytes the cell occupies is exactly what is not known.
52//!
53//! Cassandra's own serializer offers no way to derive a resume offset from a
54//! failed decode, and this repository does not invent one (no-heuristics, issue
55//! #28). Cassandra does not serve a short row either: a cell it cannot read raises
56//! out of `UnfilteredSerializer` and the read fails. So every class here is FATAL
57//! and is reported as [`Error::ColumnDecode`].
58//!
59//! Marking the column and continuing — the other outcome issue #3721 allows — is
60//! not available without a public `Value` marker variant for "present on disk,
61//! undecodable", which is a public-type change well outside a read-path fix. If
62//! one is ever added, the complex arm is where a skippable class could be carved:
63//! its framing (`skip_complex_cell`) is type-INDEPENDENT and derived from
64//! `UnfilteredSerializer`, so a value-only failure there does have a recoverable
65//! resume point. The simple arm still would not.
66//!
67//! # Why the row/partition loops must MATCH, not read messages
68//!
69//! The loops above the decoder ([`super::block_emit`],
70//! [`super::block_emit_windowed`], and the [`super::partition_driver`] policies)
71//! deliberately treat an ordinary row-parse `Err` as *end of the partition body*:
72//! a well-formed partition's last row is followed by bytes that do not parse as
73//! another row, and that is how those loops detect the end. A per-column decode
74//! failure is NOT that condition. The only sound way to tell the two apart is a
75//! match on the dedicated [`Error::ColumnDecode`] variant — inspecting message
76//! text would be exactly the byte/string-pattern inference issue #28 forbids.
77//! [`end_of_partition_or_bail`] is that single decision, written once.
78//!
79//! # The cell-flags byte: NOT a terminator (issue #3721, roborev blocker 1)
80//!
81//! An earlier revision of this module kept a `not_a_cell` predicate that treated a
82//! simple column's flags byte `> 0x1F` as an END-OF-CELLS marker and `break`ed the
83//! column loop — i.e. reported a short row as a SUCCESSFUL read, the very defect
84//! this module exists to remove. **No such marker exists in the format.** At
85//! `cassandra-5.0.8`, `db/rows/UnfilteredSerializer.deserializeRowBody` fixes the
86//! column set BEFORE any cell is read (`hasAllColumns ? headerColumns :
87//! Columns.serializer.deserializeSubset(headerColumns, in)`) and then iterates
88//! exactly that set; cell reading is bounded by the columns bitmap / subset
89//! encoding, never by a sentinel flags value. `db/rows/Cell.Serializer` defines
90//! five bits only (`0x01|0x02|0x04|0x08|0x10` = `0x1F`).
91//!
92//! So a `> 0x1F` byte at a cell position is evidence the CURSOR is wrong, and the
93//! cell decoder rejects it as corruption (`cell_value.rs`, issue #191) — which
94//! becomes an [`Error::ColumnDecode`] like every other per-column failure. The
95//! class that used to hide behind the terminator (a SPECULATIVE, index-positioned
96//! walk over-running a real row boundary) is handled where it belongs, at the
97//! callers that chose the optimization: see [`end_of_partition_or_bail`].
98
99//! # Where an INDEX-POSITIONED walk must stop, and why (issue #3721)
100//!
101//! `block_emit_windowed`'s `row_body_window` is a byte extent inside the FIRST
102//! partition's row body, resolved from that partition's authoritative row index,
103//! and it is applied to `partition_index == 0` alone. A windowed walk therefore
104//! covers that partition and STOPS.
105//!
106//! Continuing costs CORRECTNESS, not just work. Stopping the row loop at
107//! `body_end` leaves the cursor in the MIDDLE of a row — a row-index block extent
108//! is a byte bound, not a row bound — and the try-parse partition detector (issue
109//! #166, deliberately no byte-pattern heuristics) then reads a "partition header"
110//! out of a cell value and decodes a phantom partition from it. MEASURED on the
111//! #1184 fixture: the promoted-index reverse block walk stopped at `body_end`
112//! 461014, peeked a partition header there, and decoded a row whose `payload` cell
113//! flags byte was `0x70` — the ASCII `p` of the text value it was standing in
114//! (`partition_index = 1`, `row_count = 0`).
115//!
116//! That phantom parse was harmless only while its failure was swallowed. Once a
117//! per-column decode failure is reported, as it must be, an over-run reads as a
118//! corrupt SSTable. Not entering the phantom partition is the fix;
119//! [`indexed_walk_falls_back`] remains as defence in depth for any over-run this
120//! does not prevent. Every windowed caller keeps only the target partition's rows,
121//! so nothing is lost.

128/// Build the [`Error::ColumnDecode`] a row-assembly column handler propagates.
129///
130/// `column_type` comes from [`dispatch_type`] and is the type the decode was
131/// actually DRIVEN FROM — see there for why that is not always the on-disk header
132/// marshal type.
133///
134/// # Why this does NOT `warn!` (issue #3721, roborev job 82)
135///
136/// It used to, on the reasoning that a `tracing::debug!` must not be the only
137/// trace of the condition (this issue's AC6). The premise was right and the site
138/// is wrong: **a failure here is not yet known to be a failure.** This
139/// constructor cannot see its caller, and two callers legitimately retry:
140///
141/// * a BTI point read whose row body STRADDLES a chunk boundary reports
142///   `row body exhausted` — itself an `Error::ColumnDecode` — which
143///   `point_read_remember_or_bail` REMEMBERS and re-parses against a larger
144///   window, where it typically succeeds (#1572);
145/// * an index-positioned walk may fall back to the full-partition path.
146///
147/// So warning here fires on CLEAN reads, and on a large BTI table straddling is
148/// ordinary rather than exceptional. A corruption warning an operator learns to
149/// ignore is worse than no warning: it is the "a guard that reds on correct input
150/// is the guard agents learn to waive" failure, pointed at a human.
151///
152/// AC6 is satisfied WITHOUT it, and always was — by the typed, matchable
153/// `Error::ColumnDecode` this returns, which propagates to the caller and is
154/// counted once at the reader's observability boundary with its category
155/// (`data_access::sequential`, issue #1704). The ERROR is the record; the log
156/// line never was. `debug!` is retained for developers, where a provisional
157/// failure belongs.
158pub(super) fn column_decode_failure(
159    column_name: &str,
160    column_type: &str,
161    offset: usize,
162    cause: Error,
163) -> Error {
164    tracing::debug!(
165        "V5CompressedLegacy: column '{}' ({}) at offset {} failed to decode \
166         (PROVISIONAL — a chunk-straddle retry or an index fallback may still \
167         succeed; the returned Error::ColumnDecode is the record): {}",
168        column_name,
169        column_type,
170        offset,
171        cause
172    );
173    Error::column_decode(column_name, column_type, offset, cause)
174}

176/// The row body ran out of BYTES while the row's own column set still names a
177/// column as PRESENT (issue #3721). Reported as [`Error::ColumnDecode`] like every
178/// other per-column failure, so the row/partition loops route it through
179/// [`end_of_partition_or_bail`] rather than mistaking it for end-of-partition.
180///
181/// # Why this is truncation and not the legitimate end of the row
182///
183/// Cassandra basis, `cassandra-5.0.8`
184/// `db/rows/UnfilteredSerializer.deserializeRowBody`: the column set is fixed
185/// BEFORE a single cell is read —
186///
187/// ```java
188/// Columns columns = hasAllColumns ? headerColumns
189///                                 : Columns.serializer.deserializeSubset(headerColumns, in);
190/// columns.apply(column -> { ... readSimpleColumn / readComplexColumn ... });
191/// ```
192///
193/// — and iteration runs over exactly that set. Exhausting the input mid-set raises
194/// out of the serializer; there is no short-row form and no end-of-cells sentinel
195/// (see the module note above). So this condition is corrupt or truncated data.
196///
197/// # The legitimate end of data is DISTINGUISHABLE here, structurally
198///
199/// [`super::row_data`]'s loop evaluates this condition only AFTER its
200/// `if !is_present(col_idx) { continue; }` skip, so every column reaching it is one
201/// the row's missing-columns bitmap declares has cell bytes on disk — and a cell is
202/// never zero bytes (it always carries at least its flags byte, `db/rows/Cell`'s
203/// five-bit `Serializer`). A row whose column set IS fully consumed leaves the
204/// `for` loop normally and never evaluates this condition at all. "No more columns
205/// expected" and "bytes exhausted with columns outstanding" are therefore different
206/// control-flow paths, not two readings of one predicate — nothing is guessed.
207///
208/// The `break` this replaces logged `parsed {}/{} on-disk cells`, i.e. ADMITTED
209/// decoding fewer cells than the column set names, and then let row assembly return
210/// `Ok` with this column and every successor silently absent.
211///
212/// # The bound is the ROW's end, not the parse unit's (issue #3721 / #3809)
213///
214/// `row_end` is this row's authoritative end — `(row_metadata_offset +
215/// row_size_vint_len) + row_size`, Cassandra's `getFilePointer()` arithmetic (issue
216/// #237) — and NOT `data.len()`. The parse unit holds every following row and
217/// partition, so a corrupt row declaring a SHORT `row_size` leaves outstanding
218/// columns plenty of readable bytes: bounding on `data.len()` let them decode out of
219/// the NEXT row and return plausible garbage as this row's values. `row_end` is
220/// proven `<= data.len()` before the column loop (the #2481 `row_size > available`
221/// rejection), so this bound is strictly tighter and can never admit a read the
222/// looser one refused. `data_len` is still REPORTED, because "the row claimed bytes
223/// it does not own" and "the file ends here" are different operator situations and
224/// the pair distinguishes them.
225///
226/// `progress` is `(col_idx, on_disk_column_count, cells_decoded)` and `bounds` is
227/// `(offset, row_end, data_len)`; all are reported so the failure names where the
228/// body stopped, where the row ends, and how much of the column set was consumed.
229pub(super) fn row_body_exhausted(
230    column: &crate::schema::Column,
231    header_type: Option<&str>,
232    bounds: (usize, usize, usize),
233    progress: (usize, usize, usize),
234) -> Error {
235    let (offset, row_end, data_len) = bounds;
236    let (col_idx, column_count, cells_decoded) = progress;
237    let ty = dispatch_type(&column.data_type, header_type);
238    let cause = Error::corruption(format!(
239        "row body exhausted at offset {offset} (this row's body ends at {row_end}; the parse \
240         unit is {data_len} bytes) with on-disk column {col_idx} of {column_count} ('{}') still \
241         declared PRESENT by the row's column set; {cells_decoded} cell(s) decoded — truncated \
242         or corrupt row body",
243        column.name
244    ));
245    column_decode_failure(&column.name, &ty, offset, cause)
246}

248/// A column's decoder returned an offset PAST the row's authoritative end — so it
249/// read bytes belonging to the NEXT row or partition, and the value it produced is
250/// not this row's data (issue #3721 / #3809).
251///
252/// # Why this is the dangerous shape, and why it is FATAL
253///
254/// A corrupt row that declares a SHORT `row_size` and is followed by more data
255/// leaves the cell decoders with plenty of readable bytes: they are handed the
256/// whole materialised parse unit, so a cell whose length prefix or fixed width
257/// runs past the row boundary decodes SUCCESSFULLY out of the following row's
258/// bytes. Framing stays intact — row assembly's `next_offset` derives from the
259/// authoritative `row_size`, never from where the columns stopped — so the walk
260/// does not desynchronise and nothing downstream looks wrong. The read returns a
261/// plausible garbage value and reports SUCCESS, which is strictly worse than a
262/// failure: a wrong answer is indistinguishable from a right one.
263///
264/// The row's authoritative end is `(row_metadata_offset + row_size_vint_len) +
265/// row_size` — Cassandra's own `getFilePointer()` arithmetic (issue #237), the same
266/// value row assembly returns as `next_offset`. A cell may not cross it: at
267/// `cassandra-5.0.8`, `db/rows/UnfilteredSerializer.deserializeRowBody` reads the
268/// row body under that bound, so a cell extending past its own row's extent cannot
269/// occur in well-formed data.
270///
271/// Nothing here can recover: the bytes consumed past the boundary belong to another
272/// row, so neither the value nor a resume point inside this row is knowable.
273/// Reported as [`Error::ColumnDecode`] like every other per-column failure, so the
274/// row/partition loops route it through [`end_of_partition_or_bail`] instead of
275/// mistaking it for end-of-partition.
276///
277/// `bounds` is `(column_start, returned_offset, row_end)`; `progress` is
278/// `(col_idx, on_disk_column_count)`.
279///
280/// Built by [`row_bound_check`], the ONE entry point the two column arms call, so
281/// the predicate is written once rather than duplicated per arm.
282fn column_escaped_row_bound(
283    column: &crate::schema::Column,
284    header_type: Option<&str>,
285    bounds: (usize, usize, usize),
286    progress: (usize, usize),
287) -> Error {
288    let (column_start, returned_offset, row_end) = bounds;
289    let (col_idx, column_count) = progress;
290    let ty = dispatch_type(&column.data_type, header_type);
291    let cause = Error::corruption(format!(
292        "on-disk column {col_idx} of {column_count} ('{}') decoded from offset {column_start} \
293         and returned offset {returned_offset}, PAST the end of its own row body at {row_end} \
294         (from the row header's authoritative row_size) — the decoder consumed bytes belonging \
295         to the next row or partition, so the value it produced is not this row's data; \
296         truncated or corrupt row body",
297        column.name
298    ));
299    column_decode_failure(&column.name, &ty, column_start, cause)
300}

302/// The bound every per-column decode's RETURNED offset is checked against: this
303/// row's authoritative end. `Ok(())` when the decode stayed inside its own row;
304/// otherwise the refusal [`column_escaped_row_bound`] describes.
305///
306/// One function for both column arms (SIMPLE and COMPLEX) so the predicate cannot
307/// drift between them, and so `row_data`'s loop states the rule once per arm rather
308/// than restating the rationale.
309pub(super) fn row_bound_check(
310    column: &crate::schema::Column,
311    header_type: Option<&str>,
312    bounds: (usize, usize, usize),
313    progress: (usize, usize),
314) -> Result<()> {
315    let (_column_start, returned_offset, row_end) = bounds;
316    if returned_offset > row_end {
317        return Err(column_escaped_row_bound(
318            column,
319            header_type,
320            bounds,
321            progress,
322        ));
323    }
324    Ok(())
325}

327/// The per-column walk finished SHORT of the row's authoritative end: bytes inside
328/// this row body were accounted for by no column the row declares present (issue
329/// #3721 / #3809). The exact converse of [`row_body_exhausted`], and the other half
330/// of [`column_escaped_row_bound`].
331///
332/// # Why a deficit cannot be tolerated
333///
334/// `row_size` is authoritative and the row loops advance by it, so an unconsumed
335/// remainder never desynchronises the walk — which is exactly why it is dangerous:
336/// the row is returned as `Ok`, with cells decoded from a cursor that was
337/// misaligned somewhere inside the body, and nothing says so. In well-formed data
338/// the columns TILE the body exactly: at `cassandra-5.0.8`,
339/// `db/rows/UnfilteredSerializer.deserializeRowBody` fixes the column set before
340/// the first cell and writes nothing after the last one — there is no trailing
341/// field and no padding, the next row starts immediately (issue #237).
342///
343/// # Every legitimately non-advancing path is accounted for, structurally
344///
345/// * a column the row's missing-columns bitmap declares ABSENT is `continue`d
346///   before any decode and has NO bytes on disk (the bitmap IS Cassandra's
347///   `Columns.serializer` subset encoding; an absent column is not written);
348/// * a DROPPED column (issue #1080) — on disk, absent from the supplied schema — IS
349///   decoded and its offset IS advanced; only the emit is suppressed;
350/// * the read-side shadow / TTL drop (issue #1741) and the `collection_absent`
351///   emptied-collection case both advance the offset first and suppress the emit
352///   only;
353/// * a pure row tombstone with no cell bytes returns long before this check.
354///
355/// So no legitimate path leaves the cursor short, and a deficit is corrupt or
356/// truncated data.
357///
358/// # Attribution: the column SET, not one column
359///
360/// WHICH column under-consumed is not knowable here — consumption is reported only
361/// by each decoder, and every one of them reported success. `last_column` is
362/// therefore the column the walk ENDED on (the last one decoded), named so an
363/// operator has a starting point, and the message says outright that the deficit
364/// belongs to the row's column set as a whole. Nothing is inferred from the bytes
365/// (issue #28).
366///
367/// Reported as [`Error::ColumnDecode`] because that is the variant the row and
368/// partition loops match on to tell a row-body failure from end-of-partition
369/// ([`end_of_partition_or_bail`]); an `Error::Corruption` here would be folded into
370/// "end of partition" and would silently truncate the partition — the very defect
371/// this module exists to remove.
372pub(super) fn row_body_under_consumed(
373    last_column: Option<(&str, &str)>,
374    bounds: (usize, usize),
375    progress: (usize, usize),
376) -> Error {
377    let (offset, row_end) = bounds;
378    let (column_count, cells_decoded) = progress;
379    let (name, ty) = last_column.unwrap_or(("<no column decoded>", "<row body>"));
380    let cause = Error::corruption(format!(
381        "row body under-consumed: the {column_count} on-disk column(s) this row declares left \
382         the cursor at offset {offset} but the row body ends at {row_end} (from the row header's \
383         authoritative row_size), leaving {} byte(s) inside this row accounted for by no column; \
384         {cells_decoded} cell(s) decoded, the walk ended on column '{name}' — the deficit \
385         belongs to the row's column set as a whole, and which column under-consumed is not \
386         knowable here; truncated or corrupt row body",
387        row_end.saturating_sub(offset)
388    ));
389    column_decode_failure(name, ty, offset, cause)
390}

392/// The per-column walk finished PAST the row's authoritative end (issue #3721 /
393/// #3809). The exact converse of [`row_body_under_consumed`], and the whole-row form
394/// of [`column_escaped_row_bound`].
395///
396/// # Why this exists as an ERROR and not as an assertion (roborev job 13)
397///
398/// Over-consumption is refused PER COLUMN by [`row_bound_check`] — but that check
399/// runs only for a column whose decoder actually RAN, and the pre-decode
400/// [`row_body_exhausted`] bound only for a column the row's bitmap declares PRESENT.
401/// A row whose bitmap declares EVERY column absent — or a table with no data columns
402/// — walks no column at all, so neither check is evaluated even once and nothing
403/// refuses a cursor that was already past the row end when the loop was entered.
404/// That happens when a malformed row's declared `row_size` ends INSIDE its own
405/// metadata: `row_size` is counted from immediately after its own VInt and covers the
406/// whole row body (`cassandra-5.0.8`
407/// `db/rows/UnfilteredSerializer.serialize`/`deserializeRowBody`, the
408/// `getFilePointer()` arithmetic of issue #237), so the metadata is a PREFIX of the
409/// declared body in every well-formed row.
410///
411/// An earlier revision reasoned from the per-column check to a `debug_assert!` here.
412/// The reasoning was not exhaustive and the consequence was a PANIC on malformed
413/// bytes in any debug build — the same class of defect as an `unwrap()` in library
414/// code, and issue #3721 exists precisely because malformed data must produce
415/// neither a silent success NOR a panic. So the three post-walk states are each named
416/// and each RETURNS a value: short → [`row_body_under_consumed`], exact → `Ok`, long
417/// → this. Nothing is asserted. See [`row_body_reconcile`].
418///
419/// # What the report can say in each shape, and why
420///
421/// * **Some column decoded.** WHICH column over-consumed is not knowable here (every
422///   decoder that ran reported success and passed [`row_bound_check`]), exactly as
423///   for [`row_body_under_consumed`]: `last_column` is the column the walk ENDED on,
424///   named so an operator has a starting point, and the deficit belongs to the column
425///   set as a whole.
426/// * **No column decoded.** Then the cursor has not moved since the row's metadata
427///   ended — [`super::row_data`] sets it to `row_metadata_offset + header_size` and
428///   only a column decoder advances it — so its position IS the metadata's end, and
429///   the report says so. That is a DERIVED consequence of the control flow, not an
430///   inference from the bytes (issue #28).
431///
432/// Reported as [`Error::ColumnDecode`] for the reason every other condition in this
433/// module is: that is the variant the row/partition loops match on to tell a row-body
434/// failure from end-of-partition ([`end_of_partition_or_bail`]).
435///
436/// `bounds` is `(offset, row_end)`; `progress` is
437/// `(on_disk_column_count, cells_decoded)`.
438fn row_body_over_consumed(
439    last_column: Option<(&str, &str)>,
440    bounds: (usize, usize),
441    progress: (usize, usize),
442) -> Error {
443    let (offset, row_end) = bounds;
444    let (column_count, cells_decoded) = progress;
445    let past = offset.saturating_sub(row_end);
446    let cause = match last_column {
447        Some((name, _)) => Error::corruption(format!(
448            "row body over-consumed: the {column_count} on-disk column(s) this row declares \
449             left the cursor at offset {offset}, PAST the end of the row body at {row_end} \
450             (from the row header's authoritative row_size), {past} byte(s) beyond it — bytes \
451             belonging to the next row or partition were consumed as this row's data; \
452             {cells_decoded} cell(s) decoded, the walk ended on column '{name}', and which \
453             column over-consumed is not knowable here; truncated or corrupt row body"
454        )),
455        None => Error::corruption(format!(
456            "row body over-consumed with NO column decoded: the row declares \
457             {column_count} on-disk column(s) and every one of them is ABSENT (or the table \
458             has no data columns), so the cursor at offset {offset} is where the row's own \
459             METADATA ended — {past} byte(s) PAST the end of the row body its header declares \
460             at {row_end} (from the authoritative row_size). The row's declared size ends \
461             INSIDE its metadata, so neither this row nor the following row's start can be \
462             framed from that row_size; truncated or corrupt row"
463        )),
464    };
465    let (name, ty) = last_column.unwrap_or(("<no column decoded>", "<row body>"));
466    column_decode_failure(name, ty, offset, cause)
467}

469/// The column the finished walk ENDED on, as the `(name, dispatch type)` pair
470/// [`row_body_reconcile`] reports — `None` when no column was decoded at all (every
471/// column bitmap-absent, or a table with no data columns).
472///
473/// This is NOT an attribution of the mismatch (see [`row_body_under_consumed`]): it
474/// is a starting point for an operator. Resolved from the on-disk index the row loop
475/// records, so the hot path stores an index and allocates only on the failure path.
476pub(super) fn walk_end_column(
477    columns_in_order: &[super::ColumnToParse<'_>],
478    last_decoded_idx: Option<usize>,
479) -> Option<(Arc<str>, String)> {
480    let ctp = columns_in_order.get(last_decoded_idx?)?;
481    let declared = ctp
482        .schema
483        .map(|c| c.data_type.as_str())
484        .or(ctp.header_type)
485        .unwrap_or("blob");
486    Some((
487        Arc::clone(&ctp.name),
488        dispatch_type(declared, ctp.header_type),
489    ))
490}

492/// RECONCILE the finished per-column walk against the row's authoritative end —
493/// the ONE place the three possible outcomes are decided (issue #3721 / #3809):
494///
495/// * `offset < row_end` — UNDER-consumption: bytes inside this row accounted for by
496///   no column. [`row_body_under_consumed`].
497/// * `offset == row_end` — the columns TILE the body exactly, as well-formed data
498///   always does. `Ok(())`.
499/// * `offset > row_end` — OVER-consumption that reached here without any column's
500///   [`row_bound_check`] refusing it. [`row_body_over_consumed`].
501///
502/// Written as an exhaustive `match` on the comparison so no state is implicit and
503/// none is asserted away: a malformed SSTable must produce an `Err`, never a panic.
504pub(super) fn row_body_reconcile(
505    last_column: Option<(&str, &str)>,
506    bounds: (usize, usize),
507    progress: (usize, usize),
508) -> Result<()> {
509    let (offset, row_end) = bounds;
510    match offset.cmp(&row_end) {
511        Ordering::Less => Err(row_body_under_consumed(last_column, bounds, progress)),
512        Ordering::Equal => Ok(()),
513        Ordering::Greater => Err(row_body_over_consumed(last_column, bounds, progress)),
514    }
515}

517/// Is `e` the per-column decode failure that must never be mistaken for the end of
518/// a partition body? A MATCH on the variant, never a message-text test (issue #28).
519pub(crate) fn is_column_decode(e: &Error) -> bool {
520    matches!(e, Error::ColumnDecode { .. })
521}

523/// The type string [`Error::ColumnDecode`] reports: the type the failed decode was
524/// DISPATCHED ON, naming the on-disk header marshal type alongside it whenever the
525/// two differ (issue #3721, roborev blocker 3).
526///
527/// Reporting the header type alone MISIDENTIFIES the cause, and the misreport is
528/// worst exactly where the error matters most — a mis-declared schema. Both column
529/// paths dispatch on the SUPPLIED schema type for a matched column:
530///
531/// * **simple** — `parse_cell_value_schema_order` decodes on `ColumnToParse.kind`,
532///   which `RowColumnResolution::build` resolves from
533///   `schema.map(data_type).unwrap_or(header_type)`, i.e. the supplied type when
534///   the column matched and the header marshal type only for a DROPPED column. In
535///   the row loop that value IS `column.data_type` in both cases (a dropped
536///   column's synthetic `Column` is built FROM the header type). So a `text` column
537///   read as a supplied `INET` used to be reported as its on-disk `UTF8Type`, which
538///   points a reader at the data rather than at the declaration that is wrong.
539/// * **complex** — the CONTAINER is decoded from the header marshal type
540///   (`complex_type`, authoritative for `UserType(...)`, issue #1081) but the
541///   cell-path KEY and the ELEMENT are decoded from the supplied schema type
542///   (`parse_complex_column_inner`'s `column`). A map whose key is mis-declared
543///   `BIGINT` therefore fails on the SUPPLIED type while the header describes the
544///   real on-disk `int` key, and the element/key type the caller has to fix appears
545///   only in the former (measured: `map<BIGINT, TEXT> (on-disk map<int, text>)`).
546///
547/// Naming both when they differ is what makes the report complete: the declared
548/// type identifies the dispatch that failed (including its key/element parameters),
549/// the header type identifies the bytes it was pointed at. Both are authoritative
550/// metadata; neither is inferred from the bytes (issue #28).
551pub(super) fn dispatch_type(declared: &str, header: Option<&str>) -> String {
552    match header {
553        Some(h) if h != declared => format!("{declared} (on-disk {h})"),
554        _ => declared.to_string(),
555    }
556}

558/// The ONE response an INDEX-POSITIONED read may make to [`Error::ColumnDecode`]:
559/// **abandon the optimization and re-read without the window** (issue #3721,
560/// roborev blocker 2). Never "return what we have" — that is the partial-results
561/// defect this issue exists to remove.
562///
563/// A windowed walk (`parse_block_emit_windowed` with a `row_body_window`, driven by
564/// `data_access::big_promoted` / `bti_point`) positions its cursor from the
565/// promoted/BTI row index, so a failure there is ambiguous between a misaligned
566/// cursor and a genuinely undecodable column, and NOTHING at the failure site can
567/// tell them apart. Re-reading through the full-partition path — which parses
568/// forward from the partition header and is not resynchronising — resolves the
569/// ambiguity by measurement: a misalignment artifact disappears, a real decode
570/// failure surfaces from a cursor known to be at a row boundary and propagates to
571/// the caller of the read. Only the fast path is lost.
572///
573/// Callers must DISCARD any rows the failed windowed attempt buffered before
574/// retrying; every one of them collects into a local `Vec` rather than emitting
575/// incrementally, so there is nothing already handed to a consumer.
576///
577/// # Where each windowed caller retracts, and why not lower down
578///
579/// * `data_access::clustering_seek_decode` — the forward clustering-slice seek. It
580///   holds BOTH index narrowings (the decompressed `decode_end_bound` AND
581///   `row_body_window`) and so is the only level that can drop both. Retrying
582///   further down, inside `big_decode_clustering_window` or
583///   `bti_collect_partition_rows`, drops only the row-body window and still reads
584///   the NARROWED extent, which ends mid-partition — MEASURED to fail a clean read
585///   of the committed `test_big.wide_partition` fixture on the retry as well.
586/// * `big_promoted::big_reverse_partition_rows` — the reverse
587///   block walk. It has no unwindowed form to retry, so it abandons the
588///   optimization through `Ok(None)`, the documented channel every other "cannot
589///   use the fast path" branch of that function already takes; the caller then
590///   re-reads via the in-memory-sort full scan.
591///
592/// Gated `not(tombstones)` like its ONLY caller, `data_access::clustering_seek_decode`
593/// (whose seek path is itself `not(tombstones)`): under `tombstones` no windowed
594/// read path is compiled, so there is no walk to fall back.
595#[cfg(not(feature = "tombstones"))]
596pub(in crate::storage::sstable::reader) fn indexed_walk_falls_back(e: &Error) -> bool {
597    let fall_back = is_column_decode(e);
598    if fall_back {
599        tracing::warn!(
600            "index-positioned read hit a per-column decode failure ({}); abandoning the \
601             windowed optimization and re-reading the full partition (issue #3721)",
602            e
603        );
604    }
605    fall_back
606}

608/// The ONE place a block/partition row loop decides what a row-parse `Err` means.
609///
610/// * [`Error::ColumnDecode`] — a framed row whose column would have been dropped.
611///   Returned as `Err` so it reaches the caller of the read instead of silently
612///   ending the partition (issue #3721).
613/// * anything else — the ordinary "no further row parses here" signal that marks
614///   the end of the partition body. Logged exactly as before and reported as
615///   `Ok(())`, so the caller continues to `break` out of its row loop.
616///
617/// # No caller is exempt (issue #3721, roborev blocker 2)
618///
619/// An earlier revision took a `resynchronising_walk` flag and, when it was set,
620/// folded [`Error::ColumnDecode`] back into the `Ok(())` end-of-partition signal —
621/// so every index-positioned read (the promoted-index reverse walk and the
622/// clustering-slice window read, `data_access::big_promoted` / `bti_point`, issues
623/// #954/#1184) returned PARTIAL RESULTS SILENTLY. That is the original defect
624/// surviving on exactly the public read paths a wide-partition `SELECT … ORDER BY
625/// … DESC` or a clustering slice takes.
626///
627/// The two facts it conflated are real and stay distinguished — but NOT here:
628///
629/// * **cursor misalignment.** A walk positioned from an index can start, or run
630///   past, a byte that is not a row boundary and then "decode" a row out of the
631///   middle of a cell value. That is evidence about the CURSOR, not about the data.
632/// * **decode failure.** The row was framed and one column's value is genuinely
633///   undecodable.
634///
635/// Nothing at THIS call site can tell them apart, and a two-valued predicate that
636/// cannot tell would have to pick one — which is how the permissive answer (accept
637/// partial output) got chosen. The decision belongs to the caller that CHOSE the
638/// index optimization, because only it can retract that choice: on
639/// [`Error::ColumnDecode`] it abandons the windowed/indexed walk and re-reads
640/// through the FULL-PARTITION path, which is not resynchronising. A misalignment
641/// artifact then disappears (the full walk parses forward from the partition
642/// header) and a genuine failure surfaces from a cursor known to be at a real row
643/// boundary. Either way NO path returns partial output. This mirrors the fallback
644/// `prime_shadow_before_window` already uses in `block_emit_windowed` when it
645/// cannot faithfully reconstruct shadow state: lose the fast path, never the rows.
646///
647/// So this function propagates [`Error::ColumnDecode`] unconditionally, and the
648/// fallback lives at the TWO windowed callers named in the section above — the
649/// only two call sites of [`indexed_walk_falls_back`]:
650/// `bti::clustering_seek_decode::decode_clustering_seek_target` and
651/// `big_promoted::big_reverse_partition_rows`.
652///
653/// Measured, because an earlier revision of this paragraph named THREE and named
654/// the wrong functions: `big_decode_clustering_window`
655/// (`bti/clustering_seek_decode.rs`) and `bti_point::bti_collect_partition_rows`
656/// both propagate their windowed walk's `Err` with `?` and retract nothing — the
657/// retraction is one level up, for the reason the section above gives (they hold
658/// only the row-body window, not the narrowed extent).
659pub(super) fn end_of_partition_or_bail(
660    e: Error,
661    partition_index: usize,
662    row_count: usize,
663    offset: usize,
664) -> Result<()> {
665    if is_column_decode(&e) {
666        return Err(e);
667    }
668    tracing::debug!(
669        "V5CompressedLegacy: Partition {} ended after {} rows at offset {}: {}",
670        partition_index,
671        row_count,
672        offset,
673        e
674    );
675    if row_count == 0 {
676        // Not one row parsed: worth an error-level line, as before.
677        tracing::error!(
678            "V5CompressedLegacy: Partition {} - Failed to parse first row at offset {}: {}",
679            partition_index,
680            offset,
681            e
682        );
683    }
684    Ok(())
685}

687/// The pure-row-tombstone FAST PATH's precondition: a `ROW_HAS_DELETION` row with no
688/// cell bytes may be returned only when its metadata ends EXACTLY at the end of the
689/// row body its own header declares (issue #3721, roborev job 14).
690///
691/// # The state this refuses, and why `Ok` was the wrong answer for it
692///
693/// [`super::row_data`] decides "this row has cell bytes" by comparing the metadata's
694/// end (`row_metadata_offset + header_size`) with the row's authoritative end
695/// (`(row_metadata_offset + row_size_vint_len) + row_size`, Cassandra's
696/// `getFilePointer()` arithmetic, issue #237). Three states, and the fast path used to
697/// treat the last two as one:
698///
699/// * `<` — cell bytes follow the header. A row deletion COEXISTS with surviving cells
700///   (issue #932), so the normal column loop runs. Legitimate and common.
701/// * `==` — the columns occupy zero bytes: a genuine pure row tombstone. The fast path
702///   returns it, and MUST keep doing so — that is what the fast path is for.
703/// * `>` — the declared `row_size` ends INSIDE the row's own metadata. In well-formed
704///   data that cannot happen: `row_size` is counted from immediately after its own
705///   VInt and spans the whole row body, so the metadata is a PREFIX of the declared
706///   body in every row Cassandra writes (`cassandra-5.0.8`
707///   `db/rows/UnfilteredSerializer.serialize`/`deserializeRowBody`).
708///
709/// Folding `>` into `==` reported SUCCESS for a row whose extent is impossible, and
710/// the harm is not confined to that row: the fast path returns `row_end` as
711/// `next_offset`, so the cursor moves BACKWARD relative to where the metadata actually
712/// ended. The row loop then re-reads this row's own metadata bytes as the next row's
713/// header and decodes phantom rows out of them — misparsing the REST OF THE PARTITION,
714/// not merely truncating one row. Nothing downstream can see it: the rows produced are
715/// well-formed values at plausible offsets.
716///
717/// The same shape reaching row assembly through a row WITHOUT a deletion is refused
718/// after the column walk, by [`row_body_reconcile`]'s over-consumption arm; a pure
719/// tombstone returns before that walk, so this is the only place it can be caught.
720/// Deliberately checked INSIDE the tombstone branch rather than before it, so no row
721/// that already has a tighter, better-attributed refusal loses it.
722///
723/// `bounds` is `(row_metadata_offset, metadata_end, row_end, data_len)`. Reported as
724/// [`Error::ColumnDecode`] for the reason every other condition in this module is: it
725/// is the variant the row/partition loops match on to tell a row-body failure from
726/// end-of-partition ([`end_of_partition_or_bail`]) — an `Error::Corruption` would be
727/// read as "the partition ended here" and would silently truncate it.
728///
729/// No column decoded (a pure tombstone has none), so the column the failure is
730/// attributed to is the same `<no column decoded>` / `<row body>` sentinel pair
731/// [`row_body_under_consumed`] and [`row_body_over_consumed`] use.
732pub(super) fn pure_tombstone_extent_check(
733    bounds: (usize, usize, usize, usize),
734    row_size: u64,
735) -> Result<()> {
736    let (row_metadata_offset, metadata_end, row_end, data_len) = bounds;
737    if metadata_end <= row_end {
738        return Ok(());
739    }
740    let past = metadata_end.saturating_sub(row_end);
741    let header_size = metadata_end.saturating_sub(row_metadata_offset);
742    let counted_from = row_end.saturating_sub(row_size as usize);
743    let cause = Error::corruption(format!(
744        "pure row tombstone REFUSED: the row's HAS_DELETION metadata at offset \
745         {row_metadata_offset} is {header_size} byte(s) long and so ends at {metadata_end}, \
746         PAST the end of the row body its own header declares at {row_end} ({past} byte(s) \
747         beyond it; authoritative row_size={row_size}, counted from {counted_from}) — the \
748         declared extent ends INSIDE the row's own metadata, so this row has no cell bytes \
749         only because its declared size is impossible. Returning it would move the read \
750         cursor BACK to {row_end}, re-parsing this row's own metadata as the next row's \
751         header and misparsing the rest of the partition. The parse unit is {data_len} \
752         bytes; truncated or corrupt row"
753    ));
754    Err(column_decode_failure(
755        "<no column decoded>",
756        "<row body>",
757        metadata_end,
758        cause,
759    ))
