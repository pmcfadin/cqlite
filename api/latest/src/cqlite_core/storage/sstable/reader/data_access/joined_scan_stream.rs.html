1//! A scan channel whose close is PROVEN, not assumed — for EVERY streaming scan
2//! surface, not just the batched one (issues #3106, #3124).
3//!
4//! # The defect class this type exists to make unrepresentable
5//!
6//! Every streaming scan in this crate is "a spawned producer that owns the sending
7//! half of a bounded channel and reports a failure by sending `Err(..)`". If the
8//! producer instead UNWINDS — a decode panic, an abort, a cancelled task — it drops
9//! its sender with NO error and NO terminator. A consumer that reads a channel
10//! close as "the scan finished" then reports a SHORT result set as a complete,
11//! successful scan: fewer rows, no error, no log line.
12//!
13//! Issue #3106 closed that hole for ONE surface (the batched single-source scan) by
14//! pairing the channel with its producer's `JoinHandle`. Issue #3124 found the same
15//! hole on the ≠1-generation (query-engine full scan) path, at four more
16//! boundaries: the fan-out k-way merge task, each per-reader per-row sub-scan, the
17//! per-row → batch re-chunker's source, and the windowed forwarder. Rather than
18//! grow a fourth bespoke protocol, the #3106 mechanism is generalised HERE over the
19//! channel's item type, so both surfaces share ONE implementation:
20//!
21//! * [`RowScanStream`] — per-row items, `Result<(RowKey, ScanRow)>`
22//!   (`SSTableReader::scan_stream`, `SSTableManager::scan_stream`,
23//!   `generation_merge::stream_generations_for_read`).
24//! * [`BatchedScanStream`] — batch items, `Result<Vec<(RowKey, ScanRow)>>`
25//!   (`SSTableReader::scan_stream_batched`, `SSTableManager::scan_stream_batched`).
26//!
27//! Consumers are unchanged in shape: [`JoinedStream::recv`] has the same
28//! `async fn(&mut self) -> Option<Result<T>>` signature `mpsc::Receiver::recv` had,
29//! so every `while let Some(item) = stream.recv().await` loop keeps working — and
30//! now fails closed.
31//!
32//! # The boundary #3106 closed first (the batched single-source scan)
33//!
34//! `scan_stream_batched_admitted` (`sequential.rs`) drives the scan in a spawned
35//! `tokio` task that owns the sending half of a bounded channel and reports a
36//! failure by sending `Err(..)`. Before this type it returned the bare
37//! `mpsc::Receiver` and DISCARDED the task's `JoinHandle`, so a task that
38//! UNWOUND — a decode panic in `parse_block_entries_at_now`, which on the
39//! non-stitching (uncompressed) branch runs directly inside that task, or any
40//! future panic on the walk — dropped its sender with no error and no terminator.
41//! Every consumer read that close as "the scan finished":
42//!
43//! * `query_rows::drive_full_scan_rows` returned `Ok(())`, its own thread then
44//!   sent the #3106 `Done` sentinel, and the Flight `do_get` completed
45//!   SUCCESSFULLY with a truncated result set — the #3106 defect exactly, one
46//!   layer below the channel #3106 first fixed, on the arm a `do_get` with no
47//!   token filter takes (i.e. the reported repro);
48//! * the query engine's streaming SELECT / aggregate folds
49//!   (`select_executor::streaming`, `stream_agg`, `executor::streaming_scan_rows`)
50//!   returned short row sets / wrong aggregates the same way.
51//!
52//! [`BatchedScanStream`] owns the handle instead, so a channel close is
53//! DISAMBIGUATED: the task is joined and a `JoinError` (panic or cancellation)
54//! surfaces as `Some(Err(..))` rather than `None`. This mirrors what the windowed
55//! sub-path already did internally for its own two child tasks
56//! (`scan_stream_windowed`'s `parse_task.await` / feed `join_err` arms map a
57//! `JoinError` to an error), so the two arms no longer diverge on whether a dead
58//! producer is an error.
59//!
60//! # The #3124 boundaries (the multi-generation path)
61//!
62//! `SSTableManager::scan_stream`'s fan-out k-way merge task, each per-generation
63//! `scan_stream_admitted` sub-scan, and the per-row → batch re-chunker's source had
64//! the identical shape on the ≠1-generation path, and the windowed forwarder
65//! discarded its `JoinError` outright. Their wiring lives in
66//! `storage/sstable/scan_stream_fanout.rs` and
67//! `storage/sstable/reader/scan_stream_forwarder.rs`; the mechanism they all use is
68//! this type.

78/// An item type a [`JoinedStream`] can carry, plus the human name of the surface
79/// that carries it.
80///
81/// The name exists only so a dead-producer error says WHICH stream died
82/// (`per-row scan stream` vs `batched scan stream`) instead of being anonymous. It
83/// is an associated const rather than a constructor argument so a new stream
84/// surface cannot be wired up with a copy-pasted, wrong label — and so the
85/// existing `JoinedStream::new(rx, task)` call sites need no churn.
86pub trait ScanStreamItem {
87    /// How this stream is named in a failure message.
88    const STREAM_KIND: &'static str;
89}
90
91impl ScanStreamItem for (RowKey, ScanRow) {
92    const STREAM_KIND: &'static str = "per-row scan stream";
93}
94
95impl ScanStreamItem for Vec<(RowKey, ScanRow)> {
96    const STREAM_KIND: &'static str = "batched scan stream";
97}

99/// How a stream item's rows are accounted into the read-operation meter (issue #1701).
100///
101/// A FUNCTION POINTER stored on the stream, deliberately NOT a method on
102/// [`ScanStreamItem`]: that trait is PUBLIC (re-exported through
103/// `reader::{RowScanStream, BatchedScanStream}`, whose defining module is not
104/// nameable), so adding a required method to it would break every downstream
105/// implementation at compile time — and its parameter type [`ReadOpMeter`] is
106/// crate-private, so an external implementer could not even NAME the signature it was
107/// being asked to write. The metric wiring therefore stays entirely off the public
108/// surface: the pointer is a private field, set by the crate-internal constructors.
109type ItemAccounting<T> = fn(&T, &mut ReadOpMeter);
110
111/// Per-item accounting for the PER-ROW surface: one row, and a partition boundary when
112/// its key differs from the previous row's.
113fn account_row_item(item: &(RowKey, ScanRow), meter: &mut ReadOpMeter) {
114    meter.record_row(&item.0);
115}
116
117/// Per-item accounting for the BATCHED surface: every row of the batch. Per-item
118/// BOOKKEEPING, not per-item EMISSION — the meter bumps two `u64`s and the single
119/// counter add / duration record happens once, when the operation ends.
120///
121/// `&Vec<_>` (not `&[_]`) because the signature must match `ItemAccounting<T>` for
122/// `T = Vec<(RowKey, ScanRow)>` exactly.
123#[allow(clippy::ptr_arg)]
124fn account_batch_item(items: &Vec<(RowKey, ScanRow)>, meter: &mut ReadOpMeter) {
125    for (key, _) in items {
126        meter.record_row(key);
127    }
128}

130/// Accounting for a stream that is NOT a metered read operation. Its meter is inert,
131/// so this would be a no-op either way; naming it keeps the field non-optional.
132fn account_nothing<T>(_item: &T, _meter: &mut ReadOpMeter) {}

134/// Consumer handle for a streaming scan: the item channel PLUS the producer task
135/// that feeds it, so end-of-stream is an OBSERVED fact rather than an assumption.
136///
137/// Dropping it drops the receiver, which makes the producer's next send fail and
138/// unwinds it cooperatively (the pre-existing backpressure/teardown behaviour); the
139/// task is deliberately NOT joined on drop, so an abandoned scan never blocks the
140/// consumer.
141pub struct JoinedStream<T: ScanStreamItem> {
142    rx: mpsc::Receiver<Result<T>>,
143    /// What is KNOWN about the producer task. See [`TaskState`] — the point of the
144    /// enum is that there is no representable "the handle is gone and I never saw a
145    /// verdict" state to accidentally read as success.
146    task: TaskState,
147    /// This read OPERATION's row/partition/duration accounting (issue #1701).
148    /// INERT unless the stream was built by [`JoinedStream::new_measured`], because
149    /// only a TOP-LEVEL operation may be measured: a fan-out merge's per-generation
150    /// sub-scan and the per-row → batch re-chunker would otherwise count the same
151    /// rows a second and third time. Emits once — at the observed end of stream, or
152    /// on drop for a scan the consumer abandoned (the `LIMIT` shape).
153    meter: ReadOpMeter,
154    /// How to account one delivered item into `meter` (see [`ItemAccounting`]). A
155    /// private field rather than a public-trait method, so the metric wiring adds
156    /// nothing to [`ScanStreamItem`]'s published surface.
157    account: ItemAccounting<T>,
158    /// Who counts a failed scan at this stream (issue #1704). See
159    /// [`ScanErrorReporting`] — stated by the constructor, never inferred.
160    reporting: ScanErrorReporting,
161    /// One increment per stream at most: the dead-task verdict is STICKY and
162    /// re-reported on every later `recv`, and a consumer may keep polling after a
163    /// terminal channel error.
164    counted: bool,
165}

167/// Who counts a failed scan into `cqlite.errors.total{category, subsystem="reader"}`
168/// at THIS stream (issue #1704), stated by the constructing call site.
169///
170/// # Why this is not derived from whether the stream is metered
171///
172/// It was, and that was wrong. Streams nest — a fan-out merge drains one
173/// [`JoinedStream`] per generation and re-sends a sub-scan's `Err` on its own channel,
174/// and the per-row → batch re-chunker does the same — so counting at every stream
175/// would report one failed query two or three times. The first fix inferred "nested"
176/// from "has no [`ReadOpMeter`]", reusing issue #1701's grain. That inference is FALSE:
177/// `scan_stream_batched_admitted(.., Exempt)` is unmetered because a fan-out merge owns
178/// the admission permit, and `summary_scan::query_rows` consumes exactly that stream
179/// DIRECTLY, as the top-level Flight full-scan producer. Under the inference its
180/// failures counted ZERO — the #1704 defect itself, on a path this issue exists to fix.
181///
182/// Metering ("do my rows feed `read.rows`?") and counting ("will anyone else see my
183/// failure?") are independent properties of a stream. They are now stated separately,
184/// by name, at each construction site.
185#[derive(Clone, Copy, Debug, PartialEq, Eq)]
186pub(crate) enum ScanErrorReporting {
187    /// An enclosing [`JoinedStream`] sees — and counts — everything this stream
188    /// produces, including its own dead-task verdict, because the intermediate task
189    /// forwards it. Count nothing. (A fan-out per-generation sub-scan.)
190    Nested,
191    /// Nothing encloses this stream and its source is a raw producer: it is the only
192    /// observer of every failure it delivers. Count all of them.
193    TopLevel,
194    /// Nothing encloses this stream, but its SOURCE is itself a counting
195    /// [`JoinedStream`] (or an already-counted materialized read) that has already
196    /// counted the failures it forwards. Count only THIS stream's own dead-task
197    /// verdict — which nothing else can see — and never a forwarded item.
198    /// (The per-row → batch re-chunker; the `tombstones` forwarder over `scan`.)
199    TopLevelOverCountedSource,
200}
201
202/// What a [`JoinedStream`] knows about its producer task (issue #3106, roborev).
203///
204/// Modelled as a state machine rather than `Option<JoinHandle>` + a `died` flag
205/// because that pair had an UNREPRESENTED third state — handle taken, verdict not
206/// yet observed — which a cancelled join produced and which then read as a clean
207/// end of stream. Here every state either OWNS the handle (so the join can still be
208/// completed later) or carries an observed verdict.
209enum TaskState {
210    /// Not yet joined; the handle is still owned HERE. A cancelled `recv` leaves the
211    /// stream in this state, so the next `recv` can still join.
212    Running(JoinHandle<()>),
213    /// Joined, and the join returned `Ok(())`: the scan PROVABLY ran to completion.
214    /// The only state from which end-of-stream is reported.
215    Finished,
216    /// Joined, and the join returned a `JoinError`. STICKY: every later `recv`
217    /// re-reports the failure, mirroring the sibling boundary
218    /// (`QueryRowStream::terminated`), so a retrying consumer — these streams are
219    /// public API, returned by `SSTableManager`/`StorageEngine` — can never
220    /// downgrade a dead task to a clean end of stream.
221    ///
222    /// `cancelled` remembers WHICH kind of `JoinError` it was, so the sticky
223    /// re-report keeps saying the same thing the first report said (a cancellation
224    /// re-reported as a panic would be a lie about the cause).
225    Died { cancelled: bool },
226}

228impl<T: ScanStreamItem> JoinedStream<T> {
229    /// Pair a scan channel with its producer task, WITHOUT read-metric accounting,
230    /// for a NESTED stream — see [`ScanErrorReporting::Nested`].
231    ///
232    /// `cfg(test)`: production nesting sites (the fan-out sub-scans) forward their
233    /// caller's choice as a VALUE through [`unmetered_as`](Self::unmetered_as), so
234    /// this by-name form exists only for stand-in streams in tests.
235    #[cfg(test)]
236    pub(in crate::storage::sstable) fn new_nested(
237        rx: mpsc::Receiver<Result<T>>,
238        task: JoinHandle<()>,
239    ) -> Self {
240        Self::unmetered_as(rx, task, ScanErrorReporting::Nested)
241    }
242
243    /// [`new_nested`](Self::new_nested) for a top-level stream whose SOURCE already
244    /// counts what it forwards — see [`ScanErrorReporting::TopLevelOverCountedSource`].
245    pub(in crate::storage::sstable) fn new_over_counted_source(
246        rx: mpsc::Receiver<Result<T>>,
247        task: JoinHandle<()>,
248    ) -> Self {
249        Self::unmetered_as(rx, task, ScanErrorReporting::TopLevelOverCountedSource)
250    }
251
252    /// The unmetered constructor whose mode is a runtime VALUE rather than a name —
253    /// for a site (`scan_stream_admitted`) that forwards its caller's choice.
254    pub(in crate::storage::sstable) fn unmetered_as(
255        rx: mpsc::Receiver<Result<T>>,
256        task: JoinHandle<()>,
257        reporting: ScanErrorReporting,
258    ) -> Self {
259        Self {
260            rx,
261            task: TaskState::Running(task),
262            meter: ReadOpMeter::inert(),
263            account: account_nothing,
264            reporting,
265            counted: false,
266        }
267    }
268
269    /// A TOP-LEVEL read operation whose rows, partitions and duration are reported
270    /// through the catalog read metrics (issue #1701).
271    ///
272    /// `format` is the single-SSTable format label (`"big"` / `"bti"`) when the
273    /// stream reads ONE SSTable, or `None` for a cross-generation merge, whose
274    /// reconciled rows come from possibly mixed-format inputs — the
275    /// format-agnostic grain [`crate::observability::catalog::READ_ROWS`] documents.
276    ///
277    /// A metered stream is always [`ScanErrorReporting::TopLevel`]: only a top-level
278    /// OPERATION may be metered (#1701), and its source is a raw producer. The
279    /// converse does NOT hold, which is why the unmetered constructors above are
280    /// three and not one.
281    pub(in crate::storage::sstable) fn new_measured(
282        rx: mpsc::Receiver<Result<T>>,
283        task: JoinHandle<()>,
284        meter: ReadOpMeter,
285        account: ItemAccounting<T>,
286    ) -> Self {
287        Self {
288            rx,
289            task: TaskState::Running(task),
290            meter,
291            account,
292            reporting: ScanErrorReporting::TopLevel,
293            counted: false,
294        }
295    }
296
297    /// Count a failure this stream FORWARDED from its producer (issue #1704): a
298    /// terminal `Err` item on the channel.
299    ///
300    /// Skipped for [`ScanErrorReporting::TopLevelOverCountedSource`], whose source
301    /// already counted it, and for [`ScanErrorReporting::Nested`], whose enclosing
302    /// stream will.
303    fn count_forwarded_error(&mut self, err: &Error) {
304        if self.reporting == ScanErrorReporting::TopLevel {
305            self.count_once(err);
306        }
307    }
308
309    /// Count a failure this stream ORIGINATED (issue #1704): its producer task died
310    /// or was cancelled, a verdict synthesised HERE by the join.
311    ///
312    /// Counted for BOTH top-level modes — a re-chunker's own death is invisible to
313    /// the counting source it reads from, so `TopLevelOverCountedSource` must report
314    /// it or nothing will.
315    fn count_own_failure(&mut self, err: &Error) {
316        if self.reporting != ScanErrorReporting::Nested {
317            self.count_once(err);
318        }
319    }
320
321    /// At most one increment per stream. A pure side effect: the caller returns the
322    /// SAME `Err`, and the category is derived by the classifier via
323    /// [`crate::observability::record_error`] — never chosen here.
324    fn count_once(&mut self, err: &Error) {
325        if !self.counted {
326            self.counted = true;
327            crate::observability::record_error(err, "reader");
328        }
329    }
330
331    /// Next item, or `None` at a PROVEN-clean end of stream.
332    ///
333    /// When the channel closes, the producer task is joined: a task that returned
334    /// normally yields `None` (the scan really finished), while a task that DIED
335    /// yields `Some(Err(..))` — a panic as the fail-closed
336    /// [`dead_scan_task_error`], a CANCELLED/aborted task as [`Error::Cancelled`],
337    /// which is the honest cause for a scan someone stopped. That is the whole
338    /// point: a dead producer must never be indistinguishable from a finished one
339    /// (issues #3106, #3124).
340    ///
341    /// A dead task is STICKY: every subsequent call re-reports the failure, so
342    /// polling again can never downgrade it to a clean end of stream.
343    ///
344    /// # Error counting (issue #1704)
345    ///
346    /// Every `Err` this method returns — a producer-reported terminal item, a dead
347    /// task, a cancellation, and the sticky re-reports of the last two — counts ONCE
348    /// into `cqlite.errors.total{category, subsystem="reader"}` when this stream is
349    /// the top-level operation (see [`ScanErrorReporting`]). The counting is a pure
350    /// side effect: the `Err` returned is bit-for-bit the one that would have been
351    /// returned before, and the category comes from the classifier, never from here.
352    ///
353    /// # Cancellation safety (issue #3106, roborev)
354    ///
355    /// This method is cancel-safe in the way that matters here: cancelling it
356    /// (`tokio::select!`, `timeout`, …) while it is awaiting the JOIN must not lose
357    /// the task's verdict. The handle is therefore polled IN PLACE — it is never
358    /// moved out of `self` before a result is observed — so a cancelled `recv`
359    /// leaves the stream in [`TaskState::Running`] and the next `recv` simply joins
360    /// again. Moving the handle out first (`self.task.take()?`) is exactly what
361    /// reintroduced the #3106 defect: the dropped handle DETACHED the task, no
362    /// verdict was ever recorded, and the following `recv` short-circuited to a
363    /// clean end of stream for a task that may have panicked.
364    pub async fn recv(&mut self) -> Option<Result<T>> {
365        if let TaskState::Died { cancelled } = self.task {
366            self.meter.finish();
367            let err = sticky_dead_task_error::<T>(cancelled);
368            // Latched (issue #1704): the join-error arm below already counted this
369            // failure, so re-reporting it to a still-polling consumer adds nothing.
370            self.count_own_failure(&err);
371            return Some(Err(err));
372        }
373        if let Some(item) = self.rx.recv().await {
374            // Read-metric bookkeeping (issue #1701) for the rows this item
375            // DELIVERED. An `Err` item carries no rows, and the meter's own totals
376            // are emitted at the terminal transition below.
377            match &item {
378                Ok(delivered) => (self.account)(delivered, &mut self.meter),
379                // The producer reported a failure as a terminal stream item — the
380                // ordinary mid-scan failure path (issue #1704). Counted here, at the
381                // one boundary every streaming surface crosses, and passed through
382                // untouched.
383                Err(e) => self.count_forwarded_error(e),
384            }
385            return Some(item);
386        }
387        // Terminal: the producer is finished, dead, or about to be joined. Emit this
388        // operation's read totals exactly once (idempotent; `Drop` is the backstop
389        // for a consumer that stops polling early).
390        self.meter.finish();
391        // Channel closed: the producer dropped its sender. Join it to learn WHY.
392        let outcome = match &mut self.task {
393            // `JoinHandle: Future + Unpin`, so `&mut JoinHandle` is itself a future:
394            // awaiting it polls the join WITHOUT taking ownership. A cancellation
395            // here drops only this borrow.
396            TaskState::Running(handle) => handle.await,
397            // A proven-clean completion is the ONLY route to end-of-stream.
398            TaskState::Finished => return None,
399            TaskState::Died { cancelled } => {
400                let err = sticky_dead_task_error::<T>(*cancelled);
401                self.count_own_failure(&err);
402                return Some(Err(err));
403            }
404        };
405        // No `.await` between observing the outcome and recording it, so the verdict
406        // cannot be lost to a cancellation.
407        match outcome {
408            Ok(()) => {
409                self.task = TaskState::Finished;
410                None
411            }
412            Err(join_err) => {
413                // A CANCELLED task (aborted, or its runtime shut down) is a distinct
414                // cause from a panic and gets the error the doc above already promised
415                // for it: `Error::Cancelled`. Nothing in the crate aborts these tasks
416                // today, so this arm is about the doc being TRUE — and about the next
417                // caller that does abort one getting an honest cause rather than an
418                // internal-invariant-violated report.
419                let cancelled = join_err.is_cancelled();
420                self.task = TaskState::Died { cancelled };
421                let err = if cancelled {
422                    Error::Cancelled
423                } else {
424                    dead_scan_task_error::<T>(&join_err)
425                };
426                // A dead producer IS a failed scan (issue #1704) — the case that
427                // previously reached the consumer as an error while the operator's
428                // error dashboard stayed clean.
429                self.count_own_failure(&err);
430                Some(Err(err))
431            }
432        }
433    }
434}

436impl<T: ScanStreamItem> Drop for JoinedStream<T> {
437    /// Account the rows the producer had ALREADY MATERIALISED and enqueued but this
438    /// consumer never polled, then emit this operation's read totals (issue #1701,
439    /// roborev F2).
440    ///
441    /// # Why draining is the honest accounting
442    ///
443    /// Rows are accounted as they cross [`recv`](JoinedStream::recv), which is the
444    /// only place this type sees them. A `LIMIT` consumer — the COMMON case, and the
445    /// one real caller of the per-row streaming surface — stops polling early and
446    /// drops the stream while the bounded channel still holds rows the producer
447    /// decoded, sent, and can never take back. Emitting only the polled rows
448    /// understated `read.rows`/`read.partitions` while `read.bytes` still counted the
449    /// chunks those rows were decoded from, so an amplification ratio built from the
450    /// two was wrong in the exact case it matters, and the documented
451    /// "rows materialised by the read path" was contradicted by its own metric.
452    ///
453    /// `try_recv` is non-blocking and the receiver is dropped immediately after, so
454    /// this neither waits for the producer nor changes the teardown behaviour. Each
455    /// item is accounted EXACTLY once: a polled row was accounted in `recv` and is no
456    /// longer in the channel; a buffered row is accounted here and was never polled.
457    fn drop(&mut self) {
458        // R2: CLOSE the channel BEFORE draining. Without it a producer still running
459        // can complete a send in the window between the last `try_recv() == Empty` and
460        // the receiver's destruction, and that row — already decoded, already
461        // enqueued — is discarded AFTER the meter finished, making an abandoned
462        // scan's totals race-dependent. `close()` makes every in-flight and later
463        // send fail, so the set of enqueued rows is FIXED before the drain reads it;
464        // buffered messages stay receivable, which is what the drain then collects.
465        self.rx.close();
466        while let Ok(item) = self.rx.try_recv() {
467            if let Ok(delivered) = &item {
468                (self.account)(delivered, &mut self.meter);
469            }
470        }
471        self.meter.finish();
472    }
473}

505        task: JoinHandle<()>,
506        meter: ReadOpMeter,
507    ) -> Self {
508        Self::new_measured(rx, task, meter, account_batch_item)
509    }
510}

512/// The fail-closed error for a scan producer task that died without reporting
513/// (issues #3106, #3124).
514///
515/// [`Error::Internal`] (not `Corruption`, not `Storage`): nothing suggests the
516/// `Data.db` is bad — an internal invariant was violated — and `Internal` is
517/// `is_recoverable() == false`, which is honest for a deterministic failure that a
518/// retry would reproduce. The panic message is carried in the payload so the
519/// failure is diagnosable rather than anonymous.
520fn dead_scan_task_error<T: ScanStreamItem>(join_err: &tokio::task::JoinError) -> Error {
521    Error::internal(format!(
522        "{}: the scan task DIED without reporting ({join_err}) — the result set is \
523         TRUNCATED and cannot be reported as a complete scan (issues #3106/#3124)",
524        T::STREAM_KIND
525    ))
526}
527
528/// Re-report for a consumer that keeps polling after the dead-task error, preserving
529/// the CAUSE the first report gave (a cancellation stays `Error::Cancelled`).
530fn sticky_dead_task_error<T: ScanStreamItem>(cancelled: bool) -> Error {
531    if cancelled {
532        return Error::Cancelled;
533    }
534    dead_scan_task_error_after_report::<T>()
535}
536
537/// Re-report for a consumer that keeps polling after the dead-task error. The
538/// `JoinError` is consumed by the join, so this restates the verdict rather than
539/// re-deriving it — what matters is that it is still an ERROR, never a clean end of
540/// stream.
541fn dead_scan_task_error_after_report<T: ScanStreamItem>() -> Error {
542    Error::internal(format!(
543        "{}: the scan task DIED without reporting (already reported) — the result \
544         set is TRUNCATED and cannot be reported as a complete scan (issues \
545         #3106/#3124)",
546        T::STREAM_KIND
547    ))
548}

550/// Per-row streaming scan handle (issue #3124): `SSTableReader::scan_stream`,
551/// `SSTableManager::scan_stream`, `StorageEngine::scan_stream` and the
552/// cross-generation `stream_generations_for_read` all return this instead of a bare
553/// `mpsc::Receiver`, so a producer that dies mid-scan is an ERROR at every one of
554/// those boundaries rather than a short, successful-looking result set.
555pub type RowScanStream = JoinedStream<(RowKey, ScanRow)>;
556
557/// The batched streaming scan's consumer handle: the batch channel PLUS the driver
558/// task that feeds it, so end-of-stream is an observed fact (issue #3106). Behaviour
559/// and API are unchanged from when this was its own `struct` (issue #3106); only the
560/// item type is fixed here.
561pub type BatchedScanStream = JoinedStream<Vec<(RowKey, ScanRow)>>;
562
563impl SSTableReader {
564    /// Open the batched streaming scan's cursor — the FIRST thing the driver task
565    /// does, ABOVE the `requires_chunk_stitching()` branch, i.e. on every format.
566    ///
567    /// A named seam because it is the SINGLE test-only fault checkpoint for this
568    /// task (issue #3106), and it is here precisely because it is
569    /// format-branch-independent: a checkpoint inside either branch fires only for
570    /// the formats that take that branch, so it can silently not fire and leave a
571    /// test passing vacuously. Killing the task here reproduces exactly the
572    /// condition the fix is about — the task's sender drops with no error and no
573    /// terminator — for any reader, and the join that catches it wraps the whole
574    /// task, so the property proven is branch-agnostic.
575    pub(super) async fn open_batched_scan_cursor(&self) -> Result<super::ScanCursor> {
576        crate::storage::producer_fault::inner_scan_task_checkpoint(|| self.file_path());
577        self.new_scan_cursor().await
578    }
579
580    /// Decode one `Data.db` block for the batched NON-STITCHING streaming scan,
581    /// pinning `read_shadowing = true` for this scan in ONE place.
582    ///
583    /// Deliberately carries NO fault checkpoint (issue #3106, roborev): it is
584    /// reached only by readers whose format takes the non-stitching branch, and no
585    /// fixture in the tree does, so a checkpoint here would be an armable-but-never-
586    /// armed seam — latent confusion suggesting coverage that does not exist. The
587    /// task-level checkpoint in [`Self::open_batched_scan_cursor`] covers both
588    /// branches, which is what the join it proves is scoped to anyway.
589    pub(super) fn parse_batched_block(
590        &self,
591        block: &[u8],
592        schema: Option<&crate::schema::TableSchema>,
593        now_secs: Option<i64>,
594    ) -> Result<Vec<(TableId, RowKey, ScanRow)>> {
595        self.parse_block_entries_at_now(block, schema, true, now_secs)
596    }
597}
